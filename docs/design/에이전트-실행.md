# 에이전트 실행

- 에이전트는 PTY 하나에서 도는 실제 TUI다. tmux는 쓰지 않는다. PTY는 노드마다 따로 뜨는 PTY 호스트(`loom pty-host`, [src/node_host/host.rs](../../src/node_host/host.rs))가 쥔다. 데몬은 호스트에 붙어 출력을 화면에 나눠 준다. Orca도 PTY를 데몬과 따로 사는 프로세스가 쥔다.
  - 데몬이 다시 시작하거나 새 실행 파일로 바뀌어도(Rust 병합 뒤 다시 띄우기) 노드 프로세스, 최근 출력(256KB), 토큰이 남는다. 새 데몬은 시작할 때 `running` 노드마다 호스트에 다시 붙고, 호스트가 backlog를 먼저 보낸다. 카드는 다시 연결한 것처럼 앞 출력을 보인다.
  - 호스트는 루프백 TCP의 OS가 고른 포트에서 듣고, 데몬은 그 주소를 `<데이터 폴더>/pty/nodes/<노드 id>`(로그인 창은 `pty/logins/`)에 둔다. 루프백 신뢰는 데몬 HTTP와 같다. Windows에도 같은 코드가 돈다.
  - 데몬과 호스트 사이 프레임은 판 번호를 첫 프레임에 넣는다([src/node_host/wire.rs](../../src/node_host/wire.rs)). 낸 판의 프레임은 바꾸지 않는다. 새 데몬이 옛 실행 파일이 띄운 호스트와 말해야 하기 때문이다.
  - 호스트는 프로세스가 끝나면 종료 코드를 데몬에 넘기고 끝난다. 붙은 데몬이 없으면 10분 기다린다. 그 사이 다시 시작한 데몬은 코드를 받는다.
  - 호스트가 데몬에 쓰는 한 프레임이 10초를 넘기면 호스트는 그 연결을 닫는다. 새 데몬과의 인사는 그 쓰기를 기다리지 않는다. Windows에서 끝난 데몬의 연결이 열린 채 남아, 다시 뜬 데몬이 도는 노드를 `exited(?)`로 두었기 때문이다(「실측 근거」 2026-10-23 PTY 호스트).
  - WSL 노드의 프로세스가 끝나면 데몬이 그 배포판 안에서 환경에 그 프로세스의 `LOOM_TOKEN`과 배포판 기본 계정의 `HOME`이 함께 있는 프로세스를 끝낸다(`wsl::end_token`). 프로세스 나무는 따라가지 않는다. TERM 뒤 2초에 환경을 다시 읽어 아직 맞는 프로세스에만 KILL을 보낸다. `wsl.exe`는 30초 안에 끝나지 않으면 끝낸다. 다시 시작한 데몬의 연결을 호스트 주소가 거부한 노드(호스트가 끝났다)도 같다. 인사하지 않은 호스트의 노드와 호스트 연결만 끊긴 노드(`Exit::Lost`)는 끝내지 않는다. 노드 프로세스가 아직 살았을 수 있다. Windows는 닫힌 루프백 포트에 2.03~2.43초 뒤에야 연결 거부를 돌려줘서 연결 상한은 5초다(2026-10-24 실측). 다시 띄운 프로세스는 새 토큰을 받으므로 남는다. Cursor 훅의 `/init` 중계가 남았기 때문이다(「실측 근거」 2026-10-23 WSL Cursor 훅).
  - 데몬이 시작할 때 다시 붙지 않은 호스트는 끝낸다: 데몬이 꺼진 동안 지운 노드, 앞 데몬의 로그인 창(창 번호는 데몬마다 0부터 센다).
  - 호스트에서는 `scripts/host.sh`가 데몬만 다시 띄운다(「[배포](배포.md#배포)」). PTY 호스트는 데몬과 다른 프로세스 그룹이라 데몬 터미널의 Ctrl+C를 받지 않고, 데몬이 끝나면 init이 부모가 된다. 실행 파일은 새 파일로 바꿔 넣는다(rename). 도는 호스트는 옛 파일을 계속 쓴다.
  - Windows도 같다. 앱 업데이트, 앱 창 닫기, 앱 강제 종료 뒤에도 노드가 살고, 다음에 연 앱의 데몬이 다시 붙는다(2026-10-21 사람 지시 "exe 업데이트할때 노드 작업 없어지지 않고 작업이 계속 진행되도록 해줘 orca처럼"). 방법은 「[데스크톱 앱](데스크톱-앱.md#데스크톱-앱)」에 있다.
- CLI마다 실행 프로필을 둔다. 프로필은 메시지 연동(훅·app-server·서버 API)이 있는 에이전트다. 지금은 Claude Code, Codex, OpenCode 2, Cursor, Pi, OMP 여섯이다. 프로필이 바뀌는 이유는 CLI 버전이다.
- 프로필이 있으면 프로필이 시작 인자를 정한다. 카탈로그 `args`는 쓰지 않는다. 카탈로그 `args`는 Orca가 연동 없이 띄울 때의 인자다. 예: OpenCode 2의 `--standalone`은 `--server`와 함께 쓸 수 없다.

| 프로필 | loom 사용법 지시 | 상태·전달 경로 |
|---|---|---|
| Claude Code | `--append-system-prompt` | `--settings`로 넘긴 훅 6개가 `loom hook`을 부른다(SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop). 형식과 인자는 [src/profile/claude.rs](../../src/profile/claude.rs)에 있다 |
| Codex | app-server의 `-c developer_instructions=…`(TUI에 넘기면 스레드에 들어가지 않는다) | 데몬이 노드마다 `codex app-server --listen ws://127.0.0.1:0`을 띄우고 TUI를 `codex --remote <주소>`로 붙인다. 데몬도 같은 서버에 연결해 스레드 상태를 보고 `turn/*` 요청으로 전달한다. 훅은 쓰지 않는다. 연결은 [src/codex_server.rs](../../src/codex_server.rs), 요청 내용은 [src/profile/codex.rs](../../src/profile/codex.rs)에 있다 |
| OpenCode 2 | 세션 지시 항목 `loom`(`PUT /api/experimental/session/{id}/instructions/entries/loom`) | 데몬이 노드마다 `opencode2 serve --hostname 127.0.0.1 --port 0`을 띄우고 `POST /api/session`으로 세션을 만든다. TUI는 `opencode2 --server <주소> --session <id>`로 붙는다. 데몬은 세션 입력함(`POST /api/session/{id}/prompt`)으로 전달한다. 규칙과 전달 작업은 [src/profile/opencode2/mod.rs](../../src/profile/opencode2/mod.rs), 서버 연결은 [src/profile/opencode2/server.rs](../../src/profile/opencode2/server.rs)에 있다 |
| Cursor | sessionStart 훅 둘의 `additional_context`: 통신 명령(`loom cursor-hook`)과 상시 지시(`loom cursor-rules`). Cursor는 훅 하나의 맥락이 10,000자를 넘으면 버린다 | `--plugin-dir <데이터 폴더>/plugin`. 그 폴더의 `.cursor-plugin/plugin.json`이 훅 파일 `cursor-hooks.json`을 가리킨다. 훅(sessionStart, beforeSubmitPrompt, preToolUse, postToolUse, postToolUseFailure, stop)이 `loom cursor-hook`을 부른다. 형식과 인자는 [src/profile/cursor.rs](../../src/profile/cursor.rs)에 있다 |
| Pi | `--append-system-prompt`(Claude와 같은 글) | `--extension <데이터 폴더>/plugin/pi-loom.ts`. 데몬이 시작할 때 그 확장 파일을 쓴다. 확장이 세션마다 `loom pi-hook` 하나를 띄워 두고 pi 사건(session_start, before_agent_start, tool_call, tool_result, agent_end, agent_settled)마다 stdin에 `{"id", 사건}` 한 줄을 쓰고, stdout의 같은 `id` 답 `{"text"}`를 모델에 넣는다(메시징.md). 확장은 `bash` 도구도 바꿔 `run_in_background`와 기본 시간 제한을 준다. 사람의 `~/.pi/agent`는 고치지 않는다. 확장은 [src/profile/pi-loom.ts](../../src/profile/pi-loom.ts), 형식과 인자는 [src/profile/pi.rs](../../src/profile/pi.rs)에 있다 |
| OMP | `--append-system-prompt`(Pi와 같은 글. 기다림 줄만 omp의 bash에 맞춘다) | `--extension <데이터 폴더>/plugin/omp-loom.ts`. 데몬이 시작할 때 그 파일을 Pi와 함께 쓰는 훅 연결 `loom-hook.ts`와 같이 쓴다. 사건과 전달은 메시징.md에 있다. 사람의 `~/.omp/agent`는 고치지 않는다. 확장은 [src/profile/omp-loom.ts](../../src/profile/omp-loom.ts), 인자와 설정 파일은 [src/profile/omp.rs](../../src/profile/omp.rs)에 있다 |
| 프로필 없음 | 없음 | `loom wait`로만 메시지를 받는다 |

- 카드 머리의 모델·추론 강도(`NodeView.model`·`effort`)는 CLI가 알린 글 그대로다. 알리지 않으면 비운다. Claude: SessionStart 훅의 `model`, 그 뒤 훅마다 기록 파일 마지막 응답의 `message.model`·`effort`. Codex: 스레드 상태가 바뀔 때마다 `thread/read`의 `model`·`reasoningEffort`(구독하지 않은 연결에는 `thread/settings/updated`가 오지 않는다). OpenCode 2: `GET /api/event`의 `session.model.selected`(`<providerID>/<id>`, `variant`). Cursor: sessionStart·beforeSubmitPrompt·stop 훅 입력의 `model`(강도를 붙인 id, 예: `gpt-5.3-codex-low`). 도구 훅의 `model`은 강도를 뺀 이름이라 쓰지 않는다. Pi: 확장이 session_start·before_agent_start·agent_settled에 알리는 `<provider>/<id>`(예: `kta-hub/kta-chat-vl-pro`)와 생각 수준(`thinkingLevel`). 다시 띄울 때 `--model`·`--thinking`으로 돌려준다. OMP: 같은 확장 사건의 `<provider>/<id>`와 `pi.getThinkingLevel()`. 셋 다 TUI에서 바꾼 값은 다음 입력 뒤에 보인다(실측).

- 모든 권한 허용: 노드는 처음부터 승인 창 없이 모든 권한으로 뜬다. 사람이 띄운 노드와 `loom spawn` 자식이 같다. 인자는 카탈로그 항목의 `bypass` 필드다(「에이전트」). 설정에서 에이전트마다 끌 수 있다(`bypassOff`). `bypass`가 빈 에이전트는 CLI 기본 권한 모드로 뜬다.
  - 끄면 아래의 좁은 길을 쓴다: Claude는 loom 명령만 허용 목록에 넣고, Codex는 샌드박스에서 노드 문 주소만 연다. 켜면 이 길은 쓰이지 않지만 그대로 넘긴다.
  - Claude는 계정 폴더마다 첫 실행에 「Bypass Permissions mode」 동의 창을 띄운다. 동의는 사람의 보안 결정이라 사람이 카드 터미널에서 고른다. loom은 대신 누르지 않고 사용자 설정 파일을 고치지 않는다. 동의하면 Claude가 그 폴더의 `settings.json`에 `skipDangerousModePermissionPrompt`를 쓰고 다음부터 묻지 않는다.
- Claude `--settings`는 권한 허용 목록에 `loom guard`와 메시지 명령(`send`, `steer`, `interrupt`, `wait`, `done`)만 넣는다. 기본 권한 모드에서 사람이 없는 노드가 승인 창에서 멈추지 않게 한다. `loom spawn`은 `-- <명령>`으로 아무 명령이나 띄울 수 있어 넣지 않는다.
- 사람 문에는 토큰이 없다. 사람이 연 다른 웹 페이지는 두 문을 부르지 못한다. JSON 요청은 브라우저 사전 요청이 막고, 웹소켓과 DNS 재바인딩은 [src/daemon/origin.rs](../../src/daemon/origin.rs)가 막는다(`Host`는 IP나 `localhost`만, `Origin`은 `http://<Host>`만). 폰 원격은 「원격」의 예외 하나다.
- 사람의 기본 앱을 여는 두 라우트(`POST /api/files/open`, `POST /api/docs/{ID}`)는 `Origin` 머리글이 있는 요청만 받는다(`origin::from_page`). 브라우저와 앱의 WebView는 POST에 늘 붙인다. 노드 터미널의 curl·PowerShell은 붙이지 않으므로 403이다. 일부러 머리글을 넣는 요청은 막지 못한다. 근거: 2026-10-23 검토자의 시험이 사람의 앱에 시험 파일을 띄웠다. 사람 지시 "브리프 말고 기계적으로 차단해".
- Codex 샌드박스(`workspace-write`)는 셸 명령의 네트워크를 막는다. 그래서 데몬은 노드 문을 하나 더 연다. 노드 문은 노드 전용 루프백 주소 `127.76.77.1:<데몬 포트>`에서 듣고 `/api/agent/*` 가운데 `spawn`을 뺀 라우트만 둔다.
  - app-server에 `-c sandbox_workspace_write.network_access=true`, `-c features.network_proxy.enabled=true`, `-c features.network_proxy.domains={"127.76.77.1"="allow"}`를 넘긴다. 셸 명령은 Codex 프록시로만 밖에 닿는다. 프록시는 노드 문 주소 말고 모든 주소를 막는다. 파일 권한은 그대로다. 인자는 [src/profile/codex.rs](../../src/profile/codex.rs)의 `sandbox_args`에 있다.
  - `loom` 명령은 노드 문(`LOOM_URL`)에 Codex가 넣은 프록시 환경 변수(`ALL_PROXY`)로 닿는다. `loom spawn`만 데몬 주소(`LOOM_SPAWN_URL`)에 프록시 없이 간다. 샌드박스 안에서는 연결이 실패한다. 실패 메시지가 샌드박스 밖 실행 승인을 받으라고 적고, Codex 모델은 그 출력을 보고 승인을 요청한다. 사용법 지시(`developer_instructions`)에만 적었을 때는 요청하지 않았다.
  - 권한 프로필(`default_permissions`, `permissions.<이름>.network`)은 쓰지 않는다. TUI가 `thread/start`에 `sandbox: "workspace-write"`를 넣어 보내 프로필을 덮는다.
  - 설치한 Codex 버전이 고정 버전과 다르면 위 인자를 넘기지 않는다. 프록시가 뜨지 않는 버전에서 `network_access`만 켜지면 모든 주소가 열린다. 그때 Codex 노드는 loom 명령마다 승인을 묻고, 설정 화면의 버전 경고가 이 사실을 보인다.
  - 노드 문 주소에서 듣지 못하면(예: 이 루프백 주소가 없는 OS) 노드 문 없이 데몬 주소를 쓴다. 인자도 넘기지 않는다. Codex 노드는 loom 명령마다 승인을 묻는다.
  - 위험: 모든 주소(`0.0.0.0`)에서 듣는 다른 서비스는 샌드박스 안에서 `127.76.77.1`로 닿는다. 데몬을 `--listen 0.0.0.0:<포트>`로 띄우면 `spawn`도 그 길로 닿는다. Codex 도메인 규칙은 포트를 가리지 않고, unix 소켓 허용은 macOS만 된다(「실측 근거」). 그래서 더 좁힐 수 없다.
  - 신뢰하지 않은 폴더에서는 TUI가 `read-only`를 보낸다. `read-only`는 네트워크를 열지 않아 loom 명령마다 승인을 묻는다.
  - Windows에서는 위 인자를 넘기지 않는다. Codex는 Windows에서 `workspace-write`를 `read-only`로 낮추고, 프록시는 관리자 권한 Windows 샌드박스가 있어야 뜬다(「실측 근거」). 그래서 Codex 노드는 loom 명령마다 승인을 묻는다.
- 사용자의 `~/.claude`, `~/.claude.json`, `~/.codex`, `~/.cursor`, `~/.config/opencode`, `~/.local/share/opencode` 파일은 고치지 않는다. OpenCode 설정은 명령 인자, 환경 변수, 세션 API로만 넘긴다. loom이 그 폴더로 CLI(`claude auth status`, `codex app-server`)를 부를 때 CLI가 스스로 쓰는 것은 사용자가 CLI를 실행할 때와 같다. 계정 설정의 시스템 기본 [로그인]·[로그아웃]도 CLI가 쓴다(「계정과 사용량」). 하나의 예외: 노드를 시스템 기본 계정으로 옮길 때 그 세션 기록 파일을 같은 상대 경로로 복사한다(「계정 전환」).
- Codex app-server는 `[experimental]`이다. 빌드 때 `codex app-server generate-json-schema`로 받은 스키마를 저장소에 고정하고 Rust 타입을 그 스키마에서 만든다. 데몬은 시작할 때 Codex 버전을 확인한다. 고정한 버전과 다르면 화면에 경고를 띄우고 Codex 노드는 그대로 띄운다.
- 고정한 스키마는 쓰는 요청·알림의 파일만 둔다([src/profile/codex/schema/](../../src/profile/codex/schema/)). `build.rs`가 `typify`로 Rust 타입을 만든다.
- 데몬 연결은 스레드를 구독하지 않는다(`thread/resume`을 부르지 않는다). 구독하면 승인 요청도 데몬 연결로 와서 사람이 TUI에서 승인하지 못한다. 구독하지 않아도 `thread/started`·`thread/status/changed`는 온다. 서버가 따로 만드는 제목용 임시 스레드(`ephemeral`)는 거른다.
- Codex 셸 명령은 TUI가 아니라 app-server 아래에서 돈다. 그래서 app-server도 노드 환경(`LOOM_URL`, `LOOM_SPAWN_URL`, `LOOM_TOKEN`, `LOOM_TASK_DIR`, `PATH`)을 받는다. Codex 셸 스냅샷은 로그인 셸의 `PATH`를 다시 적용한다. 그래서 `-c shell_environment_policy.set.PATH=<노드 PATH>`로 노드 `PATH`를 다시 넣는다.
- 노드 문의 포트는 데몬 포트와 같다. 노드 환경의 `LOOM_URL`은 노드가 끝날 때까지 바뀌지 않으므로, 다시 시작한 데몬도 같은 주소에서 들어야 한다. 그 포트를 쓸 수 없으면(예: `--listen 0.0.0.0:<포트>`) OS가 고른다. 그때 앞 데몬의 노드는 다시 시작한 뒤 loom 명령이 닿지 않는다.
- 노드 서버(Codex app-server, OpenCode 2 서버)도 노드처럼 데몬과 따로 산다(Unix: 새 프로세스 그룹). Codex TUI는 app-server에 붙어 있어 서버가 끝나면 노드도 쓸 수 없다. 포트는 loom이 골라 넘기고 서버 출력은 읽지 않는다. 출력 파이프는 데몬과 함께 닫혀 서버가 쓰기에 실패하기 때문이다.
  - 다시 붙는 값(주소, 서버 PID, Codex 노드 스레드, OpenCode 2 세션과 비밀번호)은 노드와 함께 DB에 남긴다. 새 데몬은 그 값으로 다시 연결하고 전달 작업을 다시 시작한다. Codex는 `thread/started`가 다시 오지 않으므로 남긴 스레드 id로 `thread/read`해 상태를 읽는다.
  - 노드가 끝나면 데몬이 그 서버를 끝낸다. 데몬이 다시 시작할 때 호스트가 없는 노드의 서버도 끝낸다.
- OpenCode 2 서버는 HTTP Basic(`opencode:<비밀번호>`)만 받는다. 데몬이 노드마다 무작위 비밀번호를 만들어 서버와 TUI에 `OPENCODE_PASSWORD`로 넘긴다. 셸 명령도 이 값을 본다. 그 노드 서버에만 쓰이는 값이다.
- OpenCode 2 셸 명령도 TUI가 아니라 서버 아래에서 돈다. 서버가 노드 환경을 받는다. 셸은 서버 환경을 그대로 받아 `PATH`를 다시 넣지 않아도 된다(실측).
- OpenCode 2 권한: 데몬은 노드 세션을 만들 때 `permissions`에 모든 권한 허용 규칙(`*` → `allow`)을 넣는다. 사용자 설정이 `bash`를 `ask`로 두어도 노드는 승인 창을 띄우지 않는다(「실측 근거」). 사용자 설정 파일은 고치지 않는다.
- 데몬은 시작할 때 `opencode2 --version`도 확인한다. 고정한 버전(2.0.32)과 다르면 Codex와 같이 화면에 경고를 띄운다.

## 내장 스킬

loom은 스킬 다섯 개를 싣는다: `o-mode`, `ste-orwell`, `user-doc`, `raptor-3`(2026-10-21 사람 지시 "loom 모드, ste, 사용자 문서 작성 스킬도 loom 에 내장시켜줘"), `ask-human`(사람에게 묻는 표준, 2026-10-21 사람 지시 "질문 방식을 가르치는 스킬은 별도로 분리해서 loom에서 상시 포함되는 스킬로 만들어라"). Loom 절차 스킬도 `o-mode`(orchestration mode)라 부른다. 사람은 Orca에서도 loom에서도 `o-mode`로 부르고, 실행 환경이 절차를 고른다: loom 노드는 이 스킬, 그 밖은 사람의 Orca 판 `o-mode`(2026-10-21 사람 지시 "둘다 o-mode 이름으로 호출하고 싶고 실행환경에 따라서만 적용 스킬을 다르게 하고 싶다"). 사람의 Orca 판은 첫 줄에서 `LOOM_TOKEN`이 있으면 이 스킬로 넘긴다. Claude에서는 두 판을 플러그인 이름으로 가른다: loom 판 `loom:o-mode`, 사람의 Orca 판 `orca:o-mode`(사람 쪽 로컬 플러그인 `orca`, 2026-10-21 사람 지시 "이 스킬을 orca:o-mode로 만들어"). 노드 에이전트는 사람이 스킬을 설치하지 않아도 이 스킬을 쓴다.

- 스킬 글은 ASD-STE100과 조지 오웰의 글쓰기 6원칙("Politics and the English Language")을 따른 영어로 쓴다(2026-10-24 사람 지시 "내장 스킬들 모두 ste-100 을 적용한 영어로 작성하고 랩터3 적용할 것, 그리고 조지 오웰의 글쓰기 6원칙도 적용할 것"). 에이전트가 사람에게 쓰는 글의 언어는 `ste-orwell`이 정한다(사람의 언어). 오웰 6원칙은 `ste-orwell`의 상시 규칙이고, 옛 이름은 `ste-100`이다(Q843·Q844·Q845). 옛 설정 키 `ste100`은 `steOrwell`로 읽는다. loom이 맞추는 글(명령, 파일 이름, 역할 이름 총괄·코디·워커·검토자, 문서 머리 줄 `응답할 곳`)은 그대로 둔다. Cursor 세션 시작 훅 글(사람에게 묻기, `ste-orwell`, 랩터-3 「While you work」, o-mode 본문)은 10,000자 이하다(시험이 막는다). 그래서 o-mode의 드문 절차(목업 승인, 릴리스, 관문 스크립트 없는 저장소)는 `reference.md`에 둔다.
- 원본은 저장소 [skills/](../../skills/)다. 사람의 `~/.agents/skills`의 같은 스킬은 이 폴더를 가리키는 링크다. 실은 스킬은 같이 실은 파일만 링크한다(테스트가 막는다). STE-100 원문 PDF는 싣지 않는다. ASD가 허가 없는 복제를 금지한다.
- 실행 파일이 `rust-embed`로 [skills/](../../skills/)를 넣는다. 데몬은 시작할 때 플러그인 폴더를 지우고 다시 푼다. 폴더는 Claude 플러그인 꼴이다(`.claude-plugin/plugin.json`, `skills/<이름>/`). 코드는 [src/skills.rs](../../src/skills.rs)에 있다.
- 켜고 끄기: 「설정 › 에이전트 › 내장 스킬」의 스위치 네 개(기본 켜짐, 설정 `alwaysOn`). 목업은 [skill-options.html](../mockups/skill-options.html)이다(2026-10-21 사람 지시 "o-mode·user-doc 도 옵션에 추가해", 승인 "권장안대로"). 끈 스킬은 새로 띄우는 노드에 주지 않는다: 상시 지시에서 그 글을 빼고 스킬 폴더에서도 뺀다. 이미 뜬 노드는 그대로다. loom 명령 사용법은 스킬이 아니라 늘 들어간다. `ask-human`은 스위치가 없다: 모든 노드(부모 없는 노드와 자식)의 상시 지시 맨 앞에 본문이 들고, 모든 조합의 폴더에 든다. loom 명령 사용법의 `loom ask` 줄에도 필수 한 줄(부모가 없으면 `loom ask`로만 묻는다)이 있다. 두 글은 런타임마다 가장 강한 지시 자리에 든다: Claude `--append-system-prompt`, Codex `developer_instructions`, OpenCode 2 세션 지시 항목, Cursor sessionStart 훅(2026-10-21 사람 지시 "loom 기능과 직결되므로 … 각 에이전트에 강하게 명시되어야 함").
  - 데몬은 스위치 조합 16개마다 폴더를 먼저 푼다(폴더 하나 약 80KB). 노드를 띄울 때 풀면 동시에 뜨는 노드끼리 같은 폴더를 쓴다. 모두 켠 조합은 `<데이터 폴더>/plugin`, 다른 조합은 `<데이터 폴더>/plugin-off/<끈 스킬>`(예: `ste-orwell+raptor-3`)이다. 모두 켠 조합이 옛 경로라서 판을 올려도 이미 뜬 노드가 스킬을 잃지 않는다.
  - Cursor 훅(`loom cursor-rules`)은 스위치를 노드 환경 `LOOM_SKILLS`(JSON)로 받는다. 값이 없으면 모두 켜짐이다.

- 상시 지시: `ste-orwell` 본문, 랩터-3 「While you work」 절, o-mode 글을 loom 사용법 지시 끝에 붙인다(위 표의 「loom 사용법 지시」 길). 켠 스킬의 글만 붙인다. 모든 노드가 처음부터 본다.
  - `ste-orwell`은 언어를 고정하지 않는다. 사람에게 보이는 글은 사람이 노드에 쓰는 언어로 쓴다. 사람에게 하는 한국어 글(보고, 질문, user-doc 문서, 화면)은 합니다체로 쓰고, 저장소 문서와 커밋은 한다체로 둔다(2026-10-24 사람 지시 "말투는 공손하게"). 화면 언어 설정은 쓰지 않는다. 기본값 「시스템」은 브라우저 언어라 데몬이 모른다. 사람의 STE 플러그인이 프롬프트마다 넣는 한 줄 알림은 loom에 없다.
  - o-mode 글은 노드가 시작할 때의 자리로 고른다(2026-10-21 사람 지시 "o-mode도 다른 스킬 처럼 상시 적용이었으면 한다"). 부모 없는 노드(사람이 띄운 노드)는 `o-mode/SKILL.md` 전체를 받아 총괄이 된다. `loom spawn`으로 뜬 자식은 `o-mode/agent-rules.md`만 받는다. 역할은 브리프나 `--role`이 정한다. 자식에게 총괄 절차를 주지 않는다.
  - 자리는 띄울 때 한 번 정한다. 뒤에 부모가 바뀌어도(`loom adopt`, `loom rm`의 손자 옮기기) 뜬 노드의 지시는 그대로다. 부모를 잃은 노드는 자식 규칙을 지닌 채 남는다. 총괄 절차가 필요하면 `o-mode` 스킬을 부른다.
  - 같은 글을 따로 두지 않는다. 상시 지시는 실은 스킬 파일을 그대로 읽는다. 스킬은 전처럼 `loom:o-mode`로 부를 수 있다. 브리프에는 공통 규칙 경로를 적지 않는다.
  - 규칙 하나는 한 곳에 둔다(2026-10-23 사람 승인 Q687 A, 보고서 R14 「loom 사용 일원화 계획」. 사람 지시 "에이전트가 loom을 다루는 방식은 최대한 기계적이고, 표준화, 일관화 되며 해당 방식을 제대로 사용했는지 검증 가능(트레이스) 해야한다"). 명령의 꼴과 그 규칙(브리프 머리, `loom done`을 부를 때, 종류 낱말, 크기 제한, 진행 보고 금지)은 loom 사용법(`COMMUNICATION_USAGE`)에만 둔다. 스킬은 사용법에 없는 절차만 싣는다. loom이 거절로 막는 규칙(링크 꼴, 선택지 꼴)은 스킬에 다시 적지 않는다. 거절 글이 맞는 꼴을 알린다. 그때만 필요한 안내(열린 질문 닫기)는 그 턴의 훅 글이 싣는다.
  - 크기(Q687 A 뒤 실측): 상시 지시는 자식 약 5,200자, 부모 없는 노드 약 7,800자, 사용법은 약 3,800자다. 지우기 전에는 부모 없는 노드 9,454자였다. Windows 명령 줄 상한(32,767자)보다 작다. Claude는 이 글을 시작 인자로 받는다. Cursor는 훅 출력으로 받는다. 상시 지시만 sessionStart 훅 하나로 넘기고, 테스트가 10,000자 상한을 지킨다. 2026-10-23 실측으로 시작 글은 Claude 입력 토큰의 약 4%였다. 역할별로 글을 나누지 않는다. 검토자 글을 줄여도 하루 약 0.02%이고 조합만 는다.
  - o-mode 역할 운영(Q687 A, 2026-10-23 실측: 노드 230개 가운데 검토자 45%, 메시지 46%가 총괄을 거침, 총괄 한 세션이 Claude 입력의 21%): 총괄은 한두 줄 일만 직접 하고 그 밖은 코디 1명에게 맡긴다. main 대상 브랜치는 고위험 범위(저장 형식, 동시성, 전달·통신, 인증, 프로세스 수명, 모듈 사이 계약)를 바꾸면 검토자 2명(검토자, 보조 검토자), 그 밖(화면 글, CSS·배치, 문서, 테스트만)은 검토자 1명을 둔다. 관문이 정하고, 모르면 2명이다(2026-10-25 사람 결정 Q995 C: 검토 속도). 그 전 규칙은 늘 2명(Q859), 처음 규칙은 1명에 고위험 브랜치만 둘째를 더했다. 담당과 관문은 지금처럼 모든 검사를 돈다(D6 B). 총괄 자식, 검토자 자리, 병합 뒤 회수는 데몬이 지킨다(R17, Q789 A: 「설정」 o-mode 역할, 「병합 관문」). 총괄 맥락 알림은 두지 않는다. Q789 사람 답: "이건 새로고침하고, 다시 총괄역할 세팅하고, 이전 컨텍스트가 날라간다는 점에서 잃는게 더 크다고 판단됨".

## 에이전트

- 카탈로그는 Orca의 에이전트 표를 옮긴 데이터 [src/agents.json](../../src/agents.json)이다. 44개다. 목록을 지어내지 않는다. Orca가 표를 고치면 이 파일만 다시 옮긴다.
  - `claude-agent-teams`는 뺐다. Orca 안에서만 쓰는 Claude 팀 모드라 따로 띄울 CLI가 없다.
  - 한 줄은 `id`, `label`, `cmd`, `aliases`, `args`, `prompt`, `profile`, `bypass`, `homepage`다.
  - `bypass`는 모든 권한 허용 인자다. CLI 도움말과 실행으로 확인한 에이전트에만 넣는다(「실측 근거」). 새 CLI는 이 필드를 더하면 설정에 스위치가 생긴다.
- `prompt`는 첫 지시문을 넘기는 방법이다. Orca의 `promptInjectionMode`를 옮겼다.

| `prompt` | 명령 | Orca 값 |
|---|---|---|
| `"argv"` | `<cmd> <args…> <지시문>` | `argv` |
| `{"argvAfter": "--"}` | `<cmd> <args…> -- <지시문>` | `argv` + 구분자 |
| `{"flag": "--prompt"}` | `<cmd> <args…> --prompt <지시문>` | `flag-prompt`, `flag-prompt-interactive`, `flag-interactive` |
| `"none"` | 지시문을 넘기지 않는다 | `stdin-after-start`, `hermes-query` |

- `"none"`인 에이전트는 Orca가 시작 뒤 입력창에 지시문을 써 넣는다. loom은 PTY에 글자를 쓰지 않으므로(「메시징」) 첫 지시문을 받지 않는다. 첫 지시문은 `loom spawn`만 넘긴다.
- 탐지: 데몬이 찾기 `PATH`에서 `cmd`, 그다음 `aliases`를 찾는다(`which`). 찾기 `PATH`는 데몬의 `PATH`다. Windows에서는 그 뒤에 레지스트리의 시스템·사용자 `Path`를 찾을 때마다 새로 읽어 붙인다(Q808 A). macOS·Linux에서는 로그인 셸(`$SHELL -ilc`, 3초 제한)의 `PATH`를 앞에 두고, 데몬 `PATH`에만 있는 폴더를 뒤에 붙인다(Q839 A). 셸이 없거나 실패하면 데몬 `PATH`를 쓴다. 읽은 값은 2초 동안 다시 쓴다. 그래서 한 번 찾기(명령 이름 최대 50개)와 노드 띄우기는 셸을 한 번만 띄운다. 2026-10-24 실측: 이 PC의 `bash -ilc` 10번이 0.02~0.04초였다. 그래서 데몬이 뜬 뒤 설치기가 `PATH`나 셸 설정(`~/.zshrc` 등)에 더한 폴더도 보인다. 새 노드 창과 설정 창을 열 때, [다시 찾기]를 누를 때 다시 찾는다. 새 노드 창은 지금 목록을 바로 보이고, 결과가 오면 목록을 바꾼다. 노드를 띄울 때도 찾은 경로로 띄우고, 노드의 `PATH`는 그때 새로 읽은 찾기 `PATH` 앞에 loom 실행 파일 폴더를 둔 것이다. 데몬이 실행 파일을 찾는 곳(서버, `node`, 계정 로그인)은 모두 찾기 `PATH`를 쓴다.
  - Windows 데몬은 위치(아래 「계정과 사용량」)마다 찾는다. WSL 배포판은 `wsl.exe` 한 번으로 카탈로그 명령을 모두 찾고 Codex·OpenCode 2 버전을 읽는다. 설정 › 에이전트는 에이전트마다 줄 하나에 위치마다 메타 줄과 버전 경고를 둔다. 새 노드 창은 저장소 위치에 설치된 에이전트만 고르게 하고, 다른 위치에만 있으면 「WSL에 없음」·「이 PC에 없음」을 붙인다(목업 [wsl-place.html](../mockups/wsl-place.html) ④·⑥a, Q282 A).
- 새 노드 창은 프로필 하나만 고른다. 검색 입력 아래에 카탈로그 전체를 보인다. 줄을 누르거나 Enter를 누르면 그 프로필로 바로 띄운다. [만들기] 단추는 없다(2026-10-20 사람 지시 "새노드는 리스트 아이템을 클릭하면 바로 해당 노드가 생성되는걸로 변경"). 명세는 [settings.html 5번](../mockups/settings.html#u5)이다.
  - 순서: 「기본 셸」, 설치됨(카탈로그 순서), 설치하지 않음(2026-10-24 사람 지시 "새노드 기본 쉘을 첫번째로 나타나개 순서 변경"). 설치하지 않은 항목은 고를 수 없다. 화면은 에이전트 이름으로 분기하지 않는다.
  - `profile`이 없는 항목에는 「터미널만」을 붙인다. 그 노드는 조정·중단을 받지 않고 `loom wait`로만 받는다.
  - 처음 값은 「최근」이다: 부모 없는 노드 가운데 마지막에 만든 노드의 에이전트다. 따로 저장하지 않는다. 그 에이전트가 없으면 설치한 첫째 에이전트다. 한계: 부모를 지워 부모가 없어진 자식도 이 계산에 든다.
  - 데몬이 PATH를 찾는 동안(약 2초) 목록은 비어 있고 [만들기]를 막는다.
- 노드 목록에는 에이전트 `id`를 남긴다. 「기본 셸」로 띄운 노드와 `loom spawn -- <명령>` 자식은 에이전트가 없다. 카드 머리는 카탈로그의 `label`을, 에이전트가 없으면 「터미널」을 보인다.
- 넣지 않은 Orca 기능: 설치 버튼, 실행 파일 경로 재정의, 기본 인자·환경 변수. `loom spawn -- <명령>`이 같은 일을 한다. 기본 에이전트와 에이전트 켜기·끄기도 넣지 않았다. 「최근」과 검색 목록이 같은 일을 한다.

## 계정과 사용량

- 공급자(Claude, Codex)마다 계정을 여럿 둔다. 「시스템 기본」은 사용자의 `~/.claude`·`~/.codex`다. 지울 수 없다.
  - 시스템 기본 줄은 CLI가 준 이메일을 이름으로 보이고 「시스템 기본」 배지를 단다. 로그인하지 않았으면 [로그인], 로그인했으면 [로그아웃]을 둔다. [로그인]은 아래 로그인 창에서 로그인 폴더 변수 없이 `claude auth login`·`codex login`을 띄운다. [로그아웃]은 확인 뒤 데몬이 `claude auth logout`·`codex logout`을 돌린다.
  - loom은 사람이 이 두 버튼을 누를 때만 CLI로 시스템 기본 폴더를 바꾼다. 처음에는 바꾸지 않고 셸 명령만 알렸다. Windows 사용자는 그 명령을 칠 터미널이 가깝지 않아, 기본 계정이 누구인지 모르고 잘못 연결된 기본 계정을 끊지 못했다(2026-10-21 사람 보고 "기본계정이 뭔지도 표시가 안되고 잘못된 연결 해제도 할 수 없음"). 목업 [accounts-system.html](../mockups/accounts-system.html).
  - CLI가 `PATH`에 없으면 그 공급자의 [계정 추가]를 끄고 시스템 기본 줄에 「설치 안 됨」을 보인다. 로그인·로그아웃 명령은 노드처럼 `PATH`에서 CLI를 찾고 npm 배치 파일(`codex.cmd`)은 그 프로그램을 바로 띄운다. 못 찾으면 노드 만들기와 같은 `LaunchError::NotInstalled`로 거절한다.
  - Codex 데스크톱 앱이 넣은 `%LOCALAPPDATA%\OpenAI\Codex\bin\<해시>\codex.exe`는 찾지 않는다. 해시 폴더는 앱을 업데이트할 때마다 바뀌고 공개 약속이 아니다. 사용자는 npm으로 Codex CLI를 설치한다(2026-10-21 사람 결정 「권장안대로」).
- 위치: 계정은 노드가 도는 위치(이 PC 또는 WSL 배포판)에 속한다. 위치는 저장소 경로가 정한다(「데몬 하나」). 위치 목록은 이 PC와, 더한 저장소가 있고 지금 도는 배포판이다(`wsl.exe -l --running`). 목록을 보려고 배포판을 켜지 않는다: 5분마다 읽는 사용량이 배포판을 끄지 못하게 한다. 위치가 하나면(Linux, macOS, WSL 저장소가 없는 Windows) 화면은 전과 같다. 위치가 둘 이상이면 설정 › 에이전트 계정은 위치마다 머리 줄로 묶는다(목업 [wsl-place.html](../mockups/wsl-place.html) ③, Q282 A).
  - 위치마다 「시스템 기본」(그 위치의 `~/.claude`·`~/.codex`)과 loom 계정이 따로 있다. WSL의 loom 계정은 그 배포판의 `~/.loom/accounts`다. 데몬은 UNC 경로(`\\wsl.localhost\…`)로 읽고 쓰고, CLI에는 Linux 경로를 넘긴다. 그 배포판의 Linux loom이 만든 계정도 그대로 보인다. [로그인]·[로그아웃]·[계정 추가]·사용량은 그 위치의 CLI로 돈다(`accounts::Site`).
  - 「사용 중」 계정은 위치마다 하나다(설정 `wslAccounts`, 이 PC는 옛 `claudeAccount`·`codexAccount`). 상태 줄은 고른 저장소 위치의 「사용 중」 계정을 보인다(⑦ A).
- loom이 만든 계정은 로그인 폴더 `~/.loom/accounts/<claude|codex>/<id>`를 쓴다. `id`는 만든 시각(밀리초)의 16진수 16자리라 이름 순서가 만든 순서다.
- 새 노드는 설정에서 고른 그 위치의 계정(위치·공급자마다 하나, 「쓰는 중」)으로 뜬다. 데몬이 `CLAUDE_CONFIG_DIR`·`CODEX_HOME`을 그 폴더로 넣는다. 시스템 기본이면 넣지 않는다. 고른 계정의 폴더가 없으면 시스템 기본으로 띄운다. 이미 도는 노드를 새 계정으로 옮기는 일은 「계정 전환」에 있다.
  - loom 계정 폴더로 Claude를 띄울 때 그 폴더 `.claude.json`에 `hasCompletedOnboarding: true`가 없으면 넣는다. Claude 2.1.228은 이 값이 없으면 로그인한 폴더에서도 첫 실행에 로그인 방법을 다시 묻는다. 2.1.305는 묻지 않는다(2026-10-21 Windows 실측, 사람 지시 "이전버전에도 대응 되도록 만들어"). 시스템 기본 폴더는 고치지 않는다.
  - loom 계정 폴더로 Claude를 띄울 때 사람의 `~/.claude/CLAUDE.md`가 있고 그 폴더에 `CLAUDE.md`가 없으면 한 줄 `@~/.claude/CLAUDE.md`를 쓴다. 계정 폴더에는 사용자 지시 파일이 없어, Claude는 `HOME` 아래 저장소에서 `~/.claude/CLAUDE.md`를 조상 폴더의 프로젝트 파일로 읽는다. 그 파일이 저장소 밖 파일을 가져오면(`@~/.agents/skills/AGENTS.md`) 저장소마다 「Allow external CLAUDE.md file imports?」를 묻는다. 사용자 지시 파일의 가져오기는 묻지 않는다(Claude 2.1.310 실측, 2026-10-25). 그래서 loom은 동의 값을 쓰지 않는다. 저장소 자기 `CLAUDE.md`의 가져오기는 그대로 묻고, 그 창은 받은편지함에 뜬다. 다른 글의 `CLAUDE.md`가 이미 있으면 두고 로그에 쓴다. 링크가 아닌 글 파일인 까닭: Windows 데몬은 WSL 계정 폴더를 UNC 경로로 쓴다. 그 자리의 Windows 링크는 Linux 링크가 아니고 권한이 든다.
  - 시스템 기본은 그 CLI가 `HOME` 아래에서 고르는 폴더다. 데몬은 시작할 때 자기를 띄운 터미널의 변수(로그인 폴더, 에이전트 세션 표지, `ORCA_*`, `LOOM_*`, Claude 설정이 넣은 `ANTHROPIC_BASE_URL`)를 지운다. 그래서 노드는 데몬을 띄운 곳과 관계없이 같은 환경으로 뜬다. API 키(`*_API_KEY`)는 남긴다. 목록은 [src/profile.rs](../../src/profile.rs)의 `is_launcher_env`에 있다.
- [계정 추가]: 데몬이 폴더를 만들고, 그 폴더로 `claude auth login`·`codex login`을 PTY에서 띄운다. 화면은 이 PTY를 노드 카드와 같은 터미널로 보인다. 그래프에는 나타나지 않는다.
  - 로그인 프로세스가 코드 0으로 끝나면 창이 닫힌다. 0이 아니면 실패를 보인다.
  - 새 계정은 로그인이 실패하거나 사용자가 창을 닫으면 폴더를 지운다. [다시 로그인]은 폴더를 지우지 않는다.
- Cursor는 사용량만 보인다(목업 [cursor-usage.html](../mockups/cursor-usage.html) M18 v2, 2026-10-23 사람 지시 "커서 계정도 사용량 표시에 보여줘", "orca를 참고하라", 승인 Q666 A). 계정은 그 위치의 Cursor CLI(`cursor-agent`) 로그인 하나다. loom은 Cursor 계정을 더하거나 바꾸지 않고 설정 › 계정에도 두지 않는다. 노드도 그 로그인으로 뜬다. 데몬 라우트는 `GET /api/usage/cursor`(위치마다 `CursorView`)이고 화면은 `/api/accounts`와 같은 때 읽는다. Cursor는 계정 기능의 `Provider`가 아니다.
  - 창은 Orca와 같다: 묶음 「Cursor Models」(Auto 등 Cursor 모델), 「Other Models」(이름을 고른 모델), 상한 있는 추가 사용량 「On-demand」, 그 뒤에 「플랜」(포함 사용량 전체). 묶음 이름은 Orca처럼 번역하지 않는다. 상태 줄은 묶음만 보이고 플랜은 팝오버에만 있다. 모든 창이 결제 주기 끝에 다시 차서 팝오버 아래 줄은 「11월 20일에 초기화」다. Cursor 줄에는 계정 목록 꺾쇠가 없다.
  - Orca와 다른 것: 머리 줄에 요금제 이름(「Enterprise」) 대신 이메일을 보인다. 공급자 순서는 고정이다. 둘 다 아래 「넣지 않은 Orca 기능」과 같은 결정이다.
- 사용량 읽기는 데몬의 캐시 하나를 지난다(`src/daemon/usage_cache.rs`). 화면 수와 새로 고침 수에 상관없이 키(위치, 출처, 계정)마다 공급자를 `MIN_AGE`(1분)보다 자주 부르지 않는다. 같은 키의 동시 요청은 한 번만 읽는다. 앞의 값은 읽은 시각(`Usage.readAt`)과 함께 보낸다. 상태 줄·팝오버·설정의 「N분 전 갱신」은 그 시각을 쓴다.
  - Claude가 429를 주면 `retry-after`(없으면 300초)가 끝날 때까지 그 키를 부르지 않고 마지막으로 읽은 값을 그대로 준다. 앞 값이 없으면 `UsageProblem::RateLimited { retryAt }`를 주고 화면은 「N분 뒤에 다시 읽습니다」를 보인다. 끝난 뒤 첫 요청이 다시 읽는다. 네트워크 오류·5xx·시간 초과도 `MIN_AGE` 동안 다시 부르지 않고 앞 값을 그대로 준다. 401·미로그인·미설치는 캐시하지 않고 앞 값도 버린다. 캐시는 그 계정 로그인 파일(`.credentials.json`, `auth.json`) 내용의 지문(해시, 데몬 밖으로 내지 않는다)을 함께 들고, 지문이 바뀌면(다른 계정 로그인, 로그아웃, 토큰 갱신) 앞 값과 기다림을 모두 버린다. 한도가 토큰마다 걸리기 때문이다. 자동 전환(`auto_switch`)도 같은 캐시를 쓴다. 전환 쿨다운(10분)은 그대로다.
  - 이유: 한도는 토큰마다 걸리고 화면마다 데몬을 부르면 호출이 화면 수만큼 곱해진다. Orca·Claude Code도 같은 토큰으로 부른다. 429를 받은 뒤 다시 부르면 막힘만 늘고, 화면이 값을 버리면 정상 값마저 사라진다(2026-10-23 사람 지시 "원인 규명해서 올바르게 해결해").
- OpenCode 2에는 계정과 사용량이 없다. 공급자가 여럿이고(OpenCode 설정의 `provider`), 공급자마다 나뉜 로그인 폴더가 없고, 남은 한도를 주는 출처가 없다. Orca도 OpenCode는 로컬 `opencode.db`에서 읽은 토큰·비용 통계 창만 보이고 계정을 바꾸지 않는다.
- 사용량 출처는 Orca와 같다.

| 공급자 | 계정 정보 | 사용량 |
|---|---|---|
| Claude | `claude auth status --json`(`loggedIn`, `authMethod`, `email`, `subscriptionType`, `configDirectory`) | 구독 로그인(`authMethod`가 `claude.ai`)의 OAuth 토큰(`claudeAiOauth.accessToken`)으로. 토큰은 macOS에서 키체인 항목, 그 밖에는 `<configDirectory>/.credentials.json`에서 읽는다. macOS도 키체인에 없으면 그 파일을 읽는다. 키체인 항목은 `security find-generic-password -s <서비스> -w`로 읽는다. 서비스는 `Claude Code-credentials`다. loom 계정(`CLAUDE_CONFIG_DIR`)이면 `-`와 `configDirectory` SHA-256의 앞 8자를 붙인다(Claude Code 2.1.310 실행 파일의 규칙). 토큰을 쓰거나 갱신하지 않는다. 그 토큰으로 `GET https://api.anthropic.com/api/oauth/usage`(`anthropic-beta: oauth-2025-04-20`, Orca와 같은 `User-Agent: claude-code/2.1.0`). `five_hour`·`seven_day`의 `utilization`(사용한 %)과 `resets_at`. 모델별 주간 창은 `limits` 가운데 `kind`가 `weekly_scoped`인 항목의 `scope.model.display_name`, `percent`, `resets_at` |

| Cursor | `~/.cursor/cli-config.json`의 `authInfo.email`. `cursor-agent`가 `PATH`에 없으면 「설치 안 됨」 | `~/.config/cursor/auth.json`의 `accessToken`(JWT)으로 `GET https://cursor.com/api/usage-summary`. 쿠키 `WorkosCursorSessionToken=<sub>::<jwt>`(URL 이스케이프)와 `Origin`·`Referer: https://cursor.com`을 보낸다. `individualUsage.plan`의 `autoPercentUsed`·`apiPercentUsed`·`totalPercentUsed`(`enabled`가 거짓이면 모두 뺀다), `onDemand`(`enabled`이고 `used/limit`이 있을 때), `billingCycleEnd` |

- 상태 줄의 사용량은 Orca처럼 버튼 하나다. 누르면 팝오버 하나에 모든 공급자의 5시간·주간·모델별 창을 보인다. 공급자 줄을 누르면 그 공급자의 계정 목록이 펼쳐지고, 계정을 눌러 쓰는 계정을 바꾼다.
- 화면은 사용한 비율만 보인다. Orca 기본 표시와 같다. 막대도 사용한 양만큼 차고, 75% 이상이면 노란색이다.
- 창마다 남은 리필 시간을 그 줄 오른쪽에 보인다(2026-10-20 사람 지시 "남은 리필시간도 표시해줘 orca처럼"). 꼴은 Orca와 같다: 「47분 남음」「3시간 12분 남음」「4일 3시간 남음」. 1분이 안 되면 「곧」이다. 1분마다 다시 그린다. 정확한 초기화 시각은 아래 「창 초기화 (월) 15:40」 줄이 계속 보인다. 남은 시간은 `Intl.NumberFormat`의 좁은 단위(`unitDisplay: 'narrow'`)로 써서 언어마다 「분」·「m」으로 달라진다.
- 새로 고침은 팝오버 머리의 아이콘 하나다. 모든 공급자를 한 번에 다시 읽는다(Orca 상태 줄의 ↻와 같다).
- 사용량은 화면이 읽을 때마다 데몬이 그 자리에서 읽는다(`GET /api/accounts`). 화면은 5분마다, 사용량 팝오버를 열 때, [새로 고침]을 누를 때 읽는다. 데몬은 저장하지 않는다.
- 읽는 상한은 계정마다 15초다. 넘거나 실패하면 그 계정만 오류 한 줄을 보인다.
- 한계: API 키·토큰 로그인(`authMethod`가 `claude.ai`가 아님, Codex `rateLimits`가 `null`)은 사용량을 볼 수 없다(「API 키·토큰 로그인은 사용량을 볼 수 없습니다.」). 구독 로그인인데 토큰을 찾지 못하면 「loom이 Claude 로그인 토큰을 찾지 못했습니다.」다. macOS Cursor CLI는 토큰을 키체인에 두고 loom은 그것을 읽지 않아 「loom이 Cursor 로그인 토큰을 찾지 못했습니다.」다. 캐시 지문은 키체인 토큰을 보지 않는다. 그래서 macOS에서 다른 계정으로 로그인하거나 토큰이 갱신돼도 앞 값과 기다림이 남는다(`MIN_AGE`, 429는 `retry-after`까지). Cursor 토큰이 만료되면(`exp`가 지났거나 401) 「이 계정으로 Cursor를 한 번 실행하면 갱신됩니다」다. Claude 토큰이 만료돼 401이면 「이 계정으로 Claude를 한 번 실행하면 갱신됩니다」를 보인다. loom은 토큰을 갱신하지 않는다. 갱신은 로그인 폴더를 고치는 일이다.
- 넣지 않은 Orca 기능: Codex 한도 초기화 크레딧, 추가 사용량, 상태 줄 표시 방식(간단·자세히, 사용·남음) 바꾸기 스위치, 상태 줄 항목 고르기, 사용량 기록 화면, 요금제 이름, 많이 쓴 공급자부터 줄 세우기, Cursor 옛 요청 수 요금제(`/api/usage`)의 창, Cursor IDE 로그인 읽기.

## 계정 전환

목업 [account-switch.html](../mockups/account-switch.html) v2(2026-10-21 사람 승인). 코드는 [src/daemon/switch.rs](../../src/daemon/switch.rs)에 있다. 노드를 옮기는 일은 「다시 띄우기」다.

- 노드는 띄운 계정을 그래프에 남긴다(`nodes.account`, 시스템 기본은 NULL). Claude 노드는 세션 기록 파일 경로도 남긴다(`nodes.transcript`). `loom hook`이 훅 입력의 `transcript_path`를 이미 부르는 요청(`take`, `idle`)에 실어 보낸다. 따로 요청하지 않는다. 이 기능 전에 뜬 노드도 새 `loom`으로 바꾼 뒤 다음 훅에서 남긴다. 세션 id는 그 파일 이름이다.
- `GET /api/accounts/{provider}/nodes?to=<계정 id>`는 옮길 노드를 준다. 그 공급자의 실행 중인 노드 가운데 `to`와 다른 계정으로 띄운 노드다. `to`가 없으면 시스템 기본이다. 화면은 설정을 저장하기 전에 확인 창 목록을 읽는다. `busy`는 턴 중이라는 뜻이다(「다시 띄우기」).
- `POST /api/accounts/{provider}/move`는 그 노드를 모두 설정의 계정으로 옮긴다. 화면이 설정을 먼저 저장한다. 결과(`moved`, `later`, `failed`)를 이벤트 기록 `accountSwitched` 한 줄로도 남긴다. `from`은 옮길 노드가 가장 많이 쓰던 계정이다. 같은 수면 번호가 작은 노드의 계정이다.
- 옮기기는 노드를 새 계정으로 다시 띄우는 일이다(「다시 띄우기」). 노드 번호, 이름, 카드, 부모와 자식, 메일함은 그대로다. 토큰은 새로 받는다. 옛 프로세스의 남은 훅이 노드 대신 데몬을 부르지 못하게 하기 위해서다.
  1. 세션 기록을 새 로그인 폴더의 같은 상대 경로로 복사한다. Claude는 `projects/<작업 폴더>/<세션>.jsonl`과 곁 폴더 `<세션>/`이다. Codex는 `thread/read`가 준 `sessions/<년>/<월>/<일>/rollout-…-<스레드>.jsonl`이다. 복사하지 않으면 CLI가 「세션 없음」으로 실패한다(2.1.306, 0.159.2 실측). 로그인 파일은 복사하지 않는다. 세션 안의 `/login`도 쓰지 않는다.
  2. Claude는 옛 폴더에서 사람이 받아들인 확인을 새 폴더로 옮긴다: 작업 폴더 신뢰(`.claude.json`의 `hasTrustDialogAccepted`)와 모든 권한 허용 경고(`settings.json`의 `skipDangerousModePermissionPrompt`). 옮기지 않으면 새 폴더가 두 확인 창을 다시 보여, 사람 없는 노드가 멈춘다(2.1.306 실측). 옛 폴더에 없는 값은 옮기지 않는다. 시스템 기본으로 옮길 때는 옮기지 않는다. 시스템 기본 파일은 고치지 않는다.
  3. 새 노드 명령을 준비한다. 모델과 추론 강도는 노드의 지금 값이다. Claude는 `claude --resume <세션>`이다. Codex는 새 `CODEX_HOME`으로 새 app-server를 띄우고, 데몬이 그 서버에서 스레드를 먼저 연다(`thread/resume`). TUI는 `codex resume <스레드> --remote <주소>`다. TUI에는 권한 인자를 넘기지 않는다. 넘기면 「Permission overrides are not supported when resuming a remote task」로 끝난다. 그 대신 데몬이 `thread/resume`에 처음 권한을 넣는다(모든 권한 허용 노드는 `danger-full-access`·`never`, 아니면 `workspace-write`·`on-request`). 넣지 않으면 신뢰하지 않은 폴더에서 `read-only`로 이었다(0.159.2 실측).
  4. 옛 프로세스를 끝내고 끝나기를 기다린 뒤 새 프로세스를 띄운다. 옛 프로세스의 종료는 노드를 `exited`로 두지 않는다. 옛 PTY 호스트가 끝나며 지우는 주소 파일을 새 호스트가 같은 이름으로 쓰므로 순서를 지킨다.
- 남긴 세션이 없는 노드(이 기능 전에 뜬 노드가 아직 훅을 부르지 않았다, 기록 파일이 없다, Codex 스레드 전)는 옮기지 않는다(`failed`). 옛 계정으로 계속 돈다. 새로 띄우면 사람이 친 대화와 첫 지시를 잃는다. 그래프는 첫 지시의 첫 줄만 남긴다.
- 준비가 실패한 노드는 옛 계정으로 계속 돈다(`failed`). 한 노드의 실패는 다른 노드를 막지 않는다.
- 턴 중인 노드는 턴이 끝나면 옮긴다(`later`). 데몬이 다시 시작하면 그 노드는 옛 계정에 남고, 확인 창 목록에 다시 나온다.
- 한도 멈춤: Claude는 API 오류로 끝난 턴에 `Stop` 대신 `StopFailure` 훅을 부른다. loom은 이 훅을 쉬는 대기 훅으로도 건다. 그래야 한도로 멈춘 노드도 메시지에 깬다(2.1.306 실측: `asyncRewake` 훅이 `StopFailure`에서도 모델을 깨운다). 값이 `rate_limit`이면 `loom hook`이 쉬는 대기 요청(`idle`)에 실어 알린다. Codex는 app-server의 `error` 알림(`codexErrorInfo: usageLimitExceeded`, `willRetry` 아님)이다. 한도로 멈춘 노드는 옮긴 뒤 「Your account was switched after a usage limit. Continue the task where you stopped.」를 첫 입력으로 받는다.
- 자동 전환(설정 `autoSwitch`, 처음 값은 꺼짐): 노드가 한도로 멈춘 이벤트(위 「한도 멈춤」)로만 시작한다. 사용량을 주기로 읽거나 비율 기준으로 미리 바꾸지 않는다.
  - 대상: 그 시점에 그 노드와 같은 위치, 같은 공급자의 다른 계정 사용량을 읽는다(계정마다 15초 상한). 손으로 하는 전환도 그 위치의 노드만 옮긴다(`?distro=`). 읽은 계정 가운데 가장 많이 쓴 창의 비율이 가장 낮고 100% 미만이어야 한다. 읽지 못한 계정은 건너뛴다.
  - 대상을 설정의 계정으로 저장하고, 확인 창 없이 모든 노드를 옮긴다. 이벤트 기록의 `why`는 `rateLimit`이다.
  - 대상이 없으면 바꾸지 않는다. `noAccountLeft`에 계정들의 가장 빠른 창 초기화 시각을 남긴다.
  - 같은 공급자는 10분 안에 다시 자동 전환하지 않는다. `noAccountLeft`도 이 간격에 한 번만 남긴다. 같은 계정의 노드 여럿이 한꺼번에 한도로 멈추면 멈춤마다 다시 바꾸어 계정을 오가는 일을 막는다. 그사이 멈춘 노드는 이미 바꾼 계정으로 옮긴다(턴이 끝나면 옮길 노드).
  - 수치는 `switch.rs`의 이름 있는 상수에 있다.

## 다시 띄우기

코드는 [src/daemon/relaunch.rs](../../src/daemon/relaunch.rs)에 있다. 노드의 에이전트 프로세스를 끝내고 지금 loom 설정(실행 인자·훅·계정)으로 다시 띄워 같은 세션을 잇는다. 사람 요청(Q357 답 A): "A 하고 에이전트도 사용할 수 있는 도구로 만들어". 옛 `--settings`(동기 `Stop` 훅)로 뜬 노드가 턴 끝마다 「Stop hook error」를 보이고 쉬는 동안 메시지에 깨지 않았다.

- 부르는 곳: 노드 메뉴(`POST /api/nodes/{id}/relaunch`. 메뉴를 열 때 `GET`으로 턴 끝을 기다리는지 묻고, 기다리면 「턴이 끝나면 다시 띄웁니다」로 꺼 둔다), 에이전트 `loom relaunch [<자식>] [--agent <id>]`(`/api/agent/relaunch`. 이름이 없으면 부른 노드 자신, 있으면 자기 자식만), 계정 전환.
- 프로필이 있는 노드(Claude, Codex, Cursor, OpenCode 2, Pi, OMP)만 된다(2026-10-22 사람 지시 "다 구현해"). 셸·명령 노드는 `noResume`으로 거절한다. 이을 세션이 없고, 다시 띄우면 셸 상태를 잃는다.
- 프로세스가 끝난 노드(`exited`·`setupFailed`, 완료 뒤 끝난 노드도)는 남긴 세션으로 되살린다. 번호·이름·부모·자식은 그대로이고, `exited`·`setupFailed`는 `running`으로, 완료는 그대로 둔다. 결과는 늘 `now`다. 첫 입력은 끝난 동안 보낸 메시지를 받지 못했다는 알림이다(`Refusal::Ended`로 거절됐다). 완료 뒤 끝난 노드는 잠든 노드다(「잠든 노드」). 그동안 온 메시지가 남아 있어 첫 입력은 그 메시지가 이어 온다는 알림이다. 사람 지시(2026-10-23) "총괄 resume 시켜": 총괄이 코드 1로 끝나 자식 9개의 부모가 끝난 채 남았고, 끝난 노드를 잇는 길이 없었다. 지금은 API(`POST /api/nodes/{id}/relaunch`)와 `loom relaunch <자식>`만 부른다. 노드 메뉴는 아직 끝난 노드에 다시 띄우기를 보이지 않는다(화면 변경은 목업 승인 뒤).
- 잇는 세션: Claude는 `--resume <세션>`, Pi는 `--session <기록 파일>`, OMP는 `--resume <기록 파일>`, Cursor는 `--resume <세션>`(훅 입력 `transcript_path`의 파일 이름, `nodes.transcript`), Codex는 `resume <스레드>`, OpenCode 2는 새 `opencode2 serve`가 같은 세션 id를 열고 TUI가 `--session`으로 붙는다(세션은 서버가 아니라 OpenCode 저장소에 남는다). 세션이 아직 없으면(첫 입력 전) 실패로 남긴다.
- 결과는 `now`(쉬던 노드, 새 프로세스가 떴다)나 `atTurnEnd`(턴 중, 그 턴이 끝나면 띄운다)다. 실행 중인 도구 호출을 끊지 않는다. 턴 끝 질문 검사가 다시 일하게 한 턴은 끝이 아니다.
- 턴 중: Claude·Cursor는 턴 안의 훅(`take`)이나 쉬는 대기가 메시지를 넘긴 뒤 턴 끝 훅(`idle`)이 아직 오지 않았을 때, Codex는 스레드가 일하는 중일 때, OpenCode 2는 `session.execution.started` 뒤 `succeeded`·`failed`·`interrupted`가 오기 전이다. Claude는 쉬는 대기가 없고 세션 기록의 마지막 대화 줄이 턴 끝(`claude::turn_ended`)이 아닐 때도 턴 중이다. 턴 중 표시는 기억에만 있어, 데몬이 다시 시작하면 훅 없이 생각하는 턴은 다음 훅까지 쉬는 노드로 보였다. 쉬는 대기가 넘긴 메시지로 시작한 턴도 같았다: `loom relaunch`가 그 턴을 바로 끊었고, 받은 것으로 남은 메시지는 사라졌다(2026-10-25 워커 관찰병목 #930, 메시지 #7118). 턴 끝을 기다리는 Claude 노드의 화면에 도는 턴이 없으면 지금 다시 띄운다(`release_stopped_turns`). 도는 턴의 표시는 입력칸 위의 진행 줄(`· Coalescing… (10s · ↓ 246 tokens)`처럼 기호, 공백, `…`로 끝나는 낱말)이나 입력칸 아래 줄의 `esc to interrupt`다(2.1.310 실측: 폭 50칸에서는 아래 줄에서 `esc to interrupt`가 빠지고 진행 줄만 남았다. Esc 뒤에는 둘 다 없다). 그 화면이 5초(`STOPPED_SETTLE`) 넘게 두 번 보이고, 그사이 훅도 기록 변화도 없고, `restart_guard`(입력칸이 비고 사람이 치지 않음)를 지킬 때만 띄운다. Esc로 멈춘 턴에는 Stop 훅이 오지 않아, 이것 없이는 다시 띄우기와 그 메일이 끝없이 기다렸다(2026-10-25 검토 지적). 시간만으로 정하면 오래 도는 도구(설정한 `BASH_MAX_TIMEOUT_MS`, MCP 도구)를 끊었다(같은 날 검토자 재현). 쉬는 대기가 없다는 것만으로 턴 중이라 보지 않는다. 데몬이 다시 시작하면 옛 설정의 노드는 쉬어도 대기를 열지 않아 영원히 턴 중으로 보였다(2026-10-22 실측). 턴 끝을 기다리는 목록은 기억에만 둔다.
- 다시 띄울 노드(턴 끝을 기다리거나 다시 띄우는 중)에는 메시지를 넘기지 않고 턴 끝 질문 검사도 하지 않는다. 새 프로세스가 받는다. 턴 끝에 옛 프로세스가 받은 메시지로 새 턴을 열면 다시 띄우기가 그 턴을 끊었다(2026-10-22 실측, Codex 「Conversation interrupted」).
- Codex는 옛 app-server가 끝난 뒤 새 서버에서 스레드를 연다. 계정이 같으면 옛 서버가 스레드를 쥐어 `thread/resume`이 "already has an active writer"로 실패했다(0.159.2 실측).
- Claude는 옛 프로세스가 끝난 뒤 그 노드의 위치와 계정에서 `claude agents --json`을 읽는다. 전체 세션 id가 같은 백그라운드 작업이 있을 때만 그 id로 `claude stop`을 부르고 새 CLI를 띄운다. 맞는 작업이 없거나 목록을 읽지 못하면 아무것도 끝내지 않는다. 짧은 id(UUID의 앞 8글자)만 넘기면 앞 글자가 같은 사람의 세션을 끝낼 수 있다(2026-10-23 검토자 지적). Claude Code의 백그라운드 세션은 노드 프로세스 나무 밖(Claude 자기 데몬)에 살아 PTY 호스트를 끝내도 남는다. 남으면 `--resume`이 「That session is running in the background」로 거절하고 코드 1로 끝났다(2026-10-23 실측, 2.1.308: 사람 노드에서 REPL `/background`가 세션을 같은 id로 옮겼다). 2.1.309의 `/background`는 새 id로 갈라 옛 id를 막지 않지만, `claude --bg --resume <세션>`은 같은 id를 쥔다. 시험 데몬에서 이 상태를 만들어 수정 전에는 코드 1, 수정 뒤에는 같은 세션을 이었다(2.1.309). PTY 호스트를 끝내는 것만으로는 백그라운드 세션이 생기지 않았다. `claude stop`은 전체 UUID를 받지 않는다(「No job matching」).
- Cursor·Pi·OMP는 다시 띄운 세션에 짧은 첫 입력(`profile::RESUMED_PROMPT`)을 넣는다. 쉬는 Cursor에는 stop 훅만 메시지를 넘기므로, 입력 없이 이으면 사람이 칠 때까지 메시지가 쌓였다(실측).
- 옛 프로세스가 띄운 셸(노드 프로세스와 그 서버 아래의 세션 리더)은 함께 끝낸다. Cursor는 노드 프로세스가 끝나도 그 명령이 고아로 남았다(실측). 끝낸 명령이 있으면 모든 프로필의 첫 입력에 그 명령 줄과 「필요하면 다시 띄우라」는 한 줄을 넣는다. 명령 줄은 셸의 첫 자식 프로세스(없으면 셸 자신)의 인자이고 200자에서 자른다. 명령 줄이 `loom hook`으로 끝나는 셸은 쉬는 대기 훅이라 세지 않는다. 예전에는 `loom` 프로세스를 도는 셸을 모두 빼서, 멈춘 `loom spawn`도 알리지 않았다. Claude도 넣는다. Claude Code 2.1.310은 끝난 백그라운드 명령을 세션 기록에만 적고 턴을 열지 않았다(2026-10-25 코디 #724·#944: 멈춘 `loom spawn`이 다시 띄우기로 끝난 뒤 두 노드가 1시간 넘게 쉬었다). 2026-10-22에 「Claude Code가 스스로 알린다」고 본 것은 틀렸다. 끊긴 턴을 이으라는 첫 입력은 넣지 않는다. 이 판의 loom은 도는 Claude 턴을 끊지 않고(「턴 중」), 화면으로 풀린 다시 띄우기는 사람이 Esc로 멈춘 세션이라 그 일을 잇게 하면 사람의 멈춤을 되돌린다(2026-10-25 코디 결정). 기록의 나이로 끊긴 턴을 가리던 규칙은 오래된 Esc 세션에도 「이어 하라」를 넣어 지웠다.
- 옛 프로세스를 끝내도 그 PTY는 같은 노드의 새 프로세스가 받을 때까지 둔다(`NodeHost::stop`). 화면은 그동안 마지막 출력을 보고, 새 PTY가 오면 다시 붙는다. 옛 PTY를 먼저 놓자 그 틈에 다시 붙은 화면이 「터미널이 닫혔다」(`PtyNotice::Gone`)를 받고 다시 붙지 않았다. 사람은 그 노드를 「죽음」으로 보고 한 번 더 다시 띄웠다(2026-10-24 워커 사용량429, 이벤트 10918·10938. 같은 배포가 그 노드에 `rules-changed`를 두 번 보냈다는 보고는 틀렸다: 알림은 한 번이었다).
- 시작 글이 바뀐 노드: 데몬은 띄울 때 노드가 받은 시작 글 조각마다 SHA-256을 `nodes.rules`에 둔다(`profile::start_digests`). 조각은 사용법(`COMMUNICATION_USAGE`와 그 프로필의 대기 방식, 이름 `usage/<프로필>`)과 늘 넣는 스킬 글(이름은 원본 경로, 예: `o-mode/agent-rules.md`)이다. 데몬이 시작할 때 이 판의 글과 견주어(`profile::changed_parts`) 바뀐 조각을 받은 산 노드만 다음 턴 끝에 한 번 다시 띄운다(`relaunch_stale`). 다시 띄우면 새 해시가 남아 같은 판에서 두 번 뜨지 않는다. 완료 자식도 다시 띄운다. 재우기 전에 일을 받으면 그 일을 옛 글로 하기 때문이다(관문 검토 2026-10-24). 다시 띄우기를 기다리는 노드는 재우지 않는다. 실측(2026-10-24 시험 데몬): `usage/cursor` 해시를 바꾼 Cursor 노드가 데몬 시작 뒤 턴 끝에 한 번 다시 떠 같은 세션을 이었고, 데몬을 한 번 더 다시 시작해도 다시 뜨지 않았다(토큰 그대로). 해시가 없는 노드(셸, 이 기능 전에 뜬 노드)는 다시 띄우지 않는다. 다시 시작한 데몬은 누가 턴 중인지 모르므로 쉬는 노드도 턴 끝 신호를 기다린다: Claude·Cursor는 다시 붙는 쉬는 대기, Codex·OpenCode 2는 서버의 쉼이다. 턴 끝을 기다리는 노드의 프로세스가 끝나면 그 다시 띄우기를 지운다(`Relaunches::process_ended`). 끝난 노드에는 턴 끝이 오지 않고, 그 항목이 메일을 묶고 `loom relaunch`를 막았다(2026-10-25 pi 노드 #880·#881: 「Relaunched.」라 답하고 아무것도 띄우지 않았다). 그래서 끝난 노드는 턴 끝에 걸지 않고, 끝난 노드의 `loom relaunch`는 남은 턴 끝 항목을 무시하고 바로 띄우거나 실패 이유를 돌려준다. 근거: 시작 글은 띄울 때 한 번만 넘어가서, 바뀌어도 뜬 노드는 옛 글을 쥔다(2026-10-23 Q687 A). 배포마다 모든 노드에 `rules-changed`를 보내자 노드가 그 턴과 다시 뜬 턴, 두 턴을 썼고 기록 3,000건 안에서 27번 다시 떴다(2026-10-24 총괄 결정 A).
- 다시 띄우는 일은 부른 쪽 요청과 따로 끝까지 한다. 노드 자신이 부른 `loom relaunch`는 턴 중이라 응답이 먼저 가고, 턴 끝 훅이 띄운다.
- 결과는 이벤트 기록 `relaunched`(노드, 실패면 `error`) 한 줄로 남는다. 턴 끝에 다시 띄우다 실패하면 사람은 이 줄로 본다. 계정 전환이 옮긴 노드도 노드마다 남는다.
- 노드 번호, 이름, 카드, 부모와 자식, 메일함은 그대로다. 아직 확인하지 않은 메시지는 새 프로세스의 시작 훅이 넘긴다. 순서와 세션 기록 복사는 「계정 전환」의 1~4다. 계정이 같으면 복사하지 않는다.
- 신호의 대기(승인 창)는 새 토큰을 남기는 트랜잭션에서 지운다. 새 PTY를 띄운 뒤에 지우면 그 사이 옛 승인이 새 PTY에 쳤다(2026-10-23 리뷰 「다시 띄운 뒤 옛 승인」).
- 열린 `loom ask` 질문은 남는다. 같은 세션 잇기, 계정 전환, `--agent` 바꾸기가 모두 같다. 답은 메일함 메시지로 가고 메일함은 다시 띄워도 남는다. 근거: 2026-10-24 총괄이 Q757을 물은 뒤 규칙 변경으로 `loom relaunch`를 불렀다. 그 질문이 답 없이 닫혀(`unanswered`, `restart`) 받은편지함에서 사라졌고, 통과한 브랜치 둘이 7시간 기다렸다. 옛 기록의 `restart`는 이 판 전의 기록이다. 프로세스가 끝나면(`exited`, 재우기 포함) 질문을 닫는다(`exit`).
- 다른 에이전트로 바꾸기(`loom relaunch [<자식>] --agent <id> [--model] [--effort]`, 또는 `POST /api/nodes/{id}/relaunch`의 몸통 `{"agent", "model", "effort"}`): 같은 노드를 그 에이전트의 새 세션으로 띄운다. 2026-10-23 사람 지시 "해당 구현 진행": Claude 주간 한도로 총괄이 노드 12개를 손으로 Cursor로 옮겼다(`loom rm`, 새 루트, 이름 바꾸기, `loom adopt`). 새 노드에는 역할이 없어 관문이 코디를 보지 못했고, 번호·메일함·열린 질문·카드를 잃었다.
  - 세션은 에이전트 사이를 옮기지 못한다. 첫 입력(`relaunch.rs` `handoff`)은 옛 에이전트, 역할, 옛 세션 기록 경로(Claude·Cursor는 `nodes.transcript`, Codex는 살아 있는 app-server가 아는 기록 파일)와 「그 첫 사용자 메시지가 첫 지시」를 알리고 `git status`와 워크트리를 본 뒤 일을 이으라고 한다. 첫 지시는 따로 남기지 않는다(2026-10-23 총괄 결정). 기록 경로를 모르면(OpenCode 2, 끝난 Codex 노드) 부모에게 지시를 물으라고 한다.
  - 남는 것: 번호, 이름, 부모와 자식, 역할(`nodes.role`, 데몬은 이 이름을 보지 않는다), 자리, 메일함, 열린 `loom ask` 질문(답은 메시지로 새 에이전트가 받는다), 카드. 바뀌는 것: 에이전트, 모델·강도, 토큰, 서버·계정. 옛 세션 기록 경로는 지운다. 그 이름으로 새 에이전트의 세션을 이으면 안 된다.
  - 모델·강도는 `loom spawn --role`과 같다. 준 값이 이기고, 빈 칸은 노드 역할의 에이전트가 새 에이전트와 같을 때만 역할의 값이다. 메시지 연동이 없는 에이전트(`noLink`)와 받지 않는 모델·강도는 부를 때 바로 거절한다. 턴 끝을 기다리지 않는다.
  - 차례는 같은 세션 잇기와 같다: 턴 끝을 기다리고, 새 노드를 먼저 준비하고(실패하면 옛 프로세스가 그대로 돈다), 옛 프로세스와 셸을 끝낸다. 옛 Claude 세션이 Claude 자기 데몬에 남았으면 옛 프로세스를 끝내기 전에 끝낸다. 노드 밖에서 같은 워크트리를 계속 고치기 때문이다. 찾은 작업을 `claude stop`이 끝내지 못하면 바꾸기가 실패하고 옛 프로세스가 그대로 돈다. 다시 띄우기가 실패하면 옛 프로세스가 다시 메시지를 받는다: 턴 끝에 멈춘 쉬는 대기가 다시 기다리고, 서버 전달 작업이 메일함을 다시 본다. 멈춘 채 두면 사람이 입력할 때까지 노드가 메시지를 받지 못했다(2026-10-23 검토자 재현). 새 세션은 같은 세션 잇기의 `--resume` 거절처럼 남은 세션을 알아채지 못한다(2026-10-23 검토자 지적). 끝난 노드도 바꿔 띄운다.
  - 턴 끝을 기다리는 노드에 에이전트 바꾸기가 오면 기다리던 일을 바꾼다. 같은 세션 잇기(계정 전환)는 기다리던 바꾸기를 지우지 않는다. 다시 뜨는 중인 노드(끝난 노드를 되살리는 중도)의 바꾸기는 `relaunching`으로 거절한다. 조용히 버리면 부른 쪽이 에이전트가 바뀌었다고 믿는다.
  - 지금과 같은 에이전트도 받는다. 그 에이전트의 새 세션이 노드를 이어받는다. 맥락이 너무 길어진 세션을 새로 시작할 때 쓴다.
  - 이벤트 기록 `relaunched`에 `switched`(옛·새 에이전트)를 남긴다. 화면(노드 메뉴)은 아직 바꾸지 않았다(화면 변경은 목업 승인 뒤).
- 실측(2026-10-22, 시험 데몬, Codex 0.159.2, cursor-agent 2026.10.19, OpenCode 2.0.32): 네 에이전트 모두 쉴 때와 턴 중에 다시 띄운 뒤 다시 띄우기 전에 들은 낱말을 답했고, 그동안 보낸 큐 메시지를 받았다. 턴 중이면 `atTurnEnd`였고 턴이 끝난 뒤 새 프로세스가 떴다.
- 실측(2026-10-22, 시험 데몬, Claude 2.1.308 haiku): 동기 `Stop` 훅으로 뜬 노드를 다시 띄우니 새 프로세스가 `--resume <같은 세션>`과 `asyncRewake` `Stop` 훅으로 떴다. 다시 띄우기 전에 들은 낱말을 답했고, 그 전에 보낸 큐 메시지를 받았다. 노드 안의 `loom relaunch`는 바로 끝났고 턴이 끝난 뒤 새 프로세스가 떴다.

## 잠든 노드

코드는 [src/daemon/sleep.rs](../../src/daemon/sleep.rs)에 있다. 완료한 뒤 쉬는 자식 노드의 에이전트 프로세스를 끝내 메모리를 돌려받는다. 노드는 그래프에 `done`으로 남는다. 카드도 완료로 보인다. 2026-10-24 사람 승인: 노드 프로세스의 메모리와 토큰 낭비를 줄인다.

- 재우는 노드: 부모가 있고, `done`이고, 사람 응답 대기가 없고, 이을 세션이 있고, 쉬는 노드다(Claude·Cursor는 세션 기록과 쉬는 대기, Codex는 스레드와 쉼). 부모 없는 노드는 재우지 않는다. 사람이 그 터미널에 직접 치고, 끝난 프로세스에 친 키는 사라진다.
- OpenCode 2 노드는 재우지 않는다. 시험 데몬에서 깨운 노드가 메시지를 받고 `done`을 불렀는데, loom이 넣지 않은 턴이 하나 더 돌아 사람 입력으로 보였다. 노드는 `running`으로 돌아가 카드가 완료로 남지 않았다(2026-10-24, 이벤트 69).
- 실측(2026-10-24, 시험 데몬, `DONE_GRACE`를 20초로 줄인 빌드, cursor-agent 2026.10.22, Codex 0.159.2): Cursor·Codex 완료 자식이 재운 뒤 프로세스가 0개였고 카드는 완료였다. 메시지를 보내자 약 12초 안에 같은 세션으로 깨어 띄우기 전에 들은 낱말로 답했다. Cursor는 터미널 키 하나에 0.1초 만에 깼고, 열린 화면은 닫힌 뒤 새 PTY에 다시 붙었다(「터미널이 닫혔다」 없음). 데몬을 다시 시작한 뒤에도 메시지가 잠든 노드를 깨웠다.
- 시간: `DONE_GRACE`(10분) 동안 계속 쉬면 재운다. 한 번이라도 쉬지 않으면 다시 잰다. 근거: 사람 DB에서 완료 뒤 다시 일한 476번 가운데 90%가 10분 안에 왔다(중앙값 75초). 352번은 다시 일하지 않았다(2026-10-24 실측).
- 재우기: 메시지를 꺼내지 않게 막고, 노드를 다시 본다. 이미 열린 쉬는 대기도 같은 막음을 거쳐 꺼낸다(`App::next_mail`). 막음과 꺼냄은 한 잠금 안에 있다(`Sleeps::unless_stopping`). 그 사이 다시 일하면 재우지 않는다. 옛 Claude 백그라운드 세션을 끝낸 뒤 한 번 더 본다. 그 정리를 기다리는 동안 사람이 입력할 수 있기 때문이다. 노드가 띄운 셸, 쉬는 대기를 끝내고 프로세스를 끝낸다. PTY는 남아 화면이 마지막 출력을 본다(`NodeHost::stop`). 프로세스가 끝나면 데몬이 그 화면을 파일로 남긴다(「남긴 화면」). `EXIT_WAIT`(10초) 안에 프로세스가 끝나지 않으면 재우기를 멈추고 막음을 푼다.
- 잠든 표시: 데몬이 재우는 중에 끝난 프로세스만 `nodes.asleep`에 표시한다(`Graph::slept`). 그 노드는 `exited`가 아니라 `done`으로 남고 부모에게 알리지 않는다. 부모의 `loom done`은 회수하지 않은 잠든 자식이 있으면 거절한다(메시징.md 「노드 제거와 입양」). 다른 까닭으로 끝난 완료 노드(사람이 끝냈다, 호스트를 잃었다)는 잠든 노드가 아니다. 그 노드의 카드는 완료로 남지만 메시지를 받지 않고(`graph::REACHABLE`이 아니다) 깨우지 않는다. 근거: 호스트를 잃은 노드의 프로세스는 남았을 수 있다. 깨우면 한 워크트리에 프로세스가 둘이 된다(관문 검토 2026-10-24).
- 메시지: 잠든 노드는 산 노드처럼 메시지를 받는다(`graph::REACHABLE`). 이름으로 찾을 때와 관문을 고를 때도 같다. 깨우는 메시지(`MessageKind::wakes`)가 오면 데몬이 같은 세션으로 깨운다. 길은 끝난 노드 되살리기와 같다(「다시 띄우기」). 첫 입력은 잠든 동안 프로세스를 끝냈다는 알림이고, 남은 메시지가 뒤따른다. 알림(끝남·지움·데려감)은 깨우지 않고 다음 메시지와 함께 간다.
- 사람: 노드 메뉴의 다시 띄우기, 그리고 그 터미널에 누른 키가 깨운다. 키 자체는 끝난 프로세스에 가서 사라진다. 노드가 다시 뜨면 화면이 새 PTY에 붙는다.
- 깨우지 못하면(세션이 없다, 띄우기 실패) 노드는 코드 없는 `exited`가 되고 부모가 알림을 받는다(`Graph::sleep_lost`). 그 뒤로는 메시지를 받지 않는다. 메시지·키로 깨울 때도, 노드 메뉴로 깨울 때도 같다. 새 토큰을 남겨 잠든 표시가 지워진 뒤 띄우기가 실패해도 같다. 그래서 `sleep_lost`는 표시가 아니라 「완료이고 프로세스가 없다」를 본다(관문 검토 2026-10-24, 3차).
- 데몬이 다시 시작해도 잠든 노드는 DB에 그대로다. 그 동안 온 메시지는 시작한 데몬이 깨운다. PTY는 앞 데몬의 기억에만 있다. 그래서 메시지를 받는 노드(`Graph::reachable`)에 PTY가 없으면 데몬은 PTY 없는 터미널 연결을 열어 둔다(`coming_pty`). 남긴 화면이 있으면 그 연결에 먼저 보낸다. 잠든 노드면 그 연결에 누른 키가 깨운다. PTY가 생기거나 노드가 메시지를 받지 않게 되면(띄우기 실패, 끝남) 데몬이 연결을 닫고, 화면이 다시 열어 새 PTY에 붙거나 「터미널이 닫혔다」를 받는다. 잠든 표시는 새 PTY가 생기기 전에 지워지므로 기준으로 쓰지 않는다. 근거: 「터미널이 닫혔다」를 받은 화면은 다시 열지 않아, 키로 깨울 수 없고 깨운 노드도 따라가지 못했다. 잠든 표시만 본 첫 고침은 새 호스트가 5초 늦게 뜨자 같은 길에 빠졌다(관문 검토 2026-10-24, 1·2차).
- 남긴 화면: 재우는 중에 끝난 프로세스(`Graph::slept`)의 PTY 크기와 backlog를 데몬이 `pty/nodes.screens/<노드 번호>`에 쓴다(`NodeHost::keep`). backlog는 산 PTY와 같다: 마지막 256 KiB와, 잘린 앞부분에서 켠 화면·마우스 모드다. 임시 파일에 쓰고 이름을 바꾼다. 사람 DB에는 두지 않는다. `coming_pty`는 산 PTY에 붙을 때와 같은 차례로 보낸다: 크기(`PtyNotice::Size`), `Settled`, backlog 한 프레임. 그래서 화면은 바뀌지 않는다. 새 PTY가 붙거나(`NodeHost::resume`) 노드를 지우면(`NodeHost::kill`) 파일을 지운다. 데몬을 끌 때는 쓰지 않는다. 잠든 노드는 모두 프로세스가 끝날 때 썼다. 근거: 데몬을 다시 시작하자 잠든 노드의 터미널이 비었다(2026-10-25 사람 보고, 폰 앱 #802(워커 메시지방향-파이)). 총괄 결정 Q6266 A. 실측(2026-10-25, 시험 데몬, `DONE_GRACE`를 5초로 줄이고 셸 자식도 재우는 빌드): 300 KB를 찍은 셸 자식을 재우자 파일이 262156바이트(크기 4, 모드 `?1049h` 8, backlog 262144)였다. 데몬을 다시 시작한 뒤 그 터미널 연결이 크기, `settled`, 262152바이트 프레임을 받았다. 키 하나가 깨우기를 불렀고, 노드를 지우자 파일이 사라졌다.

## 설정

- 탭은 주제마다 하나다: 일반(워크스페이스 폴더, 시스템 알림), 휴대폰(「원격」의 짝짓기와 연결된 기기, 2026-10-22 사람 지시 "핸드폰 연결은 설정에 별도 탭을 만들것"), 에이전트, 에이전트 계정, 화면(테마, 색, 언어), 그래프(카드 보기, 그래프 범위, 간선 모양, 질문 알약), 터미널, 정보. 설정을 열면 「일반」이다. 목업 [settings-groups.html](../mockups/settings-groups.html)(2026-10-22 사람 지시 "설정은 관련있는것끼리 다시 구성을 정리해줘", 승인 "권장안대로", "계정 > 에이전트 계정"). 칸 하나뿐인 탭(워크스페이스, 원격)은 합치고, 세 주제가 섞인 「UI」는 나눴다.
- 설정은 `settings` 테이블 한 줄(JSON)이다: 모든 권한 허용을 끈 에이전트 목록, 공급자마다 쓰는 계정, 화면 테마, 터미널 테마·글꼴, 카드 보기, 그래프 범위, 간선 모양, 화면 언어, 화면 색, 워크스페이스 폴더, 노드 나무 상한(「상한」), 시스템 알림(「사람 응답 대기」), 내장 스킬 스위치(「내장 스킬」), o-mode 역할. 저장한 JSON에 없는 값은 기본값으로 읽는다.
- 초기화: 기본값을 바꾼 칸마다 [기본값], 탭 머리에 [이 탭 초기화], 탭 목록 아래에 [모든 설정 초기화]가 있다. 화면은 칸에 `null`을 보내고 데몬이 칸을 지워 기본값으로 읽는다. 기본값은 Rust에만 있고 화면은 `GET /api/settings/default`로 견준다. 고른 계정은 초기화하지 않는다(바꾸면 노드가 계정을 바꾼다). 근거: 2026-10-22 사람 지시 "모든 설정 초기화도 넣고, 각 탭별 초기화를 넣어라", "모든 설정에 초기화 버튼을 추가해".
- 찾기(목업 [settings-search.html](../mockups/settings-search.html) M34, 2026-10-22 사람 승인 Q269 A "설정 찾기 검색 기능 추가"): 탭 목록 위 칸에 글을 치면 모든 탭의 칸(`section`) 가운데 글이 맞는 칸만 한 줄로 보인다. 칸 이름 앞에 탭 이름, 맞은 글에 밑색(CSS Custom Highlight)을 둔다. 화면이 그린 글을 그대로 보므로 언어를 바꿔도 맞는다. Esc는 창을 닫지 않고 글만 지운다. 탭을 누르면 검색을 끝내고 그 탭으로 간다. 머리 줄(제목, [이 탭 초기화], [×])은 스크롤해도 위에 남는다(사람 지시 "설정 x 닫기 버튼은 스크롤 영향 안받고 항상 우상단에")
- o-mode 역할(목업 [role-settings.html](../mockups/role-settings.html) M12, 2026-10-23 사람 승인 Q510 A, 지시 "설정에서 o-mode 역할 crud (역할에 대한 책임 설정도 가능하게), 각 역할에 모델, 에이전트 환경, 추론강도 설정할 수 있게 해줘"): 「에이전트」 탭에서 역할을 더하고 고치고 지운다. 한 역할은 이름, 책임, 에이전트, 모델, 추론 강도다(설정 `roles`, 코드 [src/roles.rs](../../src/roles.rs)). 역할 표의 원천은 이 설정 하나다. `skills/o-mode`에는 표가 없다.
  - 역할은 프리셋일 뿐이다(2026-10-24 사람 결정 Q851 A). 데몬은 역할 이름으로 아무것도 정하지 않는다. 관문·검토·부모 없는 노드의 규칙은 구조로 정한다(「병합 관문」). 그래서 사람은 기본 역할을 포함해 모든 역할을 어느 언어로든 더하고, 지우고, 이름을 바꾼다. 역할을 지운 노드는 `nodes.role`에 옛 이름 글을 지닌다. 에이전트는 `loom roles`의 책임을 보고 역할을 고른다.
  - 기본값은 옛 o-mode 표(총괄, 코디, 워커, 검토자, 보조 검토자)에 「고위험 워커」를 더한 표다. CI 담당자는 없앴다(Q692 A). DB 40단계가 옛 거절 코드 `leadSpawnsOnlyCoordinator`를 새 코드로 바꾼다. 지시문 앞에 `Role: <이름> - <책임>`을 붙인다. 뜬 노드는 뒤에 설정이 바뀌어도 그대로다.

  - 고른 색은 `<style id="ui-colors">`의 `:root, [data-scheme]` 규칙으로 테마별 토큰을 얹는다. 고르지 않은 테마는 styles.css 기본값 그대로다. 브라우저가 사용자 정의 속성 안의 `light-dark()`를 선언한 요소에서 정하므로, 한 테마의 색을 보일 견본은 `data-scheme`을 달아 토큰을 다시 선언받는다.
  - 값 칸은 두 테마 색이 같으면 한 값, 다르면 「라이트 #… 다크 #…」를 보인다. 줄의 [기본값]은 두 테마를 함께 되돌린다.
  - 색 칸을 누르면 작은 창이 뜬다: 맨 위 라이트·다크 칸(그 테마의 색과 대비), 추천 색 8개, 색 값 입력, [직접 고르기](브라우저 색 창), [기본값]. 테마 칸을 고르지 않으면 두 테마에 같은 색을 쓴다. 칸을 누르면 그 테마만 바꾼다(그 칸에 테두리, 다른 칸은 흐림). 흐린 칸을 누르면 그 테마로 바뀌고, 테두리 칸을 다시 누르면 두 테마로 돌아간다. 창은 두 테마 색이 같으면 두 테마로, 다르면 지금 화면의 테마로 열린다. 창의 [기본값]은 고른 테마(없으면 두 테마)를 되돌린다. 고르면 바로 저장하고 모든 창이 같은 색을 보인다.

## 화면 언어

화면 문구는 영어와 한국어다. 명세는 [language.html](../mockups/language.html)이다(2026-10-19 사람 지시 "i18n 적용 (영어, 한국어)").

| 결정 | 정한 것 | 이유 |
|---|---|---|
| 자리와 값 | 「화면」 탭의 「테마」·「색」 아래 「언어」 드롭다운. 「시스템」「English」「한국어」. 처음 값은 「시스템」 | Orca도 Appearance의 Theme 아래에 Language(`uiLanguage`)를 둔다. 목록 첫 줄이 System이다 |
| 「시스템」 | 브라우저 언어가 `ko`로 시작하면 한국어, 아니면 영어 | Orca와 같은 규칙이다 |
| 언어 이름 | 「English」「한국어」는 화면 언어와 관계없이 그 언어로 쓴다 | Orca와 같다 |
| 라이브러리 | `i18next` + `react-i18next` | Orca와 같다. 언어를 바꾸면 `useTranslation`을 쓰는 부품만 다시 그린다 |
| 문구 자리 | `web/src/locales/en.ts`가 키의 원천이다. `ko.ts`는 그 타입을 받는다 | 키 오타와 두 파일의 키 차이를 `tsc`가 잡는다 |
| 첫 그리기 | 데몬이 첫 페이지 `<html>`에 `data-language`를 넣는다 | 테마와 같은 방식이다. 설정을 받기 전에 다른 언어가 잠깐 보이지 않는다 |
| 데몬 문구 | 화면 경로는 문장 대신 코드와 값(`Problem`, `UsageProblem`, `PtyNotice`, `VersionMismatch`)을 보낸다. 화면이 번역한다 | 타입은 Rust에만 둔다. Rust에 코드를 더하고 번역을 빠뜨리면 `tsc`가 실패한다 |
| 에이전트가 읽는 글 | CLI 출력, 노드 메시지, 훅 출력, `/api/agent/*` 오류는 한국어 그대로다 | 이번 범위가 아니다. 같은 거절(`Refusal`, `LaunchError`)을 에이전트에게는 `Display` 문장으로 보낸다 |
| 날짜·시간 | 상대 시간과 요일·시각은 `web/src/i18n.ts`의 `Intl` 포매터가 화면 언어로 쓴다. 언어가 바뀌면 포매터를 다시 만든다 | 직접 만든 포매터를 지웠다. 브라우저가 언어별 형식을 안다 |
| 이미 보인 오류 | 오류 문장은 실패한 때의 언어로 만든다. 언어를 바꿔도 이미 보인 오류 문장은 바뀌지 않는다 | 오류는 다음 시도나 창을 닫으면 사라진다. 코드를 들고 다니며 다시 번역할 만큼 오래 남지 않는다 |
| 원인 글 | OS·app-server 오류 글은 번역하지 않고 값으로 붙인다. `src/codex_server.rs`의 원인 글은 영어다 | 시스템이 낸 글이라 loom이 번역할 수 없다 |
| 재발 방지 | `npm run check`가 `web/scripts/no-hangul.mjs`를 돌린다. `src`의 문자열·JSX 글자에 한글이 있으면 실패한다(`locales/`, `gen/` 제외) | 새 문구가 번역 파일을 거치게 한다 |

## 화면 문구

`web/src/locales/`의 모든 문구는 아래 규칙을 따른다. 출처는 [Apple HIG Writing](https://developer.apple.com/design/human-interface-guidelines/writing)과 Apple 한국어 UI, 그다음 [Toss UX 라이팅 원칙](https://toss.tech/article/8-writing-principles-of-toss)이다. 둘이 다르면 Apple을 따른다(2026-10-20 사람 지시 "안내 문구들을 ui/ux 가이드에 맞게", "애플을 우선순위 더 높게").

- 말투: 문장은 합니다체로 끝낸다. 할 일을 시킬 때는 "-하십시오"를 쓴다. Apple 한국어 UI와 같다.
- 라벨·상태·버튼: 문장으로 쓰지 않고 명사로 끝낸다. 예: 「설치 안 됨」「사용 중」「불러오는 중…」.
- 버튼: 결과를 말하는 짧은 동작 이름이다. 예: 「만들기」「다시 찾기」「삭제」. 입력을 더 받는 메뉴는 끝에 「…」를 붙인다.
- 오류: 무엇이 안 됐는지와 할 일을 한 문장씩 쓴다. 사람을 탓하지 않고 감탄사·"우리"를 쓰지 않는다.
- 빈 상태: 비어 있다는 사실과 다음 동작을 쓴다. 로딩은 「…하는 중…」이다.
- 도움말: 켜면 무엇이 되는지만 쓴다. 끄면 반대라고 짐작할 수 있으면 쓰지 않는다. 화면이 이미 보이는 것은 설명하지 않는다.
- 화면 요소 이름은 작은따옴표로 감싼다: ‘새 노드’, 영어는 “New node”. 메뉴 경로는 「›」로 잇는다. 줄임표는 한 글자 「…」다.
- 영어: 모든 요소가 sentence case다. 짧은 능동문으로 쓰고 "please"를 쓰지 않는다.
- 안쪽 말 금지: 데몬·PTY·PATH·app-server·DB·파일 시스템 같은 구현 낱말을 쓰지 않는다. 사람이 아는 말(loom, 에이전트, 노드, 터미널, 폴더)로 쓴다(2026-10-20 사람 지시 "이런구문을 쓰면 사용자는 이해 못한다").
