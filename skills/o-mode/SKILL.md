# Loom 병렬 개발

## 실행 경계

- 이 파일, [브리프 공통 규칙](agent-rules.md)과 [참고](reference.md)가 실행 절차의 원천이다. 참고의 절차는 그 일을 할 때 그 파일을 읽고 따른다. 다른 오케스트레이션 스킬을 상속하지 않는다.
- loom은 이 파일을 부모 없는 노드(사람이 띄운 노드)의 시작 지시에, [브리프 공통 규칙](agent-rules.md)을 자식의 시작 지시에 늘 넣는다. 부모 없는 노드가 총괄이다. 자식은 브리프가 정한 역할을 유지한다.
- Loom 환경과 다른 터미널 환경 변수가 함께 있어도 Loom으로 배정·통신·감독한다.
- Orca CLI·앱·오케스트레이션 스킬·보조 스크립트를 실행 경로로 쓰지 않는다. Loom 기능이 없다고 그 도구로 우회하지 않는다.
- 다른 제품 벤치마킹 요청은 비교 조사다. 제공된 자료와 로컬 소스를 먼저 읽고, 그 제품의 앱·CLI는 사용자가 명시할 때만 조작한다.

## 시작

1. `LOOM_TOKEN`과 `LOOM_URL`의 존재를 확인한다. 토큰 값은 출력하지 않는다. 없으면 노드 생성·통신을 하지 않고 직접 할 수 있는 조사부터 한다.
2. 설치된 `loom`이 쓸 기능·모델 옵션을 지원하는지 [참고 「설치 판」](reference.md#설치-판)으로 확인한다.
3. `loom status`로 현재 관계와 생존 여부를 확인한다. 중첩 깊이 상한 안에서 직접 작업·직속 워커·코디 구성을 고른다.
4. 저장소 AGENTS.md와 작업 관련 문서를 읽는다. 새 워크트리의 설정 절차와 완료 확인 방법을 브리프에 적는다. `--worktree` 자식은 설정 스크립트가 성공한 뒤 같은 카드에서 뜬다.

## 역할과 배정

기본 역할은 총괄, 코디, 워커, 검토자, CI 담당자다. 사용자가 역할을 더하고 고치고 지울 수 있다. 각 역할의 책임과 에이전트·모델·강도는 loom 설정(설정 › 에이전트 › o-mode 역할)에 있다. `loom roles`로 본다.

- 자식은 `loom spawn <이름> --role <역할>`로 띄운다. 따로 준 `--agent`·`--model`·`--effort`가 설정보다 우선한다. 사용자가 직접 고른 실행자·모델은 둘 모두보다 우선한다.
- 검토자 모델은 정확도·가격·시간으로 고른다. 저장 형식, 인증, 동시성, 데이터 손실 경로와 여러 모듈의 계약 변경에 워커를 띄우면 Opus 워커로 띄운다. 이 조건만으로 워커를 띄우지 않는다(2026-10-23 사람 "네가 작업안하고 워커 부른이유"). 이런 브랜치에는 설정의 검토자와 함께 Claude `claude-opus-5-5` medium 검토자를 하나 더 띄운다(2026-10-23 실측: 두 모델이 놓친 결함이 겹치지 않아 함께 심은 결함 8/8을 찾았다, Q540).
- 크기로 맡긴다(Q522 A): 한두 줄은 총괄이 직접, 범위 하나인 작은 일은 워커 1명, 목업·여러 범위·고위험은 코디 1명. 총괄은 관문의 merged·failed 알림만 받는다. 결과 파일은 읽지 않는다.
- 사실을 가진 노드가 브리프를 쓰고 워커를 띄운다(예: CI 담당자가 찾은 불안정한 시험). 그 노드가 검토·병합·회수까지 맡는다. 총괄 브리프에는 목표(완료 조건 포함)와 범위만 적는다. 남의 사실을 옮겨 적지 않는다.
- 총괄은 상주하며 작업 컨텍스트(진행 중인 일, 자식, 결정, 승인 대기)를 관리한다. 코드 수정·화면 검증·조사는 브리프로 맡긴다.
- 코디는 강하게 결합된 작은 작업을 직접 한다. 독립된 편집 범위가 둘 이상일 때만 나눈다. 코디의 편집 범위가 하나면 워커를 `--worktree` 없이 코디 워크트리에 띄운다. 새 워크트리는 설정·빌드·병합·회수만 더한다. 워커가 도는 동안 코디는 그 워크트리를 편집·빌드하지 않고 읽기와 검수만 한다. 코디는 같은 제품 결정을 기다리는 조각을 함께 맡는다.
- 이름은 사용자의 언어로 짓는다. 브랜치·워크트리는 그 안에서 하는 작업(예: `알림표시통일`), 노드는 `<역할> <작업>`(예: `코디 알림표시통일`, `워커 완료링크`)이다. 총괄은 `<저장소> 총괄`, CI 담당자는 `CI 담당자 <저장소>`다. 노드 이름은 유일하게 짓는다. 주소는 이름, 노드 번호, `parent`를 쓴다.
- 브리프는 `~/.cache/loom-briefs/<작업>-<역할>.md`에 둔다. 코디와 사실을 가진 노드가 쓰는 브리프에는 아래를 적는다. 목표, 확인된 사실, 가설, 편집 범위, 보존할 계약, 완료 조건, 검사 명령, 시간 예산이다.
- 브리프에 공통 규칙 경로를 적지 않는다. 자식은 시작 지시로 그 규칙을 받는다. 브리프와 에이전트 메시지는 영어로 쓴다.

## Loom 명령

| 목적 | 명령·동작 |
|---|---|
| 편집할 자식 생성 | `loom spawn <이름> --role <역할> --worktree <브랜치> --file <지시 파일>` |
| 같은 워크트리에서 읽기 전용 조사 | `--worktree` 없이 `loom spawn` |
| 긴 브리프 전달 | 지시 파일에 `Read <브리프 절대 경로> and follow it.`을 적는다. 지시문은 4,096바이트 이하다 |
| 막힘·질문 | `loom ask <질문>`(부모에게 간다). 총괄에게는 진행 보고를 보내지 않는다 |
| 받은 질문에 답 | `loom answer <메시지 번호> <본문>` |
| 알림 | `loom note <대상> <본문>` |
| 방향 수정 | `loom note <자식> <본문> --steer` |
| 작업 중단 | `loom note <자식> "Stop. …" --interrupt` |
| 완료 보고 | `loom done <요약>` 또는 `loom done --file <결과 경로>` |
| 인계·조치 전파·재배정 | [참고 「명령」](reference.md#명령) |

`--worktree`는 부모 워크트리의 `HEAD`에서 갈라진다. 총괄은 기준 체크아웃에서, 코디는 자기 브랜치에서 자식을 만든다. 같은 워크트리에 편집자를 여럿 두지 않는다.

`--worktree` 자식의 설정이 실패하면 [참고 「명령」](reference.md#명령)을 따른다.

## 목업 승인

- 사람에게 보이는 목업·보고서의 형식, 스타일, 보이기는 [user-doc](../user-doc/SKILL.md)이 정한다. 아래는 loom 역할만 정한다.
- 화면 작업은 설치된 디자인 점검 스킬(예: `design-stack`)이 있으면 그것으로 점검한다. 코디가 목업을 만든다.
- 코디는 렌더 점검 뒤 경로·판·점검 결과만 보고한다. 총괄 한 명이 user-doc `show.sh`로 점검하고 `loom ask "<질문>" --doc <파일>`로 질문에 붙인다. 사람의 브라우저는 아무도 직접 열지 않는다. 브리프에 코디의 브라우저 열기를 지시하지 않는다.
- 머리 줄의 `응답할 곳`은 총괄이다. 사람은 그 노드의 대화에 승인이나 수정을 전한다.
- 사용자 승인 전에는 화면 제품 코드를 쓰거나 구현 워커를 띄우지 않는다. 승인할 판과 남은 결정을 구체적으로 제시한다.
- 사용자의 승인 판·경로·내용을 구현 브리프에 적는다. 승인 대기 중인 노드와 워크트리는 유지한다.

## 사용자 보고서

- HTML 보고서는 사람이 명시해 요청할 때만 만든다. 절차는 [참고 「사용자 보고서」](reference.md#사용자-보고서)에 있다. 그 밖의 결과는 터미널에 항목마다 문제·원인·해결 세 줄로 알리고, 할 일이 뻔하면 바로 진행한다.

## 감독과 검수

- 완료·종료·제거·인계 알림을 받는다. 주기적인 순찰 프로세스는 만들지 않는다.
- 시간 예산을 넘기면 `loom note <자식> "Report status and blockers." --steer`로 확인한다. 응답이 없으면 `loom status`로 생존을 확인한다.
- 중단이 필요하면 `loom note <자식> <본문> --interrupt`로 현재 결과·실패 원인·남은 일을 보고하게 한다. 기존 편집자가 멈췄는지 확인한 뒤 재배정한다.
- 같은 완료 명령이 두 번 실패하거나 환경 문제로 10분 넘게 막히면 [참고 「막힘」](reference.md#막힘)을 따른다.
- 검수자는 diff, 완료 조건, 검사 출력과 실제 관찰 결과를 대조한다. 실패한 검사를 약화하거나 완료 조건을 줄여 통과시키지 않는다.
- 증거가 없거나 실패했거나 검증 뒤 관련 코드가 바뀌었을 때 검사를 다시 한다. 지금 고칠 수 있는 문제는 반려해 고친다.

## 질문·응답과 대기

- 질문·답·대기는 [참고 「질문·응답과 대기」](reference.md#질문응답과-대기)를 따른다.

## 병합과 회수

- 병합은 관문 동사로만 한다: `loom ready`, `loom verdict`, `loom merge`, `loom fail`. 받는 곳·순서·필요한 값은 `loom --help`와 거절 글이 알린다. 메시지 머리의 `kind:`가 관문 단계를 알린다. 종류 낱말(READY, MERGED, QUESTION 등)로 `loom note`·`loom done`을 시작하지 않는다. loom이 거절하고 맞는 동사를 알린다.
- 브랜치 담당(코디, 또는 코디 없는 워커)은 커밋한 뒤 대상 브랜치(main, 코디 밑 워커는 코디 브랜치)를 자기 브랜치에 병합하고 검사를 다시 돌린다. 충돌은 여기서 고친다. 그 뒤 `loom ready <브랜치>`를 부른다.
- 관문(CI 담당자, 코디 밑 워커는 코디)은 검토자를 띄운다. 검토자는 diff와 브리프의 완료 조건을 확인하고 결함 파일을 쓴 뒤 `loom verdict`를 부른다. 코디는 자기 브랜치를 `loom ready` 하기 전에 워커 결과를 검수해 합친다.
- main 반영은 CI 담당자가 `loom merge`로만 한다. 손으로 main에 병합·push하지 않는다. 다음 `loom merge`가 관문 밖 커밋을 찾아 루트에 알린다.
- 저장소에 `scripts/gate/check.sh`가 없어도 `loom ready <브랜치>`를 부른다. 관문은 `kind: ready` 메시지를 받고, 손으로 병합한 뒤 `loom done`으로 알린다.
- 회수는 그 노드의 현재 부모가 한다. 총괄은 코디와 자기가 띄운 워커를, 코디는 워커를, CI 담당자는 띄운 검토자·워커를 회수한다. 대상은 자식 노드, 띄운 셸 노드, 워크트리와 브랜치, 시험 데몬 같은 백그라운드 프로세스, 임시 폴더다.
- 자식의 결과를 받거나 병합한 직후마다 회수 대상을 확인한다. 결과를 보존했고 더 쓸 계획이 없으면 바로 회수한다. 사용자 확인이나 작업 전체의 끝을 기다리지 않는다. 절차는 [참고 「회수」](reference.md#회수)를 따른다.
- 완료 보고에는 결과, 검증 근거, 반영 위치와 남은 일을 적는다. `랩터-3:` 줄에 삭제·재사용·새 부품의 이유를 적는다.
