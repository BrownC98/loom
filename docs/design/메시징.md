# 메시징

## 원칙

- PTY 입력은 사용자만 쓴다. loom은 PTY에 글자를 쓰지 않는다. 그래서 사용자가 입력하는 중에도 메시지가 그 글과 섞이지 않는다.
- 메시지는 모두 디스크 큐에 쓴다. 상태는 `queued`, 넘김, 출력, `delivered`(읽음) 넷이다. 아래 전달 지점이 본문을 꺼내면 넘김이다. 받는 쪽이 에이전트에게 본문을 쓰고 받음을 확인하면 출력이다. 같은 프로세스의 다음 에이전트 사건이 오면 읽음이다(「전달 확정」).
- 큐 메시지(`note`·`answer`)는 살아 있는 어느 두 노드 사이에도 오간다. 나무·워크트리·저장소가 달라도 된다(2026-10-21 사람 지시 "loom에서 모든 터미널은 다른 모든 터미널에 메시지를 보낼 수 있도록 해"). 에이전트는 먼저 부모·자식과 주고받고, 보고는 부모에게 한다.
- 조정·중단(`note --steer`·`note --interrupt`)은 지금처럼 부모와 자식 사이에만 오간다. 다른 에이전트의 턴에 끼어들기 때문이다. 다른 노드에 보내면 `NotRelated`로 거절한다. 조정만 같은 브랜치의 검토자끼리도 간다(「병합 관문」 검토 공유).
- 받는 쪽은 이름, 노드 번호(`12`·`#12`), `parent`(부르는 노드의 부모)다. 숫자만인 이름, `#`으로 시작하는 이름, `parent`는 노드 이름으로 쓰지 못한다(`Refusal::ReservedName`). 근거: 에이전트가 `#96` 대신 `96`(14번), 부모 이름 대신 `parent`·`#parent`(5번)로 보내 거절됐다(2026-10-20~22 이벤트 기록). 부모 없는 노드가 `parent`로 보낸 큐 메시지는 보관한다.
- 이름으로 받는 노드 찾기: 먼저 부모·자식에서 찾는다. 없으면 그래프 전체에서 프로세스가 사는 노드 가운데 그 이름이 하나뿐일 때 그 노드다. 둘 이상이면 후보를 `#<번호> <이름> (<저장소 폴더>/<워크트리 폴더>)`로 적어 거절한다. 그 이름의 노드가 모두 끝났으면 `Ended`로 거절한다. 자기 자신에게는 보내지 못한다.
- 부모·자식이 아닌 두 노드 사이 메시지도 이벤트 기록(보냄·전달)에 남는다. 둘 사이에는 간선이 없으므로 화면은 3초 동안 두 카드의 위 변을 잇고 위로 휘는 점선 곡선을 그린다. 모양·시간·층·라벨(「n 메시지 → 받는 노드」)은 간선 강조와 같다. 3초 안에 서로 보내면 한 곡선에 두 라벨을 잇고 흐르지 않는다(2026-10-21 사람 승인, 목업 [docs/mockups/any-message.html](../mockups/any-message.html) v1 A).
- 사람이 띄운 노드 이름은 데몬이 `<에이전트 id>-<번호>`로 짓는다(`claude-1`, 셸은 `shell-1`). 번호는 부모 없는 노드 사이에서 겹치지 않는 가장 작은 수다.
- 자식 이름은 형제·부모·조부모 이름과 겹칠 수 없다. 입양도 새 관계의 양쪽에서 충돌을 검사한다.
- 사람은 화면에서 노드 이름을 바꾼다(이름을 더블클릭하거나 F2). 새 이름은 부모·조부모·형제·자식·손자 이름과 겹칠 수 없다. 부모 없는 노드는 서로 형제다.
- 이름을 바꾸면 부모와 자식 메일함에 `renamed: <옛 이름> -> <새 이름> (#<번호>)` 한 줄을 넣는다. 옛 이름으로 보내면 받는 노드를 찾지 못하기 때문이다.
- `note`는 이름 대신 `'#<노드 번호>'`를 받는다. 큐 `note`의 번호는 그래프의 어느 노드든 된다. `#`로 시작하는 이름은 예약한다.
- 옛 데이터에서 부모·자식 가운데 이름이 둘 이상 맞아도 후보와 함께 거절한다. 번호를 지정한다.
- 작업 완료와 프로세스 종료는 다르다. `done`인 노드도 피드백을 받는다. 프로세스가 종료하면 새 메시지를 거절한다.
- 데몬은 재시작 뒤 살아 있는 완료 노드에도 다시 붙는다. 완료 요약은 그대로 남긴다.

## 명령

| 명령 | 누가 부르나 | 뜻 |
|---|---|---|
| `loom spawn <이름> [--worktree <브랜치>] (--role <역할> \| -- <명령>)`, `loom spawn --role <역할> --review <브랜치>` | 에이전트 | 자식 노드를 만든다. `--worktree`는 내 워크트리의 HEAD에서 새 워크트리를 만들고 그 안에 띄운다. 지시문은 stdin이나 `--file`로 받는다(머리 검사와 작업 폴더는 「작업 폴더」). `--role`은 설정의 o-mode 역할로 띄운다(「설정」). `--review`는 이름을 받지 않고 `--worktree`와 함께 받지 않는다. 이름은 `<역할> <브랜치>`다(「병합 관문」). `<명령>`은 ssh처럼 낱말을 빈칸으로 이어 셸이 해석한다 |
| `loom roles` | 에이전트 | 설정의 o-mode 역할을 한 줄씩 출력한다: 이름, 에이전트·모델·강도, 책임 |
| `loom roles set <역할> --agent <id> [--model <m>] [--effort <e>]` | 부모 없는 노드 | 역할 하나의 에이전트·모델·강도를 바꾸고 바뀐 표를 출력한다. 이름·책임은 그대로다. 빼먹은 `--model`·`--effort`는 CLI 기본이 된다. 부모가 있으면 `Refusal::RolesHaveParent`, 없는 역할·카탈로그에 없는 에이전트·받지 않는 모델 조합은 거절한다. 성공하면 화면이 설정 변경을 바로 본다(`ViewChanged`) |
| `loom note <이름, 번호 또는 parent> <본문> [--steer\|--interrupt]` | 에이전트 | `note` 종류로 보낸다. 큐는 턴을 끊지 않고 어느 노드에나 간다. `--steer`(조정: 다음 도구 호출 사이에 넣는다)와 `--interrupt`(중단: 지금 동작을 멈추고 바로 따르게 한다)는 부모·자식에게만 간다. `--steer`는 같은 브랜치의 다른 검토자에게도 간다. 보낸 메시지 번호를 출력한다 |
| `loom answer <메시지 번호> <본문>` | 에이전트 | 내가 받은 `ask`에 답한다. 다른 종류의 메시지 번호는 거절한다(`NotAsk`). 원래 메시지 번호를 함께 저장한다 |
| `loom status` | 에이전트 | 내 번호, 현재 부모·자식, 작업 상태와 프로세스 생존 여부를 JSON으로 출력한다 |
| `loom status --all` | 에이전트 | 그래프의 모든 노드를 번호, 이름, 부모, 자리(`<저장소 폴더>/<워크트리 폴더>`), 작업 상태, 프로세스 생존 여부로 JSON 출력한다. 다른 나무의 노드 번호를 찾는다 |
| `loom wait [--reply-to <메시지 번호>] [--timeout <초>] [--json]` | 에이전트 | 일반 메시지나 지정한 `ask`의 첫 `answer`를 기다린다. 메시지 종류도 출력한다 |
| `loom done <요약>` / `loom done --file <경로> [<요약>]` | 에이전트 | 결과를 `done` 종류로 부모에게 보내고 노드를 `done`으로 바꾼다. `--file`의 경로는 `file` 칸에 들고, 요약이 없으면 경로가 요약이다. 관문이 자신인 브랜치 담당이 병합하지 않은 브랜치를 `loom ready` 없이 끝내면 `warning` 칸을 더하고 출력한다. 거절하지는 않는다. 이미 `done`이어도 거절하지 않고 새 요약을 다시 보낸다(다시 깨기 전의 둘째 보고를 거절해 결과가 부모에게 가지 않았다. 2026-10-22 기록에서 거절 23번). 부모가 없는 노드는 아래 「완료 알림」의 꼴을 쓴다 |
| `loom ask <질문>` | 에이전트 | 부모가 없는 노드: 사람에게 고르기·승인을 한 줄로 묻는다. 받은편지함에 뜨고 바로 끝난다. 에이전트는 턴을 끝내고, 사람은 노드 터미널에 답한다. 부모가 있는 노드: `ask` 종류로 부모에게 보내고 메시지 번호를 출력한다(`--doc`은 거절). 선택지 꼴은 두 쪽이 같다 |
| `loom answered [Q12 …]` | 에이전트 | 사람의 입력이 열린 `loom ask` 질문의 답이라고 판단하면 부른다. 준 번호의 질문만 받은편지함에서 지운다. 번호가 없으면 열린 질문이 하나일 때만 그것을 지운다 |
| `loom relaunch [<자식>] [--agent <id> [--model <m>] [--effort <e>]]` | 에이전트 | 자기(이름이 없을 때)나 자기 자식의 에이전트 프로세스를 지금 설정으로 다시 띄우고 같은 대화를 잇는다. `--agent`면 그 에이전트의 새 세션이 노드를 이어받는다. 턴 중이면 그 턴이 끝난 뒤 띄운다(「다시 띄우기」) |
| `loom adopt <이름>` | 에이전트 | 부르는 노드가 그 노드의 새 부모가 된다. 이름은 그래프 전체에서 찾는다. 같은 이름이 둘 이상이면 거절한다 |
| `loom detach <이름>` | 에이전트 | 그 노드의 부모를 비워 다시 뿌리로 만든다. 이름은 입양과 같이 그래프 전체에서 찾는다. 이미 뿌리이거나 같은 이름의 뿌리가 있으면 거절한다. 이후 그 노드의 `loom ask`는 사람 받은편지함으로 간다 |
| `loom ready <브랜치>` | 브랜치 담당 | 병합 관문: 브랜치를 관문에 보낸다(아래 「병합 관문」). 대상을 담지 않아도 받는다. 관문 스크립트가 없는 저장소에서도 `ready` 종류로 관문에 보낸다 |
| `loom verdict <브랜치> pass\|block [--findings <파일>]` | 관문이 `loom spawn --role <역할> --review <브랜치>`로 띄운 검토자. 부모 브랜치에서 만든 브랜치는 그 부모 | 병합 관문: 판정을 넣는다. block은 결함 파일이 있어야 하고 담당에게 반려로 간다. pass는 병합 큐에 세운다. 기본 결함 파일은 「작업 폴더」에 있다 |
| `loom fail <브랜치> <원인>` | 관문 | 병합 관문: 큐의 묶음에 들기 전의 브랜치를 멈추고 담당에게 원인을 알린다(대상이 원래 체크아웃이면 루트도) |
| `loom hook` | Claude 훅 | stdin의 훅 이벤트를 받아 전달할 메시지를 돌려준다 |
| `loom guard` | Claude PreToolUse 훅 | 훅이 포그라운드 Bash 명령 앞에 이 줄을 붙인다. 부른 셸을 중단 대상으로 데몬에 알린다 |
| `loom serve` | 사람 | 데몬과 화면을 띄운다 |
| `loom open` | 사람, 바탕 화면 아이콘 | 데몬이 없으면 띄우고 화면을 기본 브라우저로 연다(「[배포](배포.md#배포)」) |
| `loom stop` | 사람 | 데몬만 끝낸다(`POST /api/shutdown`). 노드는 산다 |

- 프로필이 없는 노드에 `steer`나 `interrupt`를 보내면 오류를 내고 보내지 않는다. 큐로 바꿔 보내지 않는다.
- 답변은 내가 받은 `ask`의 보낸 노드에게 간다. 다른 노드가 받은 질문에 답하거나 남이 보낸 질문을 기다릴 수 없다.
- 옛 동사 `send`·`reply`·`steer`·`interrupt`는 지웠다. CLI가 모르는 명령으로 거절한다(2026-10-23 Q687 A).
- 요청별 대기는 다른 메시지를 꺼내지 않는다. 훅이 먼저 받은 답도 찾아 돌려준다. 같은 요청을 다시 기다리면 같은 첫 답을 돌려준다.
- `--timeout`이 지나면 HTTP 408로 실패한다. CLI는 서버의 오류 응답을 기다릴 여유 시간 5초를 더 둔다.

## 메시지 종류

메시지는 모두 종류를 가진다(출력 표준 R8 v5 2단계). 머리 글자(QUESTION:, READY 등)로 뜻을 알리면 형식이 갈리고 받는 곳이 틀렸다. 종류와 그 칸, 터미널 낱말, 머리 꼴은 [src/protocol.rs](../../src/protocol.rs)의 `MessageKind` 한 곳에만 둔다. 화면 타입은 거기서 만든다.

- 종류: 에이전트가 보내는 `ask`·`answer`·`done`·`note`, 관문 명령과 병합 큐가 보내는 `ready`·`verdict`·`merged`·`rework`·`failed`·`withdrawn`, loom이 보내는 `exited`·`setup-failed`·`removed`·`adopted`·`human-input`. `rules-changed`는 옛 알림이다. 옛 기록을 읽으려고 종류만 남겼다.
- 터미널 머리: `loom message #<번호> (from: <이름 또는 loom>, kind: <낱말>[, mode: steer|interrupt])`, 칸마다 한 줄, 그 뒤 본문. loom이 보낸 알림은 `from: loom`이다.
- 조정·중단은 `note`만 된다.
- 저장: `messages.what`에 종류 JSON을 둔다. 이벤트 `Entry::Message`도 같은 값을 가진다. 옛 줄은 값이 없고 `note`로 그린다.
- `note`·`answer`·`done` 본문을 종류 낱말(QUESTION, READY 등)로 시작하면 거절하고 맞는 동사를 알린다(`KindWord`). 관문 낱말 가운데 READY만 모든 저장소에서, 나머지는 관문 스크립트가 있는 저장소에서만 막는다.
- 턴 끝 검사: loom 명령을 부르지 않은 턴의 마지막 답이 종류 낱말로 시작하는 줄을 가지면 한 번 다시 일하게 한다. 모든 노드가 대상이다. 다시 일하게 한 검사는 이벤트 `nudged`로 남는다.
- `human-input`: Claude 노드의 UserPromptSubmit 훅이 사람이 터미널에 친 글을 부모에게 원문 그대로 보낸다(자르거나 다듬지 않는다). Claude 부모는 긴 글을 훅 상한(`BATCH_LIMIT_BYTES`) 때문에 파일 미리보기로 받는다. 띄울 때 loom이 넣은 첫 지시문은 보내지 않는다. loom은 Codex·Cursor·OpenCode 2의 `human-input` 글을 넘기지 않는다. 이 노드의 사람 지시는 에이전트가 `loom note parent`로 알린다(agent-rules).
- `rules-changed`(옛 알림): 데몬이 배포마다 산 노드에 바뀐 스킬을 알리고 `loom relaunch`를 권했다. 지금은 데몬이 시작 글이 바뀐 노드만 스스로 다시 띄운다(「다시 띄우기」).

## 노드 제거와 입양

사람 지시(2026-10-19): 부모를 지워도 자식은 지우지 않는다. 다른 노드가 언제든 부모 역할을 맡는다.

- 사람은 카드의 [노드 제거]로 노드 하나를 지운다. 확인 창 없이 바로 지운다(2026-10-20 사람 지시 "노드 제거시 경고 팝업 안뜨고 바로 삭제되도록 만들어"). 데몬은 그 노드 프로세스를 끝낸다. Codex 노드면 app-server도 끝낸다. DB에서 노드와 그 노드가 받은 메시지, 보관한 메시지를 지운다.
- 자식은 계속 돈다. 자식의 부모는 비고, 자식은 뿌리가 된다.
- 지운 노드가 `running`이었고 부모가 남으면 부모 메일함에 `removed` 한 줄을 넣는다. 이 줄은 메일함 상한을 넘어도 넣는다. 버리면 부모가 끝없이 기다린다.
- 메시지는 보낸 노드 이름을 함께 저장한다. 보낸 노드를 지워도 받는 노드는 보낸 이름을 읽는다.
- 에이전트는 `loom rm <자식>`으로 자기 자식만 지운다. 정리는 [노드 제거]와 같다. 지운 노드의 자식은 같은 트랜잭션에서 부르는 노드가 데려간다(입양 규칙). 하나라도 데려갈 수 없으면 아무것도 바꾸지 않고 거절한다. 에이전트가 사람의 길을 쓰면 회수하지 않은 손자가 뿌리로 남았기 때문이다(2026-10-21 사고). `loom done`은 일을 끝내고 프로세스가 끝난 자식(`done`이고 `process_exited`)이 남으면 거절한다(`Refusal::SpentChildren`). 거절 글은 그 자식, 지우면 데려올 손자, `loom rm`·`git worktree remove` 명령을 알린다. 부모 없는 노드도 같다. 빠지는 자식: 프로세스가 사는 자식, 관문 차례가 열린(병합 전) 브랜치의 담당과 검토자(큐가 기다리고 새 차례를 받는다), 역할 없는 자식(사람이 띄워 입양한 노드와 명령 노드 `loom spawn <이름> -- <명령>`. DB에는 둘을 가를 칸이 없다. 명령 노드는 끝나면 보통 `exited`라 규칙 밖이다), `loom done --keep <이름>=<이유>`로 남긴 자식. 남김은 그 호출에만 듣고, 이유는 요약 끝에 `Kept: <이름> (<이유>)`로 붙는다. 남김은 DB에 따로 두지 않는다. 다음 `loom done`에서 다시 이유를 적는다. 근거: 2026-10-25 사람 승인 Q994 A, "왜 다쓴걸 바로 정리 안하나". 그 전에는 사는·잠든 자식 이름을 경고로만 출력해 다 쓴 노드가 쌓였다.
- 입양: 노드의 부모를 다른 노드로 바꾼다. 부모가 있는 노드도 된다.
  - 에이전트: `loom adopt <이름>`. Claude·Codex 승인 없이 부른다. `loom spawn`만 승인을 받는다.
  - 사람: 부모가 될 카드의 아래 잇기 점을 끌어 자식이 될 카드에 놓는다.
  - 거절: 자기 자신이나 자기 자손을 부모로 정하면 순환이다. 입양 뒤 중첩 깊이가 상한을 넘거나 새 부모의 자식 수가 상한에 닿았으면 거절한다. 데려간 노드의 이름이 새 부모나 새 형제와 겹치면 거절한다.
  - 데려간 노드가 `running`이면 옛 부모 메일함에 종류 `adopted`(칸 `node`, `parent`) 메시지를 넣는다. 옛 부모가 끝없이 기다리지 않게 한다.
  - 자식에게도 새 부모 이름과 번호를 큐로 알린다. 이 통지는 메일함 상한을 넘어도 넣는다.
- 뿌리 되돌리기: `loom detach <이름>`(사람 API는 `POST /api/nodes/{id}/detach`, 화면 버튼은 없다)은 노드의 부모를 NULL로 바꾸는 한 트랜잭션이다. 부르는 쪽 제한은 없다(입양과 같다. 2026-10-26 사람 지시 "누가 누굴 띄우는지는 아무 제한 없게 하라"). 복사한 값은 없다. `ask`가 부모 유무를 부를 때마다 읽어서 보낼 곳이 바로 바뀐다.
  - 거절: 이미 뿌리인 노드, 같은 이름의 다른 뿌리가 있는 노드(뿌리 이름은 서로 달라야 한다).
  - 노드가 `running`이면 옛 부모 메일함에 종류 `adopted`(칸 `parent`는 `(none)`)를 넣고, 노드에는 부모가 없다는 큐 통지를 보낸다. 새 종류를 만들지 않은 까닭은 「부모가 바뀌었다」는 같은 사실이고 받는 쪽 처리(깨우지 않음, 상한 제외)가 같아서다. 이벤트는 `adopted`이고 `to`가 없다.
  - 이미 전달한 `ask`는 옛 부모에게 남는다. 떼어낸 뒤의 `ask`부터 사람 받은편지함(`Q` 번호)으로 간다.
- 보관: 부모 없는 노드가 부모에게 보내는 메시지는 버리지 않는다. 그 노드가 보관한다.
  - 보관하는 것: `exited`, 그래프에 없는 이름으로 보낸 `loom note`. 지운 부모의 이름이 그래프에 없는 이름이다. 부모 없는 `done`은 보관하지 않고 받은편지함 완료 알림으로만 보인다(2026-10-22 사람 질문 "위에 뜬 보관 1은 뭔가").
  - 부모를 지울 때 자식이 그 부모에게 보냈지만 아직 전하지 않은 큐 메시지도 자식이 보관한다.
  - 조정·중단은 보관하지 않고 거절한다. 받을 노드의 프로필에 따라 넣는 방법이 다르기 때문이다.
  - 새 부모가 생기면 보관한 메시지를 보낸 순서대로 그 부모 메일함에 넣는다. 보관할 때 상한(50)을 봤으므로 이때는 메일함 상한을 보지 않는다.

## 전달 지점

| 방식 | 받는 노드 상태 | Claude Code | Codex | OpenCode 2 |
|---|---|---|---|---|
| 큐 | `loom wait` 안 | `loom wait`가 본문을 돌려준다 | 같다 | 같다 |
| 큐 | 일하는 중 | 다음 PostToolUse 훅 맥락(조정과 같다). 도구를 부르지 않고 턴이 끝나면 Stop 비동기 훅이 꺼내 바로 다음 턴으로 깨운다 | `turn/completed` 뒤에 `turn/start` | 입력함 `queue`. 지금 실행이 끝난 뒤 같은 실행에 들어간다 |
| 큐 | 쉬는 중 | Stop·SessionStart 비동기 훅(`asyncRewake`)이 기다리다 꺼내고 exit 2로 끝난다. Claude가 그 stderr로 새 턴을 시작한다. 부모는 `loom wait` 대신 턴을 끝내고 기다린다 | `turn/start`로 깨운다. 부모는 `loom wait` 대신 턴을 끝내고 기다린다 | 입력함 `queue`가 새 실행을 시작한다. 부모는 `loom wait` 대신 턴을 끝내고 기다린다 |
| 조정 | 일하는 중 | PostToolUse 훅 맥락 | `turn/steer` | 입력함 `steer`. 다음 단계 사이(도구 호출 뒤)에 들어간다 |
| 중단 | 일하는 중 | 다음 PreToolUse 훅이 도구 호출을 거부하고 본문을 돌려준다. 셸 명령 실행 중이면 데몬이 `loom guard`로 알린 셸과 그 자손 프로세스를 끝내고 PostToolUseFailure 훅이 본문을 돌려준다 | `turn/interrupt` 뒤에 `turn/start` | 세션의 셸과 그 자손을 끝내고 `POST …/interrupt` 뒤에 입력함 `steer` |
| 조정·중단 | 쉬는 중 | 큐와 같다 | 큐와 같다 | 입력함 `steer`가 새 실행을 시작한다 |

Cursor는 Claude와 같은 표를 훅 이름만 바꿔 따른다(아래 「Cursor」 항목).

- 코어와 어댑터: 모든 프로필이 데몬 코어 하나(`daemon::agent`)를 거친다. 코어 일은 꺼내기, 받음 확인, 큐로 돌리기, 턴 끝, 사람 입력, 쉬는 대기, 서버 전달 작업이다. 프로필 어댑터는 그 프로그램의 사건을 코어 호출로 옮기고, 코어의 답을 그 프로그램의 형식으로 쓰기만 한다.
  - 훅 프로필(Claude, Cursor, pi, OMP): CLI 훅 코어 하나(`cli::hook`)가 모델 알림, 어댑터의 추가 알림, 바로 꺼내기(`/api/agent/take`), 쉬는 대기(`/api/agent/idle`), 출력, 받음 확인, 다시 붙기를 한다. 어댑터(`profile::HookEvent`)는 입력 읽기, 사건마다 꺼낼 종류, 출력 형식(Claude stderr와 exit 2, Cursor `followup_message`, pi 한 줄 답)과 제 일만 둔다. 제 일: Claude 서브에이전트(꺼내지 않고 받지 않은 중단만 묻는다), 사람 대기 알림(`hook-wait`), 한도 걸림(`rate_limited`). Cursor 답 글(`said`), 질문 창(`question-box`), 턴 id(`generation_id`). pi 판 맞지 않음(바로 다시 띄우기). 전달 방식은 stdin JSON 한 번(Claude, Cursor)과 pi NDJSON 통로다.
  - 서버 프로필(Codex, OpenCode 2): 코어의 전달 작업(`App::deliver_loop`) 하나가 노드마다 돈다. 어댑터(`profile::ServerAdapter`)는 꺼낼 종류 차례(`takes`), 바뀜 알림(`changed`), 턴 끝·멈춘 실행·사람 입력 신호(`signal`), 넣기(`inject`), 셸 끝내기, 턴 시작(재촉), 조정(열린 질문 알림)만 둔다. 멈춘 실행(OpenCode 2 `session.execution.failed`·`interrupted`)은 턴 끝 검사를 하지 않고 턴 끝 다시 띄우기만 돌린다. 그래서 사람 입력과 재촉 표시가 조정이 연 다음 실행으로 넘어간다(2026-10-26 보조 검토자: 멈춘 실행이 그 표시를 지워 재촉이 빠졌다).
  - 꺼내기는 한 길이다(`App::take_now`, `App::take_mail`). 다시 띄우기가 쥔 노드(턴 끝 다시 띄우기 포함)와 재우는 중인 노드에는 어느 프로필에도 메일을 넘기지 않는다. 앞 판은 훅의 `/api/agent/take`만 이 검사를 건너뛰어, 곧 끝날 프로세스에 메일을 넘겼다.
  - 턴 끝은 한 곳이다(`App::turn_ended`): 답 글, 턴 끝 검사(재촉), 재촉이 없을 때 턴 끝 다시 띄우기를 차례로 한다. 서버 프로필은 전달 작업만 턴 끝을 처리한다. 상태 추적(`follow_server_turns`)은 상태 사건만 보낸다. 앞 판은 같은 서버 턴 끝을 두 곳이 받아, 재촉으로 새 턴을 연 노드를 턴 끝 다시 띄우기가 끊을 수 있었다. 턴 끝 검사의 턴 표시(사람 입력, loom 동사 부름, 종류 줄 재촉, `loom ask`)는 `nodes.turn_flags`에도 적는다(`TurnEnds::stored`: 데몬이 시작할 때 읽고, 바뀔 때마다 쓴다). 데몬이 턴 안에서 다시 시작해도 재촉을 되풀이하거나 빠뜨리지 않는다. 질문 상자 표시는 프로세스마다 지우므로 메모리에만 둔다.
  - 한 번에 꺼내는 본문 합은 모든 프로필이 `profile::BATCH_LIMIT_BYTES`(8KB) 하나다.

- Claude: 데몬은 전달할 때 노드가 일하는지 쉬는지 보지 않는다. 불린 훅이 그 상태다(판단이 읽는 상태는 「에이전트 상태」). 훅마다 꺼내는 방식: UserPromptSubmit은 모두, PostToolUse는 조정(그리고 기다리는 큐 알림), PreToolUse·PostToolUseFailure는 중단. SessionStart·Stop은 턴이 없는 때라 비동기 훅으로 모두 기다린다. 첫 입력(지시문)을 시작 인자로 넘긴 세션은 SessionStart를 `clear`·`compact`에서만 건다. 쌓인 메시지는 첫 입력 턴의 UserPromptSubmit이 넘긴다. 근거: 워크트리 설정 동안 쌓인 조정을 시작 훅이 먼저 넘기자 Claude가 그 턴을 첫 입력보다 먼저 돌았고, 자식은 지시문이 없다고 보고 부모에게 다시 물었다(2026-10-22 실측).
- Claude 쉬는 노드 깨우기: Stop·SessionStart 훅은 `asyncRewake`다. Claude는 이 훅을 뒤에서 돌리고, exit 2로 끝나면 stderr를 모델에 넘겨 쉬던 세션을 깨운다. 입력창에 사람이 쓰던 글은 그대로 남는다(「실측 근거」). loom은 PTY에 글자를 쓰지 않는다.
  - 그 훅의 `loom hook`은 `/api/agent/idle`로 메시지가 올 때까지 기다린다. 오면 본문을 stderr에 쓰고 받음을 확인한 뒤 exit 2로 끝난다.
  - Claude는 새 턴이 시작해도 옛 비동기 훅을 끝내지 않는다(실측). 그래서 데몬은 노드마다 대기를 하나만 둔다. 같은 노드의 새 대기, 턴 안의 훅(`/api/agent/take`), 노드 프로세스 종료가 옛 대기를 빈 목록으로 끝낸다. 그 훅은 아무것도 쓰지 않고 exit 0으로 끝난다.
  - 대기가 열릴 때와 끝날 때마다 이벤트 기록에 한 줄을 남긴다: `idleOpened`(노드), `idleEnded`(노드, 까닭 `by`). 까닭은 `mail`(메시지를 넘겼다), `newWait`, `turn`(턴 안의 훅, 칸 `hook`에 런타임의 훅 이름. 그래서 `take` 요청은 `hook`을 보낸다), `relaunch`, `exit`, `sleep`, `gone`(요청이 끝나기 전에 사라졌다: 훅 프로세스가 끝났거나 연결이 끊겼다), `error`(메일함을 읽지 못했다)다(`daemon::idle::Wait`). 화면 이벤트 콘솔은 이 두 종류를 보이지 않는다. 기록 읽기(`/api/events/log`)는 500개 상한 전에 이 두 종류를 뺀다. 그래서 대기가 최근 기록을 채워도 콘솔이 비지 않는다. 웹소켓(`/api/events`)과 DB에는 있다. 대기의 노드 이름은 대기가 열릴 때 읽는다. 그래서 대기 중에 노드를 지워도 끝 기록이 남는다. 근거: 2026-10-24 Cursor 코디(노드 567)가 01:10에 턴을 끝낸 뒤 01:21 메일을 08:22 사람 입력 때에야 받았다. 쉬는 대기의 기록이 없어 그 동안 대기가 열려 있었는지 알 수 없었다(2026-10-24 총괄 결정: 화면 변경 없이 기록만). 시험 데몬 실측(2026-10-24): 대기를 연 curl을 끝내자 바로 `gone`이 남았다.
  - 한계: Linux loom 사본 없이 띄운 WSL Claude 노드의 Stop 훅은 interop `loom.exe`로 간다. 그 띄우기가 멈추면 데몬은 기록 파일의 턴 끝으로 그 일을 안다(「에이전트 상태」 닿지 않은 stop 훅). 다른 노드의 훅은 노드 접속점으로 간다(「에이전트 실행」).
  - 세션 시작 훅의 대기가 첫 턴의 UserPromptSubmit보다 늦게 열리면 그 턴 동안 산다. 그 사이에 온 메시지는 Claude가 턴 안의 다음 입력으로 넣는다. 잃지는 않는다.
  - 프로세스가 끝난 노드의 대기는 거절한다(410). Claude가 죽고 훅만 남아도 다시 붙지 못한다.
  - 노드 명령은 머리글 `loom-protocol: <판>`(`protocol::NODE_CALLS`)을 보낸다. 머리글이 없으면 데몬이 받는다(배포 전에 뜬 옛 훅, 한 판 동안). 받지 않는 판이면 데몬은 426과 고정 글 하나로 거절하고, 그 노드를 판 맞지 않음(`versionMismatch`)으로 두고 같은 세션으로 바로 다시 띄운다(pi `relaunch-unserved`와 같은 `App::relaunch_unserved`). 거절된 훅 뒤에는 턴 끝을 볼 수 없어 듣는 중을 기다릴 수 없기 때문이다.

WSL 노드에서는 그때마다 Windows `loom.exe`를 interop으로 띄웠고, interop이 가끔 시작에서 실패했다(`~/.loom/wsl-interop.log`: `UtilAcceptVsock:273: accept4 failed 110`, hook 1회, pi-hook 3회, 2026-10-25). 실패한 사건은 사라졌고, 쉬는 대기면 노드가 메시지를 못 받았다(같은 날 pi 시험에서 9.6분). 이제 셸 심은 `pi-hook`을 버퍼 없이 바로 실행한다: 노드 접속점이 있으면 Linux loom으로, 없으면 interop `loom.exe`로 세션마다 한 번 띄운다(재시도는 확장이 맡는다). 훅 프로세스가 끝나면 확장은 열린 요청을 모두 실패로 끝내고 다음 요청에서 훅을 다시 띄운다. 프로세스를 띄우는 곳은 `open` 하나다(나중에 다른 전송으로 바꿀 자리). before_agent_start(사람 입력과 첫 지시문)는 모두를 꺼내 그 실행의 loom 메시지로 넣는다. tool_result는 모두를 꺼내 도구 결과 끝에 글로 붙인다. tool_call은 중단만 꺼내 그 호출을 막고(`block`) 본문을 이유로 준다. 중단이 없으면 bash 명령 앞에 `loom guard` 줄을 붙인다. 명령이 이미 그 줄로 시작하면 붙이지 않는다(모델이 기록의 줄을 따라 쓴다). pi의 bash에는 백그라운드 인자가 없었다. 모델이 Claude의 `run_in_background`를 쓰면 pi가 무시하고 끝날 때까지 턴을 막았다(2026-10-25 pi 시험에서 시험 데몬에 62분 묶임). 그래서 확장은 같은 이름의 `bash` 도구를 등록해 pi 것을 바꾼다. bash는 사람의 pi 설정(`shellCommandPrefix`·`shellPath`)을 pi와 같이 따른다. 호출마다 그 자리의 설정을 pi의 신뢰 판단(`ctx.isProjectTrusted()`)과 함께 읽어, 신뢰하지 않은 저장소의 `.pi/settings.json`은 쓰지 않는다. `run_in_background: true`면 같은 셸(`getShellConfig`)로 명령을 떼어(`detached`) 띄우고 출력을 `$LOOM_TASK_DIR/logs/background-<시각>-<번호>.log`에 쓴 뒤 pid와 로그 경로를 바로 돌려준다. 시작에 실패하면 도구 오류로 알린다(이 호출에는 `loom guard` 줄을 붙이지 않는다). 아니면 pi의 bash를 그대로 부르고, `timeout`이 없으면 1200초를 준다. 시간이 넘으면 pi가 프로세스를 끝내고 결과가 그 사실과 `run_in_background`를 알린다. 모델의 실수로 노드가 말없이 묶이지 않는다. 다른 도구가 부른 호출(`parentToolCallId`)은 꺼내지 않는다.
- OMP(omp 18.12.6): pi에서 갈라진 CLI다. Pi와 같은 `loom pi-hook` 줄 형식과 공용 모듈 `loom-hook.ts`를 쓰고, 확장 `omp-loom.ts`에는 다른 점만 둔다. omp에는 `agent_settled`가 없어 `agent_end`에서 턴 끝을 본다. `willContinue`이면서 `awaitingAsyncWork`가 아니면(omp가 스스로 이어 간다) 기다리지 않는다. 마지막 응답의 `stopReason`이 `aborted`여도 기다리지 않는다. 하위 에이전트 세션(`ctx.agent.kind`가 `sub`)도 같은 확장을 싣는다. 확장은 그 사건을 모두 버린다. 버리지 않으면 하위 세션이 노드의 기록 파일을 바꾸고 메시지를 꺼낸다. omp의 bash에는 `async`(백그라운드 작업)와 기본 시간 제한(300초)이 있어 바꾸지 않는다. `async: true` 호출에는 `loom guard` 줄을 붙이지 않는다. omp는 bash 명령을 자기 프로세스 안의 셸에서 돌린다(2026-10-25 시험: `sleep 50` 동안 omp 밑에 `loom pi-hook` 말고 자식 프로세스가 없었다). 그래서 데몬이 guard로 찾은 셸을 끝내는 중단이 omp에는 듣지 않는다(같은 시험에서 `sleep 40`이 끝까지 돌았다). 대신 확장이 도구가 도는 동안 1초마다 중단만 꺼낸다(`tool_call` 사건). 중단이 있으면 `ctx.abort()`로 턴을 끊고, 쉬게 되면 본문을 loom 메시지로 넣어 새 턴을 연다(같은 시험: 보낸 뒤 1초 안에 `Command aborted`).

- WSL 노드는 Windows 프로세스를 셸로 적지 않는다. Windows `loom.exe guard`의 조상 가운데 노드 프로세스의 자식은 안쪽 `wsl.exe`라서, 그것을 끝내면 노드의 WSL 세션이 통째로 끝난다(2026-10-24 노드 729: 중단 한 번에 노드가 죽었다). 대신 shim(`wsl::write_shim`)이 `guard`를 직접 맡고 loom.exe를 띄우지 않는다. 부모 PID와 그 시작 시각(`/proc/<pid>/stat` 22번째 칸)으로 빈 표시 파일 `/tmp/loom-guard-<uid>/<토큰>/<pid>.<시작 시각>`을 만들고(폴더 0700, 자기 것이 아니거나 링크면 적지 않는다), 끝난 셸의 표시를 지운다. 경로는 고정이다: 데몬의 `wsl.exe -e sh` 세션과 노드 셸은 `XDG_RUNTIME_DIR`·`TMPDIR`가 다를 수 있다. 중단하면 데몬이 커밋 뒤 요청 스레드 밖에서 `wsl.exe`를 한 번 띄운다(`wsl::end_shells`). 시작 시각이 맞고 환경에 노드 `LOOM_TOKEN`이 있는 표시만 그 셸과 자손을 끝내고(PID 재사용 대비), 읽은 표시 파일만 지운다. 폴더는 지우지 않는다: 읽은 뒤 생긴 표시가 남아야 다음 중단이 그 셸을 끝낸다(2026-10-25 검토). 개수 상한은 없다: 오래 도는 명령의 표시가 짧은 명령 표시에 밀려나면 중단이 그 명령을 놓친다(2026-10-24 검토). Linux bash는 fork를 흉내 내지 않아 부모 PID가 셸이다.
- 서브에이전트·백그라운드 포크의 훅(입력에 `agent_id`가 있다)은 메일을 꺼내지 않고 쉬는 대기를 끝내지 않는다. Bash 앞 `loom guard` 줄은 붙인다. 서브에이전트 PreToolUse는 `/api/agent/interrupt-pending`(꺼내지도 확인하지도 않는 조회)으로 받지 않은 중단이 있는지 묻고, 있으면 고정 글로 도구 호출을 거부해 서브에이전트를 본 에이전트로 돌려보낸다. 중단 본문은 본 에이전트의 다음 훅(Agent 호출의 PostToolUse)이나 쉬는 대기가 꺼낸다. 서브에이전트 훅은 사람 대기가 없으면 `hook-wait`를 보내지 않는다: 본 에이전트의 승인 대기를 지우지 않게 한다. 근거: 2026-10-24 실측(Claude Code 2.1.310). 본 에이전트의 Stop 훅 뒤 서브에이전트 PreToolUse가 쉬는 대기를 턴 시작으로 끝내 깨움이 사라졌고, 서브에이전트 PostToolUse가 본 에이전트 메일을 꺼내 갔다. 꺼내지 않기만 하면 포그라운드 서브에이전트가 끝날 때까지 중단이 늦는다(2026-10-24 검토).
- 백그라운드 Bash 명령(`run_in_background`)에는 붙이지 않는다. 결과를 기다리는 백그라운드 `loom wait`를 중단이 끝내면 안 된다.
- 중단 요청은 수신자·본문 길이·프로세스 생존·큐 용량을 먼저 검사한다. 거절한 요청은 셸을 끝내지 않는다.
- Claude 중단은 같은 트랜잭션에서 메시지를 쓴 뒤 셸을 끝낸다. 커밋 전에는 대기 명령이나 훅이 메시지를 꺼낼 수 없다.
- Codex·OpenCode 2 중단은 전달 작업이 큐에서 꺼낸 뒤 셸을 끝낸다. 서버의 턴 중단보다 셸 종료가 먼저다.
- 데몬은 셸이 노드 프로세스의 자손일 때만 끝낸다. 끝난 셸의 PID를 다른 프로세스가 받았을 수 있다.
- 전달 확정(최소 한 번 전달, 읽음 확인): 메시지는 넘김, 출력, 읽음을 거친다(R32 v3 ④A).
  - 넘김: 꺼낸 메시지에 꺼낸 시각(`sent_at`)을 적는다. 넘긴 메시지는 다시 꺼내지 않는다.
  - 출력: 받는 쪽이 에이전트에게 본문을 쓴 뒤 `/api/agent/ack`로 알린다(`printed`). `loom wait`는 본문을 출력한 뒤, `loom hook`은 훅 출력을 쓴 뒤, Codex·OpenCode 2 전달 작업은 넣기 요청이 성공한 뒤 알린다. 훅이 없는 노드(명령, 연결 없는 에이전트)는 출력이 곧 읽음이다.
  - 읽음: 출력 뒤 같은 프로세스에서 다음 사건 `turnStarted`, `turnEnded`, `turnEndedWaitOpened`(합친 턴 끝), `serverBusy`, `serverIdle`가 오면 모델이 본문을 지나 돌았다. 상태 기계가 그 사건을 적용하는 트랜잭션에서 그 노드의 출력한 메시지를 `delivered`로 바꾸고 `message`(`step: delivered`)를 남긴다(`agent_state::apply`). Codex·OpenCode 2는 넣기 성공이 출력이고, 다음 서버 상태 변화가 읽음이다.
  - 큐로 돌리기: 프로세스 종료(`exited`), 다시 띄우기 시작(`relaunchStarted`), 재우기(`slept`)는 읽지 않은 메시지(넘김·출력)를 모두 큐로 돌린다. 새 프로세스가 다시 꺼낸다. 마지막 쉬는 대기가 출력 전에 끊기면(`waitClosed` `gone`·`error`), 새 쉬는 대기가 열리면(`waitOpened`), 그리고 훅 턴 끝(`turnEnded`, `turnEndedWaitOpened`)에는 넘겼지만 출력하지 않은 메시지를 큐로 돌린다. 새 대기는 쉬는 대기의 답을 다 받지 못한 훅이 다시 붙은 것일 수 있다. 그 답의 메시지는 넘김으로 남고, 쉬는 노드에는 큐로 돌릴 다른 사건이 오지 않기 때문이다(2026-10-26 보조 검토자). Claude·Cursor·pi는 stop 훅과 함께 도는 꺼내기 훅이 없다. 그래서 턴 끝에 출력하지 않은 메시지는 응답을 잃은 꺼내기다. 같은 요청의 대기가 바로 다시 꺼낸다(2026-10-25 코디 답 #7596 A). Codex·OpenCode 2 전달 작업은 넣기 요청이 실패하면 그 묶음을 바로 큐로 돌리고(`Graph::release`, `App::deliver_loop`), 메일함이나 스레드가 다시 바뀔 때 다시 꺼낸다. 데몬이 시작할 때도 넘겼지만 출력하지 않은 메시지를 큐로 돌린다. 시간으로 다시 주는 규칙(`REDELIVER_AFTER` 30초)은 지웠다.
  - 늦은 받음 확인: 받음 확인은 넘긴 메시지에만 듣는다. 큐로 돌린 뒤 옛 프로세스가 보낸 확인은 아무것도 바꾸지 않는다.
  - 한계: 받는 쪽이 본문을 넣은 뒤 확인하기 전에 죽거나, 뒤에서 도는 `loom wait`가 넘겨받은 메시지를 턴 끝이 큐로 돌리면 같은 메시지가 두 번 간다. 그래서 본문 머리에 메시지 번호를 넣는다(`loom message #12 (from: 총괄, kind: note)`, 아래 「메시지 종류」). 에이전트는 같은 번호로 같은 메시지임을 안다.
  - 한계: 훅이 출력하고 확인했지만 Claude가 훅 시간 초과로 그 출력을 버리면 다음 사건이 그 메시지를 읽음으로 바꾼다. `loom hook`의 응답 상한(5초)을 훅 `timeout`(10초)보다 짧게 두어 드물다. 앞 판(30초 뒤 다시 줌)도 같거나 나빴다.
- Codex: 전달 작업은 메일함이나 스레드 상태가 바뀔 때 꺼낸다. 쉬면 모두, 일하면 조정·중단만 꺼낸다.
- Codex: `turn/start`를 보낸 뒤 상태 알림이 오기 전까지는 일하는 중으로 본다. 그 사이에 큐로 턴을 하나 더 시작하지 않는다.
- Codex: `turn/start`가 막 시작된 다른 턴과 겹쳐 실패하면 본문을 `turn/steer`로 넣는다. `turn/steer`가 이미 끝난 턴을 겨눠 실패하면(`expectedTurnId` 불일치) `turn/start`로 보낸다. 꺼낸 메시지를 잃지 않는다.
- Codex 중단: 데몬은 app-server 아래의 세션 리더(셸 명령)와 그 자손을 먼저 끝낸다. MCP 서버와 `codex-code-mode-host`는 서버 세션 안에 있어 남는다. 그 뒤 지금 턴에 `turn/interrupt`를 보내고 `turn/start`로 본문을 보낸다.
- OpenCode 2: 데몬은 전달할 때 노드가 일하는지 쉬는지 보지 않는다. 서버 입력함이 상태에 맞게 넣는다. 메일함이 바뀌면 조정·중단을 먼저 꺼내고, 없으면 큐를 꺼낸다.
- OpenCode 2: 메시지 id는 데몬이 만든다. 서버는 같은 id를 한 번만 넣는다. 넣기가 실패하면 같은 id로 1초 간격, 5번까지 다시 넣는다. 그래서 다시 넣어도 두 번 들어가지 않는다. 넣기가 성공한 뒤 받음을 확인한다. 5번 모두 실패하면 그 묶음을 바로 큐로 돌린다(「전달 확정」).
- OpenCode 2 중단: 데몬은 서버 셸 목록(`GET /api/shell`)에서 그 세션의 셸 PID를 읽는다. 서버의 자손인 셸과 그 자손을 끝낸 뒤 메시지를 넣는다. 전달 작업은 중단을 꺼내면 `interrupt`를 보낸 뒤 본문을 입력함 `steer`로 넣는다. `interrupt`는 셸의 프로세스 그룹만 끝낸다. 셸보다 먼저 보내면 셸이 목록에서 빠지고, `setsid` 자손은 부모를 잃어 찾을 수 없다.
- OpenCode 2: 중단 전에 입력함에 있던 큐는 중단 본문의 실행이 끝난 뒤 들어간다(실측).
- Windows Codex 중단: Windows에는 세션 리더가 없어 데몬은 셸을 찾지 않는다. Codex가 `turn/interrupt` 때 셸을 스스로 끝낸다(「실측 근거」).

### 에이전트 상태

데몬 DB 표 `agent_states`가 노드마다 에이전트 상태 하나를 둔다(`graph::AgentState`). 상태는 시작(`starting`), 창 막힘(`blocked`, 닫히면 돌아갈 상태를 둔다), 듣는 중(`listening`), 듣지 못함(`deaf`), 턴(`turn`), 다시 띄우는 중(`relaunching`, 실패하면 돌아갈 상태를 둔다), 판 맞지 않음(`mismatch`), 잠(`asleep`), 끝남(`ended`)이다. 모든 에이전트 경로가 공통 사건(`AgentEvent`)을 보내고, 순수 함수 `AgentState::next` 하나가 상태를 바꾼다. 사건, 상태 쓰기, 그 사건이 바꾸는 메시지 상태(「전달 확정」)는 한 트랜잭션이다. 상태가 바뀔 때만 행의 `seq`가 1 늘고 이벤트 기록에 `agentStateChanged`(전, 후, 사건)를 남긴다. 표에 행이 없는 노드는 프로세스 칸으로 정한다(잠, 끝남, 그 밖에는 시작).

| 사건 | 입구 |
|---|---|
| `turnStarted`, `waitOpened`, `waitClosed`(까닭은 `idleEnded`와 같다) | 훅 프로필의 `/api/agent/take`, `/api/agent/idle`(`daemon::idle`). 사건마다 그 일을 한 곳이 한 번 보낸다: 대기 열기, 턴 훅, 대기를 끝낸 데몬(`relaunch`·`sleep`·`exit`), 메일을 넘긴 대기(`mail`). 대기 요청 쪽은 그만 아는 까닭(`gone`, `error`)만 보내고, 노드에서 마지막으로 연 대기일 때만 보낸다 |
| `turnEndedWaitOpened` | 턴 끝을 실은 `/api/agent/idle`(`IdleRequest.turn_end`). 턴 끝 검사가 재촉을 돌려주면 대기를 열지 않고 사건도 보내지 않는다(턴이 이어진다) |
| `turnEnded` | 옛 판 훅의 `/api/agent/turn-end`(한 판 동안 남긴다. 이 길만 턴→듣지 못함→듣는 중을 거친다), 닿지 않은 stop 훅의 증거(아래) |
| `serverBusy`, `serverIdle`, `serverLost` | Codex 스레드 상태, OpenCode 2 `working`(`daemon::runtime::follow_server_turns`). 노드의 지금 서버만 보낸다. 다시 띄우기나 종료가 바꾼 옛 서버의 늦은 사건은 버린다. 턴 끝 처리는 하지 않는다(「코어와 어댑터」) |
| `dialog`, `dialogCleared` | 신호의 응답 대기(`Graph::set_wait`), 사람 입력(`typed`), 닫기(`dismiss`) |
| `relaunchStarted`, `relaunchFailed`, `relaunched`, `slept`, `exited` | 옛 프로세스 끝내기(`end_old`, 옛 프로세스가 끝나지 않으면 실패), `Graph::restarted`·`slept`·`end_process`·`sleep_lost`(열 값을 바꾸기 전에 적용한다) |
| `versionMismatch` | pi 판이 맞지 않는 요청(`relaunch_unserved`) |

메일을 넘긴 대기 끝(`waitClosed` `mail`)은 턴이다. 듣는 중에 마지막 대기가 메일·턴 말고 다른 까닭으로 끝나면 듣지 못함이다. 창 막힘과 다시 띄우는 중에 온 사건은 돌아갈 상태에 적용한다. 노드 상태는 `loom status`의 `agent_state` 칸에 있다. 화면은 보이지 않는다(2026-10-25 사람 결정 Q1030: 카드에 보일 정보가 아니다). 화면 이벤트 콘솔은 `agentStateChanged`를 보이지 않는다.

판단은 이 상태를 읽는다(R32 v3 ②A).

- 턴 중(`App::busy`)은 시작, 턴, 다시 띄우는 중, 판 맞지 않음이다. 창 막힘은 턴 중이 아니다. 다시 띄우기는 턴 중이면 턴 끝까지 기다리고, 아니면 지금 한다(「다시 띄우기」, 에이전트-실행.md).
- 재우기는 듣는 중인 노드만 본다(`sleep_resting`, `put_to_sleep`).
- 옛 판정(훅 프로필의 `IdleWaits.turns`, Codex 스레드 상태, OpenCode 2 `working`, Claude 기록 파일의 열린 턴)과 그림자 비교(`agentStateDisagreed`)는 지웠다. `agentStateDisagreed` 종류는 옛 이벤트 기록을 읽으려고만 남긴다.

듣지 못하는 노드 살리기(R32 v3 ④A):

- 듣는 중에 마지막 대기가 `gone`·`error`로 끝나 듣지 못함이 되거나, 서버 연결이 끊겨(`serverLost`) 듣지 못함이 되면 데몬이 바로 같은 세션으로 다시 띄운다(`App::recover`). 데몬은 상태 변화를 이벤트 기록에서 받는다(`Graph::agent_changes`, `App::watch_agents`).
- 창 막힘 안에서 듣지 못함이 된 노드(대기가 끊김, 서버 연결이 끊김)는 창이 닫혀(`dialogCleared`) 듣지 못함이 될 때 살린다. 가드가 사람을 지킨다(2026-10-26 보조 검토자: 창 아래에서 훅이 끝난 노드가 사람 입력 전까지 듣지 못했다).
- 다시 띄우기 전에 가드(`restart_guard`)를 본다. 기록 파일이 그대로이고, 상태가 아직 듣지 못함이고, 사람이 쓰다 만 글이 없고(`nodes.drafted`), 사람 응답 창이 없어야 한다. `drafted`는 DB에 있어 데몬이 다시 시작해도 남는다. 보낸 뒤 사람의 첫 글자 입력이 켠다. 제어 문자, ESC로 시작하는 키(화살표, Esc), 터미널 보고, 사람 응답 창이 열린 동안의 키는 켜지 않는다(2026-10-26 보조 검토자 5회차: Esc 하나가 pi 노드를 영영 막았다). Esc 하나(0x1b)도 끈다(총괄 결정 #8218: 사람이 입력을 버린 것으로 본다. 각 TUI가 Esc로 입력 칸을 비우는지는 보지 않았다). 입력 칸을 비우는 키 Ctrl-C(0x03)는 끈다: pi 1.4.0 `app.clear` 기본 키 `ctrl+c` 「Clear editor」(`dist/core/keybindings.js:14`), OMP도 `app.clear` `ctrl+c`(실행 파일 문자열 「Clear editor (first) / exit (second)」), cursor-agent 2026.10.22 `handleCtrlC`는 비지 않은 입력을 지운다(`7000.index.js`). 사람 입력이 보내질 때(꺼내기 훅의 사람 입력: Claude `UserPromptSubmit`, Cursor·pi 사람 입력, 서버의 사람 입력) 끈다. Claude는 화면이 멈췄을 때 입력 칸이 비어 있어도 끈다. 프로세스가 바뀌면(다시 띄움·깨움·되살림·에이전트 바꿈, 끝남, 잠)과 턴이 시작되면(상태가 턴으로 바뀜. 창이 닫히거나 다시 띄우기가 실패해 같은 턴으로 돌아가는 것은 빼고) 같은 트랜잭션에서 끈다(`agent_state::apply`). 새 세션의 입력 칸은 비어 있기 때문이다(2026-10-26 보조 검토자 6회차). 다시 띄우기가 실패해 옛 프로세스가 남으면(`relaunchFailed`) 끄지 않는다. 한계: Pi·OMP·Cursor에서 사람이 Backspace로 글을 모두 지우면 보내거나 Ctrl-C를 칠 때까지 켜진 채다. 그 입력 칸을 읽지 않기 때문이다. 사람은 그 노드 앞에 있다. 글 하나에 쓰기 몇 번이고, 글자마다 쓰지 않는다. 끄는 일이 그 노드의 다시 보기 사건이다(`App::draft_ended`). 앞 판은 메모리의 입력 시각(`IdleWaits.typed_at`)을 보아 데몬 재시작 뒤 pi·OMP·Cursor의 쓰다 만 글을 몰랐다(2026-10-26 총괄 결정). Claude는 입력 칸이 비고 화면에 도는 턴이 없어야 한다. 가드가 막으면 노드는 듣지 못함으로 남는다. 그 노드의 다음 상태 변화가 다시 듣지 못함이면(예: 창이 닫힘) 다시 해 본다. 막은 뒤 그 노드에 새 메일이 와도 다시 해 본다(`watch_sleep`의 메일함 변화, `App::recover_held_with_mail`). 막을 때 본 가장 새 메일보다 새 메일만 센다. 다시 띄우기가 옛 프로세스를 끝내기 전에 실패하면(세션 기록 복사, 새 프로세스 준비) 옛 프로세스를 그대로 두고, 같은 막음으로 다음 사건과 새 메일에 다시 해 본다. 오류는 `relaunched` 기록에 남는다. 옛 프로세스가 이미 끝난 뒤의 실패만 노드를 잃음으로 바꾼다(2026-10-26 R32 점검: 앞 판은 실패마다 옛 프로세스를 끝내고 노드를 끝냈다). 아무도 치지 않는 노드(입력 칸에 남은 글)는 다른 사건이 오지 않아, 메일을 받아야 할 때 다시 본다(2026-10-26 코디 결정). 사람 입력으로 턴이 시작하면 끝난다. 시각으로 다시 해 보지 않는다.
- 훅 프로세스가 살아 있어도 쉬는 대기가 없으면 듣지 못한다. 그래서 데몬은 훅 프로세스를 보지 않고 바로 다시 띄운다. 접속점이 있는 노드는 훅의 연결을 호스트가 쥐어, 데몬이 다시 시작해도 대기가 `gone`으로 끝나지 않는다. 접속점이 없는 노드의 훅이 다시 붙지 못하면 다시 띄우기 말고는 돌아올 길이 없다. 다시 띄우기는 같은 세션을 잇고 노드를 접속점으로 옮긴다. 옛 훅은 옛 프로세스와 함께 끝난다. 늦게 온 옛 대기는 메시지를 출력하지 못해 확인하지 않으므로, 다음 `waitOpened`가 그 메시지를 큐로 돌린다(「전달 확정」). 근거: 앞 판은 훅 프로세스가 살아 있으면 다시 띄우지 않고 `SWEEP`마다 다시 보았다(`Held::Hook`, `wsl::hook_running`). 2026-10-26 05:07 배포 뒤 접속점 없는 Claude 노드 6개가 그 검사에 막혀 사람이 입력할 때까지(최대 2.5시간) 듣지 못했다. 그 막음은 메모리에만 있어, 07:45 데몬 재시작 뒤 #526은 아무 사건도 다시 살리지 않았다.
- 데몬이 시작할 때(`App::watch_agents`) 듣지 못함으로 저장된 노드를 모두 같은 규칙으로 살린다. 가드가 화면을 읽으므로, 모든 살리기는 호스트가 아직 화면을 보내지 않은 노드면 첫 화면이 온 뒤 본다(`App::recover`). 붙은 직후 쉬는 대기 검사로 듣지 못함이 된 노드도 같다(2026-10-26 검토자 3회차: 빈 화면을 사람 입력으로 보고 막았다).
- 데몬이 다시 시작하면 메모리의 쉬는 대기가 없다. 그래서 데몬은 노드의 호스트에 붙은 사건에서 그 노드를 본다(`App::hear_lost_wait`): 훅 프로필(Claude, Cursor, Pi, OMP) 노드가 듣는 중인데 열린 쉬는 대기가 없으면 `waitClosed` `gone`을 적용한다(`IdleWaits::lose_unheld`). 노드는 듣지 못함이 되고 위와 같이 살린다(2026-10-26 보조 검토자: DB가 듣는 중으로 남긴 노드에 메일이 가지 않았다).
  - 판 5 호스트는 데몬이 없는 동안 쥔 연결 수를 스트림 연결에 알린다(`Held`, 「에이전트 실행」 노드 접속점). 데몬은 그 수만큼의 첫 스트림에 표를 붙이고(`arrival::callers`), 표가 모두 돌아오면 그 노드를 본다. 쉬는 대기 요청의 표는 대기를 연 뒤에(`App::wait_idle`), 다른 요청의 표는 노드 라우터에 닿을 때(`runtime::from_its_node`), 요청 없이 끝난 연결의 표는 그 끝에 돌아온다. 그래서 쥔 쉬는 대기는 검사보다 먼저 열리고, 노드는 듣지 못함을 거치지 않는다. 쥔 연결이 없으면 붙을 때 바로 본다.
  - 판 4 이하 호스트는 쥔 수를 알리지 않는다(판 3 이하는 접속점도 없다). 그 노드는 붙을 때 바로 본다. 쉬던 노드는 듣지 못함이 되고 같은 세션으로 한 번 다시 뜨며, 다시 뜬 노드는 판 5 호스트를 얻는다. 쥔 쉬는 대기가 다시 띄우기의 가드보다 먼저 닿으면 노드는 듣는 중으로 남는다. 노드가 듣는 중으로 보이는데 아무도 듣지 않는 것보다 조용한 다시 띄우기 한 번이 낫다(2026-10-26 코디 답 #7980·#7982).
  - 근거: 첫 검사를 30초 미루던 쓸기(`SWEEP`)를 지웠다(R32 시간표 「30초 쓸기는 상태 바뀜 사건으로 바꿈」). 데몬은 시작을 마친 뒤에야 접속점 요청을 받으므로, 붙는 순간에는 쥔 쉬는 대기가 아직 열리지 않았다. 그래서 `App::resume` 끝에서 본다면 쉬는 노드가 모두 듣지 못함이 된다.
- 턴 끝 다시 띄우기가 걸려 있으면 그 계획(같은 세션 또는 다른 에이전트)을 쓴다.
- 다시 띄우기 자체가 실패하면 노드를 끝낸다(`Graph::lost`). 부모는 지금의 `exited` 알림을 받는다(2026-10-25 사람 결정 Q1030). 가드가 막은 것은 실패가 아니다.
- 사람이 Claude를 스스로 끝낼 때(`/exit`) 훅이 끊겨 `gone`이 먼저 올 수 있다. 사람의 입력 기록이 기록 파일보다 새로우므로 가드가 막는다. 가설: 사람이 loom 화면 밖(다른 터미널)에서 끝내면 가드가 막지 못하고 노드가 다시 뜰 수 있다. 확인하지 않았다.
- 닿지 않은 stop 훅(Claude, Cursor): loom은 PTY에 글자를 쓰지 않는다. 그래서 알림 줄(`claude::wake_line`)과 그 60초 감시(`wake_unheard`)를 지웠다. 대신 `end_unhooked_turns`가 증거로 사건을 만든다. 턴 상태인 Claude 노드의 기록 파일이 지금 턴이 시작된 뒤(상태 기계가 턴으로 바꾼 시각, `Graph::turn_began`. `agent_states.changed_ns`에 나노초로 적어 데몬이 다시 시작해도 남고, 기록 파일 시각과 그대로 비교한다. 앞 판은 초 단위라 같은 초 안의 앞뒤를 가리지 못했다: 내림이면 깨우기 전 기록을 증거로 보고, 올림이면 첫 초 안에 끝난 턴을 놓쳤다(2026-10-26 검토자 2·3회차))에 바뀌었고, 그 뒤 `STOP_HOOK_GRACE`(60초) 넘게 그대로이고, 마지막 대화 줄이 턴 끝이며(턴 끝 다시 띄우기가 걸린 노드는 Esc로 끊은 턴도 본다), 화면에 도는 턴이 없으면 데몬이 `noIdleWait`를 남기고 `turnEnded`를 적용한다. Cursor는 기록 파일 대신 턴 끝 답 글(`afterAgentResponse`) 뒤 `STOP_HOOK_GRACE` 동안 꺼내기 훅(`/api/agent/take`)도 턴 끝도 없음을 본다(2026-10-26 검토자: 옛 `IDLE_GRACE` 감시를 지운 뒤 Cursor에는 증거가 없었다). 턴 시작보다 오래된 기록 파일은 앞 턴의 끝이라 증거가 아니다(2026-10-26 R32 4단계 시험 데몬: 메일이 깨운 Claude 노드를 같은 초에 듣지 못함으로 바꿨다). 노드는 듣지 못함이 되고 위와 같이 다시 띄운다. 이 검사는 재우기 검사와 같은 고리(`watch_sleep`)에서 사건마다 돈다: 메일함 변화, 사람 입력, 에이전트 상태 바뀜, 화면 멈춤(`SCREEN_QUIET` 뒤), Cursor 답 글. 기록 파일이나 답 글이 아직 `STOP_HOOK_GRACE`보다 젊으면 고리는 그 끝 시각에 한 번 더 깬다. 지금 턴의 증거가 아직 없는 노드는 화면이 멈춘 시각 + `STOP_HOOK_GRACE`에 한 번 더 본다(`Sleeps::settled`, 멈춤 하나에 한 번). 화면이 멈춘 뒤에야 기록 파일에 마지막 쓰기가 오면 화면 사건이 더 없기 때문이다(2026-10-26 검토자 3회차). 파일 감시와 주기 검사는 두지 않는다.
- 다시 띄운 세션의 첫 입력: 「다시 띄우기」(에이전트-실행.md).
- 남은 시각 규칙: `STOP_HOOK_GRACE`(위 증거), 재우기의 `DONE_GRACE`, 옛 프로세스 끝을 기다리는 `EXIT_WAIT`. 앞 둘은 정해진 간격으로 훑지 않고 끝나는 시각 하나를 기다리며, 끝나면 상태(`deaf`, `asleep`)로 보인다. `EXIT_WAIT`는 `relaunchFailed`로 보인다. 3단계가 기본 훅으로 증거 검사를 없앤다.

## 사람 응답 대기

에이전트가 묻는 방법(누구에게, 어떤 한 줄 꼴로)은 내장 스킬 [ask-human](../../skills/ask-human/SKILL.md)이 정한다(「내장 스킬」). 노드가 사람의 답·승인을 기다리면 화면에 알린다(목업 [human-question.html](../mockups/human-question.html) v3, 2026-10-21 사람 지시 "에이전트가 사람에게 승인 또는 선택을 하게끔 하는 질문을 loom 시스템에서 표준화"). 표준은 하나다. 규칙·구조를 바꾸는 질문은 안마다 「지금 → 바꾼 뒤」 예를 하나 붙인다. 보고서·목업은 결정마다 권장, 사람에게 달라지는 것, 비용, 위험, 되돌리는 길을 한 곳에 둔다(2026-10-24 Q858 사람 지시 "보고서와 목업은 사람의 빠르고 정확한 의사결정을 최대한 도와주는 방식으로 작성되어야 한다", Q859에서 안마다 예를 기각하지 않음. 그날 답 26개 중 8개가 예 없는 규칙 질문의 되묻기였다). 보고서 첫 절은 답 한 문장과 정할 수를 주고, 제목은 결론으로 시작하고, 절마다 `정할 것`·`반영함`을 단다. 근거는 셋까지, 사람이 따라가 볼 수 있는 사실로 쓰고, 지금 상태가 있으면 안에 `지금 그대로`를 넣는다. 근거 셋·안 넷 상한은 출처가 아니라 loom이 정했다: 첫 화면에서 다 읽는 수다(2026-10-24 Q869 사람 지시 "의사결정권자를 위한 문서 작성법을 조사해서 스킬을 개선하라". 출처: BLUF, Minto, completed staff work, 정부 결정 메모, Google 설계 문서, Tufte, NN/g, Bezos 한 방향 문. 보고서 R22 v1에 사람이 "결론이 뭐고 … 판단 근거가 잘 드러나지 않게" 답했다).

Rust로 옮긴 글 검사가 DOM 규칙과 어긋났기 때문이다(2026-10-23 검토 추적-codex F4, 추적-opus S4, 관문 결정). 옛 표에 남은 글 파일 문서는 열지 않고 목록에도 보이지 않는다. 근거: 2026-10-23 Q687 A(계획 R14). 점검하지 않은 `.md`를 붙이면 사람이 형식 없는 글을 받았다. 데스크톱 링크는 문서를 파일의 기본 앱이 아니라 데몬 주소(`/api/docs/{ID}/`)로 브라우저에서 연다. 화면은 ID와 제목만 받는다. 질문 글 끝의 밑줄 링크 「M25 <제목> ↗」를 누르면(따로 단추가 아니다. 2026-10-21 사람 지시 "문서 링크는 별도 버튼이 아니라 질문텍스트의 하이퍼링크표시+아이콘 으로 표시한다") 데몬이 기계의 기본 브라우저로 그 문서의 데몬 주소(`http://127.0.0.1:<포트>/api/docs/{ID}/`)를 연다(`POST /api/docs/{ID}`). `file://` 탭은 워크트리를 지우면 죽는다. 데스크톱 앱에서도 앱 창이 아니라 브라우저다. 문서 주소는 대기 번호가 아니라 문서 ID다. 대기가 닫혀도, 원본(지운 워크트리의 목업)이 없어도 같은 주소가 열린다(2026-10-23 사람 "왜 내가 목업을 못보나", "클로드 아티팩트처럼 상시 볼 수 있게 하면 안됨/"). 원본이 있으면 원본을 매번 새로 읽어 새 판이 보인다. 원본이 없으면 붙일 때마다 덮어쓴 사본(`<데이터 폴더>/docs/<ID>/<파일 이름>`)을 낸다. 사본은 문서 파일 하나다(user-doc 문서는 HTML 한 파일이다). 옆 파일(그림)은 사본이 없다. 문서 옆 파일은 목업(`docs/mockups` 아래)과 사본의 폴더에서만 낸다. 보고서는 그 파일 하나만 낸다. 보고서 폴더에는 다른 지시와 비밀 파일이 있다. 둘 다 없으면 404와 그 까닭이다. ID와 경로는 `~/.cache/user-doc/ids.tsv` 한 표가 잇는다(`user_doc::doc_file`). 이벤트 콘솔의 질문·완료 줄도 펴면 같은 링크가 있고, 오른쪽 사이드바 [문서] 탭이 표의 모든 문서를 최근에 붙인 순으로 보인다(목업 M13). 문서를 사람의 브라우저에 바로 띄우는 길은 없다(`loom show`는 점검·ID·통과 기록만 한다).

- 지우는 길: 신호가 거둔다. 사람이 받은편지함 줄의 [×](「알림 지우기」, `DELETE /api/waits/{n}`, 그 대기 하나)를 누른다(2026-10-21 사람 지시 "질문 알림 발생하면 제거할 길이 없음"). `loom ask` 질문을 [×]로 닫으면 그 노드에 사람이 보낸 큐 메시지 「Q12 was closed without an answer.」 한 줄이 간다. 에이전트가 오지 않을 답을 기다리지 않는다(2026-10-22 사람 지시 "Q257은 답 없이 닫혔다. 라고만 보내라"). 사람이 그 노드 터미널에 키를 누른다(터미널이 스스로 보내는 초점·커서·마우스 응답은 키가 아니다, `node_host::typed`). 단 `loom ask` 질문은 키로 지우지 않는다: 그 입력이 어느 질문의 답인지 에이전트가 판단해 `loom answered Q12 Q13`으로 그 질문만 지운다. 열린 질문이 하나면 번호를 빼도 된다. 여럿인데 번호를 빼면 거절하고 열린 번호를 알린다(M28: 모두 닫지 않는다)(2026-10-21 사람 지시 "사람이 정말 답변을 했을때만 알림이 제거되도록 알림제거는 사용자 입력을 에이전트가 판단하여 제거하도록 하라". 사람이 다른 말을 쳐서 질문이 두 번 사라졌다). 프로세스가 끝나면 신호의 대기와 질문을 모두 지운다. 다시 띄우면(계정 전환 포함) 신호의 대기만 지우고 질문은 남긴다(「다시 띄우기」).
- 턴 끝 검사: 사람이 띄운 노드가 사람 입력(TUI 입력, 받은편지함 답)을 받은 턴에 글을 쓰고, 사람 응답 대기 없이, 마지막 입력 뒤 `loom done`도 부르지 않고 턴을 끝내면 한 번 다시 일하게 한다(`daemon::turn_end`). 넘기는 글은 하나다: 사람에게 묻는 글이면 `loom ask`, 쓸 수 있는 결과면 `loom done --asked`, 아니면 지금 하는 일이나 상황을 짧은 낱말 몇 개로만 사람의 말로 답한다. 검사 이름은 붙이지 않는다(2026-10-22 사람 지시 "턴 끝 명시하지 말고, 그냥 현재 너의 작업 또는 상황을 브리핑하는 짧은 단어로 명해"). 빈 글은 글이 없는 것으로 본다. 받은편지함에는 걸지 않는다. 다시 일한 턴과 사람 입력 없이 시작한 턴(백그라운드 작업 알림, 자식 메시지)은 검사하지 않는다. 그런 턴마다 깨워 짧은 답 턴이 끝없이 붙었다(2026-10-22 사람 지시 "이거 뜨는 근본 원인 해결하라"). 근거: 물음표로 끝나는 문장만 보던 검사(2026-10-21 승인)는 물음표 없이 고르게 하는 글을 놓쳐 사람이 「질문 알림이 안 떴다」고 보고했다. 2026-10-22 사람 결정 Q334 A로 글 검사를 지우고 이 규칙으로 바꿨다.

- Cursor 질문 창(AskQuestion): 사람은 `loom ask`로만 답한다(2026-10-24 사람 지시 "커서의 질문도 지금 같은 자체 질문 방식이 아닌 loom의 방식을 따르도록 강제하라"). 총괄 Cursor 노드가 이 창으로 물었고, 사람은 받은편지함 밖에서 답했다. 그래서 loom에 기록이 없었다. loom은 노드 터미널에 키를 치지 않고 Cursor 훅으로만 일한다(Q770 B). 훅은 창을 막지도 닫지도 못한다: Cursor는 AskQuestion에 preToolUse·postToolUse를 부르지 않는다(아래 2026-10-24 실측). 그래서 창은 전처럼 사람을 기다리고, 화면 대기(`Screen`)가 받은편지함에 뜬다. 두 가지로 `loom ask`를 쓰게 한다. ① Cursor 사용법 끝 문장: AskQuestion을 쓰지 말고 `loom ask`로 물으라. ② stop 훅이 대화 기록(`transcript_path`)의 마지막 턴에서 AskQuestion 호출을 찾으면(`cursor::used_question_box`) 데몬에 알린다(`/api/agent/question-box`). 턴 끝 검사가 같은 질문을 `loom ask`로 다시 물으라는 글로 한 번 다시 일하게 한다(`TurnCheck::QuestionBox`, 이벤트 `nudged`). 자식 노드와 loom 동사를 부른 턴도 대상이다. 같은 턴에 `loom ask`로 물었으면 다시 일하게 하지 않는다. 훅은 기록 전체를 줄씩 읽는다(긴 턴의 앞 호출도 찾는다). 새 프로세스(`App::launch`)는 노드의 두 표시를 지운다. 턴 끝 전에 끝난 프로세스의 `loom ask`가 새 프로세스의 창을 덮지 않는다. Windows 데몬의 WSL 노드는 Windows 훅이 돈다. 그래서 기록 경로를 훅의 작업 폴더(`\\wsl.localhost\…`)로 바꿔 읽는다(`wsl::from_node`).

## 맥락과 크기

- 자식은 새 맥락에서 시작한다. 지시문(4KB 이하)과 부모 이름만 받는다. 부모 대화를 넘기는 fork는 두지 않는다.
- 에이전트 자식(`--role`)은 카탈로그의 `prompt` 방법으로 지시문을 시작 명령에 받는다. 쉬는 상태로 뜬 TUI는 지시문을 읽을 턴이 없기 때문이다.
- `-- <명령>`으로 띄운 자식은 지시문을 메일함의 첫 메시지(보낸 노드는 부모)로 받는다. 자식은 `loom wait`로 읽는다.
- `loom note`·`ask`·`answer` 본문도 4KB 이하다. 4KB를 넘는 자료는 파일에 쓰고 경로를 적는다.
- `loom done` 요약은 1KB 이하다. 더 길면 `--file`을 쓰고 부모에게는 경로만 간다.
- 완료 통지는 일반 메일함 상한을 넘어도 넣는다. 일반 메시지가 완료 보고를 막지 않는다.
- `done` 없이 PTY가 끝나면 부모 메일함에 종류 `exited`(칸 `node`, `code`) 메시지만 넣는다. 설정 스크립트가 실패했으면 종류 `setup-failed`와 출력 끝을 넣는다(「저장소와 워크트리」). 부모가 없으면 보관한다. 이 줄은 메일함 상한을 넘어도 넣는다.
- 재시작 뒤 복구하지 못한 미완료 노드는 같은 경로로 `exited`(코드 `unknown`)를 알린다. 반복 검사로 중복 통지를 만들지 않는다.

## 작업 폴더

출력 표준 R8 v5 3단계(2026-10-23 사람 승인)다. 브리프·결과·결함 파일·병합 기록이 `~/.cache/loom-briefs`, `~/.cache/loom-results`, `<공유 git 폴더>/loom-gate/`에 흩어져 있었고, 위치는 스킬 글에만 있었다. 그래서 loom이 작업마다 폴더 하나를 만들고 그 경로를 노드 환경에 넣는다. 코드는 [src/task.rs](../../src/task.rs)다.

| 정한 것 | 근거 |
|---|---|
| `loom spawn`이 `~/.cache/loom/<작업>/`에 `brief.md`(받은 지시문), 빈 `result.md`, `review/`, `logs/`를 만들고 자식 환경에 `LOOM_TASK_DIR`로 넣는다. 그래프가 자식을 받은 뒤, 띄우기 바로 전에 만든다. 이미 있는 파일은 덮지 않는다 | 같은 작업의 둘째 자식(검토자)이 첫 브리프와 결과를 지우지 않게 한다 |
| 폴더 이름은 데몬이 띄울 때 한 번 정한다: `<저장소 폴더 이름>-<브랜치>`(`--worktree` 자식), `<저장소 폴더 이름>-<노드 이름>`(에이전트를 사람이 띄운 노드). 그 이름의 폴더가 이미 있으면 `-2`, `-3`…을 붙인다. 정한 이름은 노드 줄(`nodes.task`)에 남는다. `--worktree` 없는 자식은 부모의 폴더를 물려받는다 | 브랜치 글을 나중에 다시 풀어 폴더를 찾지 않는다. 병합 뒤 같은 브랜치 이름을 다시 써도, `feat/x`와 `feat-x`가 같은 글이 돼도 새 작업은 앞 작업의 파일을 물려받지 않는다. 이름을 바꾸거나 입양해도, 다시 띄워도 폴더가 그대로다 |
| 폴더 이름은 한 단계다. `/`(와 `\`, `:`)는 `-`다. 모든 작업 폴더가 `~/.cache/loom/` 바로 아래에 나란히 있다 | 폴더 이름이 경로를 벗어나지 못한다. 폴더 찾기는 이름이 아니라 데몬의 `nodes.task`가 한다(아래 「작업 폴더 묻기」 줄) |
| WSL 노드는 그 배포판 홈의 Linux 경로, Windows 노드는 Windows 경로(`%USERPROFILE%\.cache\loom\…`)를 받는다. Windows 데몬은 WSL 폴더를 UNC 경로로 만든다 | 노드 안의 에이전트가 그 경로를 그대로 연다. WSL의 `loom.exe`는 같은 배포판의 UNC 경로로 바꿔 읽는다(`wsl::from_caller`) |
| 에이전트를 사람이 띄운 노드도 `LOOM_TASK_DIR`을 받는다. 폴더 이름은 노드를 더하기 전에 다음 노드 이름(`next_root_name`)으로 정해 `add_root`가 남긴다. 셸·명령 노드는 처음에 폴더가 없다(`task` 없음). 데몬이 처음 물을 때 만든다 | 이름을 바꿔도 폴더가 그대로다. 셸은 파일을 쓸 일이 거의 없어 빈 폴더를 남기지 않는다 |
| `loom relaunch`·계정 전환으로 다시 띄운 노드(자식도, 사람이 띄운 노드도)는 남은 `nodes.task`의 폴더를 `LOOM_TASK_DIR`로 받는다. 작업 폴더 전의 노드는 이때 처음 폴더를 받는다 | 옛 노드도 다시 띄우면 기본 경로를 쓴다 |
| `loom spawn`은 지시문이 있으면 머리 `Goal`, `Facts`, `Scope`, `Done when`, `Checks`, `Time`을 본다. 머리는 `<머리>:`로 시작하는 줄이나 그 낱말의 ATX 제목(`## Goal`, 닫는 `#`와 탭도 된다)이다. 굵은 글·목록 꼴은 아니다. 빠지면 빠진 머리를 적어 거절한다. 지시문 없는 `loom spawn`은 받는다 | o-mode 브리프 틀을 글이 아니라 검사로 지킨다. 거절 글이 받는 꼴을 알린다 |
| `loom done --file`의 상대 경로는 부른 노드의 작업 폴더 기준이다. `loom verdict`에 `--findings`가 없으면 부른 노드 자기 작업 폴더의 `review/<브랜치>-<내 노드 이름>.md`를 쓴다(검토자는 `--worktree` 없이 떠 관문의 폴더를 물려받는다. 한 관문 아래 브랜치가 여럿이라 브랜치 이름을 붙인다). 그 파일이 없으면 pass는 결함 파일 없이 가고 block은 그 경로를 적어 거절한다. 병합 큐의 기록은 `<공유 git 폴더>/loom-logs/batch-<묶음>-<단계>.log`(검사)와 `batch-<묶음>-publish.log`(게시·배포 확인)다. 묶음 번호는 다시 쓰지 않는다. 결과 메시지의 `log` 칸이 그 경로다 | 병합 기록 자리가 WSL 에이전트와 Windows 데몬에 모두 닿아야 한다. 데몬이 쓰므로 노드의 작업 폴더가 아니라 저장소 쪽에 둔다. 결함 파일은 브랜치 이름이 아니라 검토자 자신의 폴더에서 찾아 브랜치 이름을 바꿔도 깨지지 않는다 |
| 작업 폴더 묻기: CLI는 환경의 `LOOM_TASK_DIR`을 믿지 않고 데몬의 `/api/agent/task`에 묻는다(`branch` 없음: 부른 노드, 있음: 그 브랜치 담당). 응답은 데몬이 쓰는 꼴의 경로다(WSL 폴더는 UNC). 이 길은 노드 문에 있어야 한다(`every_agent_route_the_cli_calls_is_on_the_node_door` 시험이 지킨다). 환경이 없는 노드(작업 폴더 전에 뜬 노드)와 Windows `loom.exe`도 같다 | 홈을 짐작하지 않는다. WSL의 `loom.exe`에는 배포판의 `HOME`이 없다 |
| 보존 기한은 따로 없다. 옛 `~/.cache/loom-briefs`, `~/.cache/loom-results`는 읽기만 한다 | 흔적 보존은 이벤트 상한이 정한다 |

## 병합 관문

관문 글을 손으로 쓰자 받는 곳이 틀리고(READY가 총괄에게 감), 형식이 갈리고, 흔적 없는 병합이 생겼다. 그래서 관문 일을 하는 명령이 보고도 한다(출력 표준 R8 v5 1단계, 2026-10-23 사람 결정 Q559 A). 상태·전이·보내는 쪽·받는 쪽·관문 낱말·audit·스크립트 계약은 [src/protocol.rs](../../src/protocol.rs) 한 곳에만 둔다. 상태 저장과 흔적은 `src/graph/gate.rs`, git 확인은 `src/daemon/gate.rs`, 병합 큐는 `src/daemon/queue.rs`가 맡는다. 에이전트 절차는 [o-mode "Merge and cleanup"](../../skills/o-mode/SKILL.md#merge-and-cleanup)에 있다.
관문 스크립트(`scripts/gate/check.sh`)가 없는 저장소에서도 `loom ready`는 `ready` 종류로 관문에 간다. 상태와 audit은 없다. 관문은 손으로 병합하고 `loom done`으로 알린다.

- 관문 고르기(2026-10-23 사람 결정 Q692 A, 2026-10-24 Q851 A로 구조 규칙): 데몬은 역할 이름을 보지 않는다. `loom spawn --worktree`는 부모 워크트리의 `HEAD`에서 가른다. 관문과 대상은 적어 두지 않고 `loom ready` 때 지금의 부모 관계에서 계산한다(`daemon::gate` `gate_of`, 2026-10-26 사람 결정 "DB 관계만 원천이다, 파생 값은 쓸 때 계산한다"). 부모가 있으면 데몬은 부모 워크트리의 지금 브랜치를 본다. 그 브랜치가 원래 체크아웃의 브랜치가 아니면 부모가 관문이고 대상은 그 브랜치다. 그래서 `loom adopt`, `loom rm`, `loom detach` 뒤에는 새 부모를 따른다. 옛 판은 spawn 때 부모 브랜치를 `nodes.branched_from`에 적어 부모가 뒤에 브랜치를 바꿔도 대상을 그대로 두었다(검토 F2). 그 복사본은 관계가 바뀌면 틀려져서 이 규칙으로 없앴다(DB 마지막 단계가 열을 지운다). 아니면(부모 없음, 부모가 원래 체크아웃의 브랜치에 있음, 부모가 다른 저장소에 있음) 담당 자신이 관문이고 대상은 원래 체크아웃의 브랜치다. 부모와 같은 워크트리를 쓰는 노드는 대상과 같은 브랜치라 `sameAsTarget`으로 거절된다. 차례의 대상 종류는 저장한 관문이 담당이 아닌지로 정한다(`graph::gate` `target_kind`). 그래서 `loom adopt` 뒤에도 그 차례는 옛 관문이 판정한다(검토 F3). DB 38단계는 옛 자료의 규칙이라 그대로 둔다. DB 40단계는 묶음 없는 `merging` 차례(옛 CI 관문의 고아 차례)를 담당에게 준다. 원래 체크아웃이 대상이면 판정은 관문이 `loom spawn --role <역할> --review <브랜치>`로 띄운 그 브랜치의 검토자(관문의 자식, `nodes.review`)만 한다. `--review`는 부른 노드가 관문인 차례가 있는 브랜치만 받는다(`noRound`, `notGate`). `loom verdict`는 `--review` 없는 노드와 다른 브랜치의 검토자를 거절한다(`notReviewer`, 2026-10-24 코디 결정 #4460, 검토 R632-3). 담당은 판정하지 못한다. 원래 체크아웃이 대상이면 관문 자신도 판정하지 못한다. 상주하는 CI 담당자는 없앴다: 관문 노드 하나가 모든 브랜치를 기다리며 맥락을 쌓았다.
- 검토는 main 앞 한 번이다(2026-10-24 사람 결정 Q785~Q787 A): 부모 브랜치에서 만든 브랜치(코디 밑 워커 브랜치)는 검토자가 없다. 관문인 부모가 결과를 브리프의 완료 조건과 대조해 받아들이고(코드 검토가 아니다) `loom verdict`를 부른다. pass는 코디 브랜치 큐에 세운다. block은 결함 파일에 완료 조건에서 빠진 것을 적는다. 그 브랜치의 `--review`와 다른 노드의 판정은 `coordinatorAccepts`로 거절한다. 코디 브랜치를 포함한 원래 체크아웃 대상 브랜치는 `--review` 검토자를 그대로 받는다. 코디는 독립 검토자가 아니므로 받아들이기만 하고 검토하지 않는다. 앞서 Q784에서 사람은 C(코디 브랜치가 검토 없이 main 큐에 선다)를 골랐다. 그러나 코디가 직접 쓴 코드가 검토 없이 main에 갈 수 있어 Q785~Q787에서 이 규칙으로 바꿨다. 「검토하지 않은 변경」을 기계로 따로 보는 검사는 두지 않는다(Q784에서 A안 거절). 근거: 둘째 층은 이미 합친 같은 코드를 다시 검토했다. 2026-10-24 병합큐 작업은 두 층을 차례로 여러 번 돌았고, 한 바퀴에 20~30분이 걸렸다.
- 병합 큐(2026-10-23 사람 결정 Q697 A, 총괄 #3761): pass 판정이 브랜치를 큐에 세운다. 데몬 작업 하나가 대상마다 큐 전체를 묶음 하나로 끝낸다. 큐 작업은 pass 판정과 그래프의 노드 바뀜(`Graph::changes`: 검토자가 끝나거나 지워지면 차례가 풀린다)에 깬다. 앞 판의 60초 깨우기(`TICK`)는 지웠다. DB 오류로 멈춘 차례는 다음 사건에 다시 돈다. 임시 워크트리(`<공유 git 폴더>/loom-batches/batch-<묶음>-<단계>`)에서 대상 위에 큐 순서로 `--no-ff` 병합하고 check.sh를 한 번 돌린다. 지나면 원래 체크아웃이면 대상을 묶음 끝으로 옮기고 그 커밋을 push한 뒤 ship.sh가 배포를 확인한다. 코디 브랜치면 코디 워크트리가 깨끗할 때만 빨리 감는다. 미커밋 변경이 있으면 반려다. 쌓다가 충돌하면 그 브랜치는 반려되고 나머지로 다시 쌓는다. 근거: 전경 `loom merge`가 12분 넘게 셸을 막아 그동안 메일이 쌓였고, 브랜치마다 검사를 따로 돌렸다.
  - 모든 관문 동사는 바로 돌아온다. 결과는 `merged`·`rework`·`failed` 메시지다. `loom merge`는 없앴다.
  - 묶음에 드는 때: pass를 받았고, 이 브랜치의 검토자가 모두 끝났다. 이 브랜치의 검토자는 관문의 산 자식(잠든 노드 포함) 가운데 담당이 아니고 `--review <이 브랜치>`로 뜬 노드다. 끝남은 담당의 마지막 ready 뒤 이 브랜치 판정이다. 담당이 다시 ready를 부르면 데몬이 그 검토자들에게 새 차례(`ready`)를 보내고, 모두 다시 판정해야 묶인다. 판정 없이 끝난 검토자는 세지 않는다. 검토자를 둘 두는 브랜치(고위험, Q995 C)면 관문은 둘째 검토자를 첫 판정 전에 띄운다(검토 B1·B1'). pass 뒤에도 남은 검토자가 있으면 pass 메시지가 그 이름과 `loom rm` 길을 알린다(검토 S7). 앞 판은 차례 번호와 판정 흔적으로 검토자를 짐작했고, 검토마다 새 빈틈이 나왔다(검토 B1', R632-3 세 번). 그래서 짐작을 지우고 띄울 때 묶는다.
  - 큐 순서는 첫 pass 순서다(`seq`). 초 단위 시각은 같은 초의 두 pass를 가르지 못한다(검토 R6).
  - 검사는 호스트에서 한 번에 하나다(`/tmp/loom-gate-check.lock`의 `flock`). check.sh가 남긴 자식은 잠금을 쥐지 않는다. cargo 빌드는 공유 폴더의 `loom-batch-target`을 다시 쓴다.
  - check.sh는 메모리 여유(dev-toolbox `capacity.py`의 `headroomMiB`)가 2×5GiB 이상이면 cargo 단계를 두 갈래로 함께 돌린다: Linux 갈래(clippy, test, 주석 시험)와 Windows 갈래(clippy, test). 아니면 앞처럼 차례로 돌린다. 단계마다 `memcap -m 5G`와 여유 확인(40분까지 기다림)은 그대로다. 갈래마다 출력을 따로 모아 둘 다 끝난 뒤 차례로 적고, 실패한 갈래 이름을 적는다. Windows 갈래는 `<target>/windows-gate`에 빌드한다: 한 target 폴더에서는 cargo의 빌드 폴더 잠금이 두 빌드를 차례로 돌렸다(2026-10-25 실측, 「Blocking waiting for file lock on build directory」). 근거: 구조 개선 보고서 R27 ④ A안. 묶음 검사의 대부분이 차례로 도는 두 cargo 갈래였다.
  - 이분 탐색 책임 규칙: 묶음의 모든 시도는 처음 읽은 대상 커밋 위에 쌓는다(검사 중에 대상이 움직여도 같다, 검토 S6). 묶음이 실패하면 앞 절반을 대상 위에 쌓아 검사한다. 지난 앞쪽은 지난 것으로 두고, 실패를 더하는 첫 브랜치 하나를 찾는다. 그 브랜치만 반려되고 나머지는 처음 큐 자리로 다시 선다. 검사는 많아야 1 + ceil(log2 n)번이다. 여러 브랜치가 함께 있어야만 깨지면 그 가운데 뒤에 쌓인 브랜치가 반려된다.
  - 흔들리는 검사의 위험: 검사가 가끔 실패하면 이분 탐색이 죄 없는 브랜치 하나를 반려한다. 다시 지나면 그 브랜치는 다시 `loom ready`로 큐에 선다. 같은 실패가 되풀이되면 검사를 고칠 일이다. 묶음 흔적(`batch` 이벤트)에 단계마다 결과와 기록 파일이 있다.
  - 앞 브랜치가 이미 품은 브랜치는 병합하지 않는다. 그 브랜치는 품은 병합 커밋으로 `merged`다. ship.sh는 자기 병합이 있는 마지막 브랜치를 받는다(검토 S5).
  - 원래 체크아웃의 대상에 원격에 없는 커밋이 있으면 검사 전에 묶음은 `failed`다(검토자2 B1). 대상이 움직여 다시 서는 일이 한 대상에서 3번 이어지면 묶음은 `failed`다: 조용히 검사만 되풀이하며 다른 대상을 굶기지 않게 한다.
  - 검사가 지난 뒤와 남은 묶음의 게시를 이을 때(대상이 아직 묶음 끝을 담지 않았으면) audit를 다시 돈다. 브랜치가 움직였거나 담당 워크트리가 검토한 커밋에 있지 않거나 추적 파일에 미커밋 변경이 있으면(`SourceDirty`) 그 브랜치는 반려되고 나머지는 큐에 다시 선다. 담당 워크트리가 없으면 보지 않는다(검토 R632-1·R632-4). 이어 게시할 묶음 끝이 원격에 없는데 원래 체크아웃의 대상이 이미 그 끝이면, audit 전에 비교 교환(`git update-ref`)으로 처음 커밋으로 돌린다. 대상이 끝을 지나 움직였거나 추적 파일이 깨끗하지 않으면 돌리지 않고, 묶음을 「<대상> needs repair」와 처음·끝 커밋으로 `failed`로 끝낸다(루트가 받는다). 묶음 줄은 남기지 않는다: 남기면 다음 깸이 같은 일을 되풀이한다(검토 R3-1).
  - push가 실패했는데 다시 fetch한 원격이 그대로면 묶음은 `failed`다(원인과 기록 파일). 원격이 움직였으면 큐에 다시 선다. push 실패 뒤 대상은 작업 폴더의 추적 파일이 깨끗하고 대상이 아직 묶음 끝일 때만(`git update-ref` 비교 교환) 처음 커밋으로 돌린다. 아니면 그대로 두고 대상이 움직였다고 알린다(검토 R632-2). 묶음 끝이 원격에 오른 뒤 ship.sh가 실패하면 `merged`에 「deploy: unknown」과 원인을 단다(검토 S2·S6). push는 검사한 커밋(`<끝>:refs/heads/<대상>`)을 보낸다. 빨리 감기 뒤 브랜치가 그 커밋이 아니면 게시하지 않는다(검토 R1).
  - 데몬이 묶음 중에 끝나면 `batches` 줄이 남는다. 브랜치의 끝 상태를 쓰지 못해도 줄이 남는다(검토 R3). 큐는 깰 때마다 남은 줄을 거둔다: 임시 워크트리를 지우고, 검사 전이면 그 브랜치들을 큐에 다시 세우고, 검사를 지났으면 게시를 잇는다(게시는 다시 불러도 된다). `host.sh`가 배포를 확인하는 동안 사람의 데몬을 다시 띄우는 길이 이것이다. 게시(fetch, 빨리 감기, push, 되돌리기)는 큐의 PUBLISH 하나가 맡는다. ship.sh는 묶음 끝이 원격에 있는지 보고 배포만 확인한다(검토 R632 랩터-3).
  - 받는 곳: 결과는 담당과 관문이 받는다. 대상이 원래 체크아웃일 때만 루트가 `merged`·`failed` 사본을 받는다(코디 #3883 (1)). 묶음 시작과 다시 세우기는 알리지 않는다. 대상 종류는 관문이 담당의 부모인지로 정한다: 옛 CI 담당자가 관문인 줄도 원래 체크아웃이 대상이라 루트가 받는다(검토 N5).
  - 흔적: 검사마다 `batch` 이벤트 하나(묶음 번호, 대상, 단계, 쌓은 브랜치와 브랜치마다 기다린 초, 검사 초, 결과, 기록 파일).
  - 임시 워크트리 경로는 묶음·단계마다 다르다. 끝난 데몬의 스크립트가 검사 뒤 끝 덫으로 자기 경로만 지운다. 같은 경로면 새 묶음의 워크트리를 지워 거짓 반려가 났다(검토 S1·R2).
  - 마이그레이션 38은 옛 pass·병합 중 줄과, 관문이 새 규칙의 관문이 아닌 ready 줄(옛 CI 담당자)을 묶음 없는 `merging`으로 둔다. 데몬이 시작할 때 그 줄을 `failed`로 끝내고 담당·관문에 「loom upgrade: send loom ready again」을 보낸다. 큐에 세우면 오래 버린 차례의 검토한 커밋을 병합할 수 있다(검토 S4·R4·R5). 같은 마이그레이션이 `nodes.review`를 더한다. 옛 검토자 노드는 값이 없어 판정하지 못한다: 관문이 `--review`로 다시 띄운다.
- 대상 포함 검사를 없앴다(코디 #3889 (8)): `loom ready`는 브랜치가 대상을 담지 않아도 받는다. 큐가 지금 대상 위에 쌓으므로 충돌만 반려한다. 근거: 거절 8건 뒤 워커가 main을 손으로 병합했다. 미커밋 변경과 판정 뒤 브랜치 이동(`HeadMoved`)은 그대로 막는다.
- 검토자 자리(R17 ⑤, Q789 A): 검토자는 브랜치·역할마다 한 자리다. 같은 관문·브랜치·역할의 검토자가 있으면 `loom spawn --review`를 거절한다(`Refusal::ReviewerSeated`). 프로세스가 끝난 검토자도 자리를 지킨다: 관문이 `loom relaunch`로 다시 띄운다. 이름은 데몬이 `<역할> <브랜치>`로 짓는다. 근거: 규칙 글만 있을 때 브랜치 20개에 검토자 46개가 떴고, 1+1을 넘는 노드가 10개(약 54만 토큰)였다.
- 병합 뒤 회수(R17 ⑥, Q789 A): `merged` 뒤 데몬이 큐 밖의 작업에서 그 브랜치의 검토자, 담당 노드, 깨끗한 워크트리, 로컬·원격 브랜치를 지운다. 노드 프로세스를 먼저 끝내고 폴더를 지운다. 원래 체크아웃, 다른 노드가 쓰는 워크트리(코디 워크트리를 쓰는 워커), 부모 없는 담당, 자식이 있는 담당은 남는다. 변경이 남은 워크트리는 워크트리·브랜치·담당을 남기고 담당의 부모에게 알린다. 담당 혼자 쓰는 워크트리가 다른 브랜치로 바뀌었거나 브랜치에 대상에 없는 커밋이 생겼어도 같다. 워크트리는 `--force` 없이 지운다: 검사 뒤에 생긴 변경은 git이 거절하고, 그때도 워크트리·브랜치를 남긴다. 원격 브랜치는 마지막으로 본 커밋을 조건(`--force-with-lease`)으로 지운다. 원격이 그 뒤에 움직였으면 원격 브랜치를 남기고 알린다(검토 F1~F2, B1). 근거: `merged`를 받은 담당 21개 중 8개가 5분 넘게 남았고(가장 긴 것 665분), 에이전트가 친 회수 명령이 약 1,560개였다.
- 검토 중단(코디 #3889 (7)): 차례가 판정·병합 전에 `working`·`failed`로 돌아가면(block, 큐의 반려, `loom fail`) 데몬이 그 차례의 검토자에게 `withdrawn`(칸 `branch`, `head`)을 보낸다. 받는 노드는 위 「묶음에 드는 때」의 이 브랜치 검토자 가운데 부른 노드가 아닌 노드다. 담당의 ready만 차례를 가른다(검토 N1·R7). 메시지 연동이 있는 에이전트는 조정으로 받는다. 다른 브랜치의 검토자는 받지 않는다(`--review`). 판정 전 담당의 새 커밋은 데몬이 보지 못한다. 큐의 audit가 `HeadMoved`로 반려할 때 알린다. `withdrawn` 본문은 받는 검토자에게 지금까지 찾은 결함을 자기 결함 파일에 적고 멈추라고 한다. 그 파일은 다음 차례에 다른 검토자에게 간다.
- 검토 공유(2026-10-24 사람 지시 "검토자끼리는 서로 자신이 찾은 결함 및 수정사항을 공유하여 중복 검토 하지 않도록 하라", "검토자가 수정사항을 발견하면 바로 다른 검토자에게 리포트해서 중복검토를 하지 않도록 하라"): 한 브랜치의 검토자는 결함을 찾으면 바로 다른 검토자에게 `loom note <검토자> --steer`로 보낸다. 받은 결함은 다시 보지 않는다. 판정은 검토자마다 따로 한다.
  - 조정은 부모·자식 사이에 더해 같은 관문·같은 `--review` 브랜치의 검토자끼리도 간다(`mailbox::steerable`). 중단은 그대로 부모·자식 사이만 간다.
  - 검토자의 결함 파일은 그 검토자가 이 브랜치의 마지막 판정에 준 파일이다(`--findings`). 없으면 기본 이름(`task::findings`, `review/<브랜치>-<검토자 이름>.md`)이다. 검토자는 관문의 작업 폴더를 같이 쓰므로 기본 이름은 `$LOOM_TASK_DIR/review/…`로 적는다. 메시지 세 가지(소개, 새 차례, `withdrawn`)가 같은 규칙(`findings_of`)을 쓴다(검토 F2).
  - 둘째 검토자가 뜨면(`loom spawn --review`) 데몬이 새 검토자에게 먼저 뜬 검토자들의 이름과 결함 파일을, 먼저 뜬 검토자에게 새 검토자의 이름과 결함 파일을 메모로 보낸다. 일하는 검토자는 조정으로 받는다(`Graph::introduce_reviewer`).
  - 새 차례(`ready`)의 본문은 다른 검토자의 이름과 결함 파일, 자기 결함 파일, 고친 범위 `git log <마지막으로 판정한 커밋>..<새 커밋>`을 적는다. 마지막 판정은 그 검토자의 이 브랜치 `verdict` 흔적이다. 검토자는 그 범위만 다시 본다. 판정한 적이 없으면(판정 전에 거둬졌으면) 브랜치 전체를 본다. 거둔 검토자는 브랜치 일부만 보았을 수 있기 때문이다(검토 F1). 근거: 2026-10-24 둘째 차례에서 두 검토자가 diff 전체를 다시 읽었고, 한쪽이 다른 쪽이 이미 낸 결함을 다시 찾았다. 거둔 검토자의 결함은 사라졌다.

남은 위험: 묶음 끝을 push한 뒤 배포 확인 15분 동안 큐가 기다린다. 그동안 다른 대상의 묶음도 기다린다. 데몬이 죽어도 check.sh는 남아 돌 수 있다. 잠금 때문에 다음 검사는 그 검사가 끝날 때까지 기다린다.
