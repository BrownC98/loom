# Loom 병렬 개발

## 실행 경계

- 이 파일과 [브리프 공통 규칙](agent-rules.md)이 실행 절차의 원천이다. 다른 오케스트레이션 스킬을 상속하지 않는다.
- 사용자가 이 스킬을 켠 노드가 총괄이다. 브리프에서 이 파일을 읽는 자식은 배정된 역할을 유지한다.
- Loom 환경과 다른 터미널 환경 변수가 함께 있어도 Loom으로 배정·통신·감독한다.
- Orca CLI·앱·오케스트레이션 스킬·보조 스크립트를 실행 경로로 쓰지 않는다. Loom 기능이 없다고 그 도구로 우회하지 않는다.
- 다른 제품을 벤치마킹하라는 요청은 비교 조사다. 실행 도구를 바꾸라는 뜻이 아니다. 먼저 제공된 자료와 로컬 소스를 읽는다. 비교 제품의 실행 중인 앱이나 CLI 조작은 사용자가 그 조작을 명시한 경우에만 한다.

## 시작

1. `LOOM_TOKEN`과 `LOOM_URL`의 존재를 확인한다. 토큰 값은 출력하지 않는다. 없으면 노드 생성·통신을 하지 않고 직접 할 수 있는 조사부터 한다.
2. 설치된 `loom --help`, `loom spawn --help`, `loom wait --help`를 읽는다. 소스에 있는 기능을 설치된 기능으로 간주하지 않는다.
3. `status`, `reply`, `wait --reply-to --timeout --json`의 지원 여부를 확인한다. 없으면 그 기능이 필요한 위임을 보류하고 직접 작업한다. 버전 차이를 보고한다. 사용자 데몬을 임의로 교체하지 않는다.
4. `loom status`로 현재 관계와 생존 여부를 확인한다. 중첩 깊이 상한 안에서 직접 작업·직속 워커·코디 구성을 고른다.
5. 저장소 AGENTS.md와 작업 관련 문서를 읽는다. 새 워크트리의 설정 절차와 완료 확인 방법을 브리프에 적는다. `--worktree` 자식은 설정 스크립트가 성공한 뒤 같은 카드에서 뜬다(loom 0.1.332부터).

## 역할과 배정

| 역할 | 책임 | 실행자·모델 |
|---|---|---|
| 총괄 | 범위, 배정, 사용자 승인, 최종 검수, main 병합과 회수 | 현재 세션을 유지한다 |
| 코디 | 작업 하나의 조사, 설계, 목업, 워커 명세와 결과 검수 | Claude, `claude-opus-5-5`, medium |
| 워커 | 정해진 편집 범위의 구현과 검증. 다시 위임하지 않는다 | Claude, `claude-sonnet-5-5`, medium |
| 평가자 | 구현과 별개로 결과·원문·관찰 증거를 평가한다 | Codex, `gpt-6.1-sol`, high |

- 사용자가 지정한 실행자·모델이 표보다 우선한다. 저장 형식, 인증, 동시성, 데이터 손실 경로와 여러 모듈의 계약 변경은 Opus 워커가 맡는다.
- 모델·강도 옵션은 설치된 `loom spawn --help`에 있을 때만 쓴다. 없으면 사용자 설정을 따르며 실제 모델을 보고한다. 임의의 셸 명령으로 에이전트를 띄워 프로필을 우회하지 않는다.
- 강하게 결합된 작은 작업은 직접 한다. 독립된 편집 범위가 둘 이상일 때만 나눈다. 코디의 편집 범위가 하나면 워커를 `--worktree` 없이 코디 워크트리에 띄운다. 새 워크트리는 설정·빌드·병합·회수만 더한다. 워커가 도는 동안 코디는 그 워크트리를 편집·빌드하지 않고 읽기와 검수만 한다. 코디는 같은 제품 결정을 기다리는 조각을 함께 맡는다.
- 새 노드와 브랜치는 한국어로 짓는다. 주소는 이름이나 `'#<노드 번호>'`를 쓴다. 셸에서 `#` 주소는 따옴표로 감싼다.
- 브리프는 `~/.cache/loom-briefs/<작업>-<역할>.md`에 둔다. 목표, 확인된 사실, 가설, 편집 범위, 보존할 계약, 완료 조건, 검사 명령과 시간 예산을 적는다.
- 브리프 마지막 줄은 `- Common rules: <이 스킬 폴더의 절대 경로>/agent-rules.md`다. 자식이 그 파일을 바로 읽게 절대 경로로 쓴다. 브리프와 에이전트 메시지는 영어로 쓴다.

## Loom 명령

| 목적 | 명령·동작 |
|---|---|
| 편집할 자식 생성 | `loom spawn <이름> --agent <agent> --worktree <브랜치> --file <지시 파일>` |
| 같은 워크트리에서 읽기 전용 조사 | `--worktree` 없이 `loom spawn` |
| 긴 브리프 전달 | 지시 파일에 `Read <브리프 절대 경로> and follow it.`을 적는다. 지시문은 4,096바이트 이하다 |
| 진행·도움 요청 | `loom send <부모> "STATUS: …"` 또는 `"ESCALATION: …"` |
| 방향 수정 | `loom steer <자식> <본문>` |
| 작업 중단 | `loom interrupt <자식> "Stop. …"` |
| 완료 보고 | `loom done <요약>` 또는 `loom done --file <결과 경로>` |
| 인계 | 새 총괄에서 `loom adopt <코디 이름>`. 현재 관계와 보관된 메시지를 확인한다 |
| 조치 전파 | 살아 있는 자식마다 `loom send`. 코디는 필요한 조치를 자기 자식에게 전달한다 |
| 실패 후 재배정 | 기존 노드의 종료를 확인하고 새 이름으로 생성한다. 브리프에 보존한 브랜치·결과를 적는다 |

`--worktree`는 부모 워크트리의 `HEAD`에서 갈라진다. 총괄은 기준 체크아웃에서, 코디는 자기 브랜치에서 자식을 만든다. 같은 워크트리에 편집자를 여럿 두지 않는다.

## 목업 승인

- 사람에게 보이는 목업·보고서의 형식, 스타일, 브라우저에 띄우기는 [user-doc](../user-doc/SKILL.md)이 정한다. 아래는 loom 역할만 정한다.
- 화면 작업은 설치된 디자인 점검 스킬(예: `design-stack`)이 있으면 그것으로 점검한다. 코디가 바뀔 구역의 최소 목업을 만든다.
- 코디는 렌더 점검 뒤 경로·판·점검 결과만 보고한다. 사람의 브라우저는 총괄 한 명이 user-doc `show.sh`로 연다. 브리프에 코디의 브라우저 열기를 지시하지 않는다.
- 머리 줄의 `응답할 곳`은 총괄이다. 사람은 그 노드의 대화에 승인이나 수정을 전한다.
- 사용자 승인 전에는 화면 제품 코드를 쓰거나 구현 워커를 띄우지 않는다. 승인할 판과 남은 결정을 구체적으로 제시한다.
- 사용자의 승인 판·경로·내용을 구현 브리프에 적는다. 승인 대기 중인 노드와 워크트리는 유지한다.

## 사용자 보고서

- HTML 보고서는 사람이 보고서를 명시해 요청할 때만 만든다(2026-10-21 사용자 지시 "보고서는 내가 명시하지 않으면 굳이 쓰지 않도록 한다"). 그 밖의 결과·진행·정할 것은 작업 뒤 터미널에 항목마다 문제·원인·해결 세 줄로 짧게 알리고, 할 일이 뻔하면 바로 다음 일을 한다("할일이 뻔한건 보고서 일일이 작성하지말고 그냥 진행해"). 목업 승인은 이 규칙과 별개로 그대로 한다.
- 만드는 보고서(조사·설계·비교·결과)는 user-doc 형식의 HTML로 만든다(2026-10-21 사용자 지시 "앞으로 보고서는 html 형식으로 제공해"). 채팅·`loom done`에는 한국어 요약과 그 파일 링크만 적는다. 에이전트끼리 읽는 글은 영어 markdown으로 둔다.
- 완성되면 총괄이 검수하고 바로 user-doc `show.sh`로 연다(2026-10-21 사용자 지시 "html 보고서는 완성되면 총괄이 브라우저에 띄우고 보고서에는 누구에게 답변을 해야하는지 노드명을 적는다").

## 감독과 검수

- 완료·종료·제거·인계 알림을 받는다. 주기적인 순찰 프로세스는 만들지 않는다.
- 시간 예산을 넘기면 `loom steer <자식> "Report status and blockers."`로 확인한다. 응답이 없으면 `loom status`로 생존을 확인한다.
- 중단이 필요하면 `loom interrupt`로 현재 결과·실패 원인·남은 일을 보고하게 한다. 기존 편집자가 멈췄는지 확인한 뒤 재배정한다.
- 같은 완료 명령이 두 번 실패하거나 환경 문제로 10분 넘게 막히면 부모에게 원인·영향·시도·필요한 결정을 보낸다.
- 부모는 해결 담당자와 조치를 정한다. 관련 자식에게 원래 메시지 번호와 함께 알리고 해결 결과를 확인한다.
- 검수자는 diff, 완료 조건, 검사 출력과 실제 관찰 결과를 대조한다. 실패한 검사를 약화하거나 완료 조건을 줄여 통과시키지 않는다.
- 증거가 없거나 실패했거나 검증 뒤 관련 코드가 바뀌었을 때 검사를 다시 한다. 지금 고칠 수 있는 문제는 반려해 고친다.

## 질문·응답과 대기

- 시작할 때와 `adopted` 알림 뒤에 `loom status`로 현재 부모와 자식을 확인한다. 전송이 실패해도 관계와 `alive`를 먼저 확인한다. 메시지는 현재 부모와 자식 사이에만 보낸다.
- 질문은 `loom send <상대> "QUESTION: …"`으로 보낸다. 출력의 메시지 번호를 기록한다. 노드 번호와 메시지 번호를 구별한다.
- 받은 질문에는 `loom reply <메시지 번호> "ANSWER: …"`로 답한다. 답변에는 원래 질문 번호가 붙는다. 부모가 바뀌어 답변이 거절되면 현재 부모에게 질문 경위와 결과를 보낸다.
- 특정 답변은 `loom wait --reply-to <질문 번호> --timeout <초> --json`으로 확인한다. 자신이 보낸 질문 번호를 쓴다. 시간은 작업 예산 안에서 정한다. 이 대기는 다른 메시지를 소비하지 않는다. 훅이 이미 받은 답변도 찾는다.
- 제한 시간이 지나도 질문은 취소되지 않는다. 같은 질문을 자동으로 다시 보내지 않는다. 관계와 생존을 확인하고 감독 절차를 따른다. 늦은 답변도 원래 질문 번호로 확인한다.
- 같은 질문을 다시 기다리면 첫 답변이 다시 나올 수 있다. 모든 메시지는 메시지 번호로 중복을 걸러낸다.
- 답변과 무관한 일은 계속한다. 기다려야 하면 턴을 끝낸다. 메시지가 오면 데몬이 쉬는 노드를 깨운다(Claude는 비동기 훅, loom 0.1.336부터. Codex·OpenCode 2는 새 턴). 무기한 `loom wait`를 띄우지 않는다. 특정 답변을 명시적으로 확인할 때만 제한 시간 있는 대기를 쓴다.
- 0.1.336 전에 뜬 Claude 노드는 다시 시작할 때까지 옛 훅을 쓴다. 그 노드는 Bash `run_in_background`로 `loom wait --json` 하나를 띄우고 턴을 끝낸다.
- `done`은 작업 완료이며 프로세스 종료가 아니다. `alive: true`인 완료 노드는 피드백을 받는다. 완료 뒤에도 피드백을 기다리면 실행자별 수신 방식을 유지한다. `alive: false`인 노드는 새 이름으로 다시 띄운다.
- `loom done`은 한 번만 부른다. 완료 뒤 수정 결과는 `loom send <부모> "REWORK DONE: …"`로 보고한다. 특정 피드백의 답변이면 `loom reply <피드백 메시지 번호> "REWORK DONE: …"`를 쓴다.
- 메시지 본문은 4,096바이트 이하, 완료 요약은 1,024바이트 이하다. 긴 자료는 파일에 쓰고 경로를 보낸다. `done --file`은 파일 내용 대신 절대 경로를 보낸다. 결과 파일 자체에 메시지 본문 크기 제한을 적용하지 않는다.

## 병합과 회수

- main 반영은 총괄만 한다. 코디는 배정된 통합 브랜치에서 검수한 워커 결과를 합칠 수 있다.
- 병합·검증 명령은 저장소 AGENTS.md와 프로젝트 문서를 따른다. 별도 흐름이 없으면 기준 체크아웃에서 `git merge --no-ff --no-edit <브랜치>`를 쓴다.
- 병합 후 필요한 검사를 한다. 같은 파일을 편집하는 자식에게 기준 브랜치 변경을 알린다. push와 배포는 사용자 요청 범위에서만 한다.
- 미보존 변경, 검증·승인·병합 대기, 사용 중인 사용자 노드와 기준 체크아웃을 보존한다.
- 회수는 그것을 만든 부모가 한다(총괄·코디 모두). 대상은 자식 노드, 띄운 셸 노드, 워크트리와 브랜치, 시험 데몬 같은 백그라운드 프로세스, 임시 폴더다.
- 자식의 결과를 받거나 병합한 직후마다 회수 대상을 확인한다. 결과를 보존했고 더 쓸 계획이 없으면 바로 회수한다. 사용자 확인이나 작업 전체의 끝을 기다리지 않는다.
- 회수 전에 해당 워크트리의 `git status --short`로 미커밋 변경과 추적하지 않는 파일을 확인한다. 검토 증거가 그 폴더에만 있으면 먼저 보존한다. 다른 작업이 사용 중이면 회수하지 않는다.
- 전용 노드를 제거한 뒤, 기준 체크아웃에서 `git worktree remove <경로>`를 실행한다. 병합된 작업 브랜치는 `git branch -d <브랜치>`로 지운다. 강제 삭제하지 않는다.
- 남겨야 하는 워크트리는 경로·이유·담당자·회수 조건을 완료 보고에 적는다. 완료 상태라는 이유만으로 방치하지 않는다.
- 노드 제거는 `loom rm <자식 이름 또는 '#번호'>`로 한다. 자기 자식만 지울 수 있다. 그 자식의 프로세스도 끝난다.
- 지운 자식에게 자식(손자)이 있으면 손자는 내 자식이 된다. 출력이 옮긴 이름을 알린다. 그 노드도 결과를 보존한 뒤 `loom rm`으로 회수한다. 옮길 수 없는 손자가 있으면(깊이·자식 수 상한, 이름 겹침) `loom rm`은 아무것도 바꾸지 않고 이유를 출력한다.
- `loom done`이 아직 사는 자식을 경고하면 그 자식을 먼저 회수한다.
- 완료 보고 전에 `git worktree list`, `git branch`, 가능한 경우 `loom status`로 회수를 확인한다. 삭제 명령 실행만으로 완료했다고 보고하지 않는다.
- 완료 보고에는 결과, 검증 근거, 반영 위치와 남은 일을 적는다. `랩터-3:` 줄에 삭제·재사용·새 부품의 이유를 적는다.
