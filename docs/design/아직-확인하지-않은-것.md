# 아직 확인하지 않은 것

- WSL Cursor 노드가 에이전트 없이 `running`으로 남은 원인(2026-10-23 사람 노드 #538). 그 노드의 진짜 `wsl.exe`(System32 `wsl.exe` 아래), `wslhost.exe`, PTY 호스트, 고아 훅 감싸개와 중계가 남았다. PTY 호스트는 출력을 읽고 있었다(다른 노드와 같은 스레드 모양). 노드를 지운 뒤에도 PTY 호스트와 `wsl.exe`가 남았다. 23:53에 그 `wsl.exe` 아래에서 새 Cursor 훅 `loom.exe`가 떠 데몬에 붙었다. 그 훅에 맞는 Linux 중계는 없었다. 커널 로그에는 「UtilAcceptVsock: Waiting for abnormally long accept」를 되풀이하는 중계가 86개 있었다. 데몬 다시 시작은 그 노드의 마지막 턴 4분 뒤였다. 가설: WSL 쪽이 멈췄다. 에이전트가 살았는지 주기로 보는 검사는 원인을 찾을 때까지 넣지 않는다(2026-10-23 총괄 결정 A).

- Windows Claude 노드의 훅과 `loom guard` 중단. 측정한 Windows PC의 Claude 로그인이 만료되어 Claude 노드를 돌리지 못했다. `loom guard`의 셸 고르기 규칙은 Git Bash 나무로만 확인했다.
- macOS 앱 업데이트 전체 길(새 판 받기, 앱 묶음 바꾸기, 다시 띄우기, 새 데몬이 다시 붙기). Mac이 있는 사람이 두 판으로 확인한다. 근거는 「데스크톱 앱」 업데이트 줄의 소스 읽기와 아래 macOS 실측이다.
- macOS 노드 안의 Claude Code·Codex 로그인과 계정 전환. 러너에는 두 CLI가 없었다.
- Codex app-server를 unix 소켓으로 쓸 때의 메시지 틀. 지금은 `ws://127.0.0.1`만 쓴다.
- Windows 앱 업데이트 전체 길(새 판 빌드, [다시 시작하여 업데이트], 새 데몬이 다시 붙기). 새 판은 Actions로만 빌드한다. 위 실측은 부품마다 따로 했다. 다시 붙기 코드는 Linux와 같다.
- Tailscale Serve가 실제로 보내는 `Host`·`X-Forwarded-Host`와 폰에서 홈 화면에 추가한 웹 앱. 이 기계에는 tailnet과 폰이 없다. 머리글은 만든 요청으로만 시험했다(`origin.rs` 시험, 시험 데몬에 curl).
