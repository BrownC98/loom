# 데몬 하나

한 기계·한 사용자에 데몬은 하나다. 앱 창, 브라우저 탭, `loom open`은 모두 그 데몬의 화면을 여는 뷰어다(2026-10-21 사람 결정 "상태를 하나로 통일하고 프론트는 뷰어의 역할에 충실하게 한다", 그 앞 질문 "웹버전, 네이티브버전 따로 돌아가더라도 동일 데몬을 사용하는 방안은 어떤가?").

| 결정 | 이유 |
|---|---|
| 고정된 곳은 데이터 폴더(「저장」) 하나다. 실행 파일은 어디에 있어도 된다(앱 묶음, `~/loom/bin`, 옮긴 폴더) | 사람 질문 "데몬 설치위치는 고정이라 간주하고 규칙을 세운건가?". 설치 방법마다 실행 파일 자리가 다르다 |
| 데몬은 시작할 때 `<데이터 폴더>/daemon.lock`을 잠그고(배타 잠금), 주소를 잡은 뒤 `<데이터 폴더>/daemon.json`(`url`, `pid`, `version`, `exe`)을 쓴다. 잠그지 못하면 「a daemon already runs at <주소>」를 쓰고 끝난다 | 두 데몬이 한 DB와 한 노드 무리를 함께 쓰지 않는다. OS가 프로세스와 함께 잠금을 푼다. 그래서 남은 파일은 잠금이 아니다 |
| 뷰어는 `loom start`로 데몬을 찾는다. `daemon.json`의 데몬이 답하면 붙는다. 답하지 않으면 같은 실행 파일로 데몬을 새 세션에 띄운다. 포트는 `--listen`, 없으면 `daemon.json`의 포트, 없으면 7420이다. 그 포트를 다른 프로그램이 쓰면 OS가 고른다 | 노드 환경의 `LOOM_URL`은 데몬 포트를 담는다. 다시 띄운 데몬이 같은 포트에서 들어야 살아 있는 노드의 loom 명령이 닿는다 |
| 새 판이 이긴다. `loom start`를 부른 실행 파일의 판이 도는 데몬보다 새로우면 `POST /api/shutdown`으로 그 데몬을 끝내고, `daemon.lock`이 풀린 뒤 자기 데몬을 띄운다. 같거나 옛 판이면 붙는다. 판은 `MAJOR.MINOR.PATCH`를 수로 비교한다 | 앱 업데이트, `install.sh` 업데이트, 앱과 웹 버전을 함께 쓰는 경우가 같은 규칙 하나다. 노드는 데몬보다 오래 살아 새 데몬이 다시 붙는다(「에이전트 실행」) |
| `start`·`open`·`stop`이 끝내는 데몬은 자기 데이터 폴더의 `daemon.json`이 가리키는 데몬이나 `--listen`으로 준 주소의 데몬뿐이다. `daemon.json`이 없으면 `stop`은 아무것도 하지 않고, `start`는 다른 주소에 `/api/shutdown`을 보내지 않는다. 시험 `HOME`의 loom이 7420의 사람 데몬을 끝낸 일(2026-10-21)이 이 규칙의 근거다 | 다른 데이터 폴더의 데몬은 다른 사용자·시험의 것이다. 포트만 보고는 누구의 데몬인지 알 수 없다 |
| `scripts/host.sh`는 늘 `loom stop` 뒤 `loom start`다 | main 빌드는 판 번호가 같을 수 있다. 같은 판이면 붙기만 하므로 바꾼 코드가 올라가지 않는다 |
| DB 마이그레이션은 앞으로만 간다(`src/db.rs`). 자기보다 새 판이 올린 DB를 만나면 데몬은 시작하지 않고 「this loom (<판>) is older than the data in <경로>. Open the newer loom.」을 쓴다 | 옛 판이 모르는 표·열을 쓰다 데이터를 잃지 않게 한다 |
| 제품 상태는 모두 데몬에 둔다: 노드, 저장소, 카드 자리·크기, 설정, 정렬 방향, 미니맵 접힘, 현재 저장소, 사이드바 너비·열림, 닫은 전환 알림. 화면은 설정에서 바꾼 칸만 보내고(JSON Merge Patch), 데몬이 한 잠금·한 트랜잭션에서 지금 설정에 합친다(`Settings::patch`). 그래서 두 화면이 같은 때 다른 칸을 바꿔도 둘 다 남는다. 하나가 바뀌면 데몬이 `/api/events`에 내용 없는 `ViewChanged`를 보내고, 다른 뷰어는 설정·자리·크기를 다시 읽는다. 뷰어에는 시점(카메라·배율)과 마우스 올림만 남는다 | 사람 질문 "동일 데몬이면 화면은 같은 상태를 공유하나 터미널도 동일하게 보이고". 시점은 보는 방법이지 상태가 아니다. 창 크기가 다르면 시점도 달라야 한다 |
| 터미널(PTY)의 열·줄은 상태 하나다. 그 노드 표준 카드의 크기를 기본 글꼴 크기로 잰 값이고, 카드 크기를 바꿀 때 바뀐다. 펼친 카드는 펼친 동안 PTY 크기를 자기 칸에 맞추고, 접으면 카드 크기로 돌아간다(2026-10-22 사람 지시 "크게보기 … 원래대로 보이도록"). 심플 보기 오른쪽 칸도 펼친 카드처럼 PTY 크기를 자기 칸에 맞춘다. 글꼴 크기는 설정 값 그대로이고 칸을 바꾸면 열·줄이 바뀐다(2026-10-22 사람 지시 "일반적인 터미널의 크기를 조정해도 터미널 폰트 크기는 안변하잖아, 사이드탭 터미널도 동일하게 작동하게 만들어"). 표준 보기로 돌아오면 카드가 다시 정한다. 한 노드를 여러 화면이 보면 사람이 지금 쓰는 화면이 PTY 크기를 다시 정한다(tmux `window-size latest`): 창 초점, 탭이 보임, 터미널 초점, 키 입력 때 자기 칸 크기가 PTY 크기와 다르면 보낸다. 보기만 하는 화면은 PTY를 바꾸지 않는다(2026-10-22 사람 지시 "네이티브에서 창크기 조절하니 웹에서 이렇게 보인다. 이 문제를 해결하라"). 폰 화면은 크기를 빌리기만 한다(`PtyRequest::Borrow`): 폰이 그 터미널을 보는 동안만 폰 폭이고, 목록으로 돌아가거나 다른 노드로 가거나 화면이 가려지거나(`GiveBack`) 연결이 닫히면 데몬이 빌리기 전 크기로 바로 돌린다. 그 사이 다른 화면이 크기를 쥐었으면 돌리지 않는다. 빌림과 돌림은 PTY마다 한 잠금 안에서 한다(`NodeHost::borrow`·`give_back`)(2026-10-23 사람 결정 Q442 A "폰을 보는 동안만 폰 폭, 떠나면 바로 PC 크기로 되돌림") | 전에는 보는 화면마다 자기 칸에 맞춰 PTY 크기를 바꿨다. 마지막에 연 화면이 이겨서 다른 창의 터미널 줄이 깨졌다 |
| 웹 버전은 모든 OS에 앱 없이 설치된다. 릴리스에 데몬 실행 파일 `loom-web-linux-x64`, `loom-web-windows-x64.exe`, `loom-web-macos-arm64`가 있다. Linux·WSL은 `scripts/install.sh`, Windows는 `scripts/install.ps1`(`irm … \| iex`, `%LOCALAPPDATA%\loom\bin\loom.exe`)가 받고 바탕 화면 아이콘(`loom open`)을 만든다. macOS의 `install.sh`는 앱을 설치한다(「데스크톱 앱」). macOS 웹 버전은 손으로 받는다. 이미 설치한 macOS 웹 버전은 데몬 업데이트로 `loom-web-macos-arm64`를 받는다. 그 Mac에서 `install.sh`를 다시 부르면 웹 데몬을 끝내고 `~/loom/bin/loom`을 앱에 든 loom을 부르는 껍데기로 바꾼다. 옛 `~/Applications/loom.command`도 그래서 앱의 데몬을 연다. Windows 앱 설치 파일은 시작 메뉴에 「loom (browser)」(`loom.exe open`)를 더한다. macOS `install.sh`는 `~/Applications/loom (browser).command`(앱에 든 `loom open`)를 만든다 | 사람 지시(2026-10-21) "방법2 의 경우 웹버전만 받고 네이티브 앱을 안받은 사람을 커버할 수 없음". 파일 이름의 `web`은 앱 설치 파일(`loom_<판>_x64-setup.exe`)과 가른다(2026-10-22 사람 지시 "파일명에 혼동이 생기지 않도록"). 0.1.698 이하 웹 버전은 옛 이름을 찾아 업데이트하지 못한다. 설치 명령을 한 번 다시 돌린다 |
| 업데이트(`src/update.rs`, 목업 [docs/mockups/web-update.html](../mockups/web-update.html) v2): 데몬이 시작할 때와 6시간마다 Release의 `latest.json`을 보고, 새 판이면 모든 뷰어의 오른쪽 아래 카드와 **설정 › 정보**에 알린다. [업데이트]는 하나다. 데몬 옆에 `loom-app(.exe)`가 없으면(웹 버전) 데몬이 자기 OS의 파일을 받아 자기 파일을 바꾸고(Unix는 rename, Windows는 도는 파일을 `loom.exe.<초>.old`로 바꾼 뒤 새 파일을 넣는다) `loom start --listen <자기 주소>`를 띄운다. 새 판이 이겨 옛 데몬이 끝난다. 옆에 앱이 있으면 앱을 `--update`로 띄우고, 앱은 묻지 않고 Tauri 업데이터로 설치한 뒤 다시 뜬다. 확인은 릴리스 CI 빌드(`LOOM_RELEASES`)만 한다 | 사람 지시(2026-10-21) "데몬이 latest.json을 보고 화면에 알리고, 누르면 받아 바꾸고 다시 뜬다(노드는 산다, 목업 먼저)", "그리고 설정에 현재 버전과 업데이트 확인 및 수동 업데이트 버튼 추가", "웹에서 바로 업데이트 불가함?". 앱 묶음은 서명된 앱 업데이터만 바꾼다. `host.sh` 개발 빌드는 Release 판이 아니라 알리지 않는다 |
| Windows에서는 데몬 하나가 이 PC와 WSL 배포판의 노드를 함께 돌린다. 실행 위치는 저장소 경로가 정한다(`place::of`가 `place::Machine`을 준다): `ssh://<호스트>/<절대 경로>`면 그 SSH 호스트(모든 OS. 파일은 SSH 배포판 호스트로 닿는다. git·노드·작업 폴더는 아직 「SSH hosts are not connected yet」로 실패한다), Windows에서 `\\wsl.localhost\<배포판>\…`(또는 `\\wsl$\…`)면 그 배포판, 아니면 이 PC다. 위치로 갈리는 코드는 `Machine`의 세 변형을 모두 적어, 변형을 더하면 컴파일이 그 자리를 찾는다. 위치의 파일 읽기·쓰기·목록은 `place::Files`다(이 PC·WSL은 `std::fs`와 UNC, SSH는 배포판 호스트 요청). 따로 저장하는 값은 없다. WSL 폴더의 git은 그 배포판의 git이다(`src/git.rs`) | 사람 결정 Q274 "C", 목업 [wsl-place.html](../mockups/wsl-place.html)(M36, Q282 A). 데몬이 둘이면 앱이 어느 데몬을 볼지 골라야 했고 포트·시작 순서가 엇갈렸다. 경로가 이미 위치를 담으므로 같은 사실을 DB에 다시 두지 않는다 |
| 장소 표시는 WSL·SSH 저장소에만 붙인다: 사이드바는 「WSL」(마우스를 올리면 배포판), 저장소 상자와 그래프 제목은 「WSL · <배포판>」이다. SSH 저장소는 세 곳 모두 「SSH · <호스트>」다. API는 장소를 `RepoView.place`·`FolderList.place`(`PlaceView`: 이 PC, 배포판, 호스트) 하나로 준다. WSL 저장소의 경로 글은 배포판 안의 Linux 경로이고, 홈 아래면 `~/…`다. SSH 저장소의 경로 글은 그 PC 안의 경로다. 노드 카드와 워크트리 묶음에는 붙이지 않는다. WSL 요청(노드 띄우기, 폴더 목록)이 0.8초를 넘으면 「<배포판>를 시작하는 중입니다」를 보인다 | 목업 wsl-place.html ②(A)·②′·⑥b, ssh-repo.html ④(M54, Q1911). 저장소 대부분이 한쪽에 있으면 모든 줄의 표시가 되풀이된다. UNC 경로는 앞부분이 길어 잘린다. 배포판 홈은 쓸 때마다 배포판 호스트로 새로 읽는다(`wsl::home`). 기억하지 않는다 |
