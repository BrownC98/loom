# Loom 브리프 공통 규칙

Loom 코디·워커는 [o-mode](SKILL.md)를 따른다. loom이 이 글을 자식의 시작 지시에 늘 넣는다. 브리프의 `Common rules:` 줄은 같은 글을 가리킨다. 역할과 작업 범위는 브리프가 정한다. 사용자 지시가 우선한다.

## 시작

- 저장소 AGENTS.md와 브리프를 읽는다. 확인된 사실과 가설을 구별한다.
- 역할, 통신, 목업 승인과 회수는 위 스킬 안의 절차를 쓴다. 다른 오케스트레이션 규칙을 불러오지 않는다.
- 편집 전 랩터-3 부품 목록을 만든다. 새 부품의 요구, 재사용할 부품과 지울 부품을 첫 `STATUS` 메시지에 적는다.

## 작업과 연락

- 워커는 맡은 조각의 구현과 검증을 끝낸다. 코디는 설계·배정·검수를 맡는다.
- 읽기 전용 원인 조사는 편집 범위 밖까지 할 수 있다. 범위와 계약 안의 구현 방법은 스스로 정한다.
- 편집 범위 확대, 완료 조건·제품 동작·공유 계약 변경은 부모에게 질문한다. 영향받지 않는 작업은 계속한다.
- [질문·응답과 대기](SKILL.md#질문응답과-대기)를 따른다. 보고는 영어로 쓴다. 사용자에게 보이는 글은 사용자의 언어로 쓴다.
- 조정 메시지는 현재 작업에 반영한다. 중단 메시지는 하던 작업을 멈추고 따른다.
- 사용자가 내 터미널에 직접 지시하면 그 지시를 따르기 전에 부모에게 `loom send parent "USER DIRECTION: <사용자 원문> → <할 일>"`로 알린다(2026-10-20 사용자 지시 "사용자가 코디나 워커에 직접 지시를 내렸다면 해당 사실을 상위 에이전트에게 보고"). 승인·선택처럼 결정이면 `USER DECISION:`으로 쓴다. 원문은 고치지 않고 따옴표로 옮긴다. 범위나 계약이 바뀌는 지시면 부모의 답을 기다린 뒤 편집한다. 코디는 자식에게서 받은 `USER DIRECTION`·`USER DECISION`을 같은 형식으로 자기 부모에게 넘긴다.
- `git stash`는 쓰지 않는다. 다른 워크트리와 공유하기 때문이다. 기존 변경은 보존한다.
- 검증은 실제 동작과 완료 조건을 확인한다. 테스트나 단언을 약화해 통과시키지 않는다.

## 완료

- `git status --short`와 diff를 확인한다. 저장소가 요구하는 검사를 마친다.
- 보고에 원인, 바꾼 파일, 검사 명령·결과, 증거 경로, 브랜치와 커밋 SHA를 적는다. 미커밋이면 그대로 밝힌다.
- 남은 위험과 범위 밖 후보를 구별한다. 지금 고칠 수 있는 결함은 먼저 고친다. `랩터-3:` 줄을 넣는다.
- 일을 끝낼 때마다 `loom done`을 부른다. 피드백·재작업을 받으면 노드는 다시 「실행 중」이고, 끝나면 `loom done`을 또 부른다. 요약은 노드 카드에서 사용자가 읽으므로 사용자의 언어로 쓴다(2026-10-20 사용자 지시 "요약은 항상 사용자 언어로 표시"). HTML 보고서는 쓰지 않는다. 사람이 보고서를 요청했다고 부모가 알릴 때만 [사용자 보고서](SKILL.md#사용자-보고서) 형식으로 쓴다. 에이전트용 긴 결과는 영어로 파일에 쓴다. 요약에는 사용자의 언어로 한두 문장과 그 경로를 적는다.
- 완료 뒤 피드백과 재작업 보고는 위 통신 절차를 따른다. 자기 워크트리는 부모가 결과를 확인하기 전에 지우지 않는다.
- `loom done` 전에 자기가 띄운 시험 데몬·백그라운드 프로세스·임시 폴더를 끝내거나 지운다. 증거 파일만 남긴다. 노드의 PTY 호스트(`loom pty-host`)는 데몬을 끝내도 산다. 그래서 시험 `HOME`을 환경에 가진 loom 프로세스를 모두 끝낸다. 실행 파일이 `target/`이든 설치된 `loom`이든 같다(2026-10-21 워크트리를 지운 뒤 PTY 호스트 145개가 남았다. 같은 날 설치된 `loom`으로 띄운 시험 PTY 호스트 10개가 `target/` 규칙을 빠져나갔다). 자기 자식은 [병합과 회수](SKILL.md#병합과-회수)에 따라 회수한다.
- 결과 보고에 전용 워크트리 경로와 후속 작업 여부를 적는다. 총괄은 결과 수용 뒤 [병합과 회수](SKILL.md#병합과-회수)에 따라 정리한다.
